# ae-sdd Skill installation contract

This is the shared file-deployment contract for the [installation](install.md) and [uninstall](uninstall.md) procedures. It describes an Agent-executed operation, not a daemon, workflow state machine or executable installer. The source owner is this file; deployment copies must be byte-identical. The machine-readable plugin discovery record is the system registry at `al-skills/registry.yaml`.

## Package layout

The user-facing entry is `ae-sdd`. Project knowledge (`al-knowledge`) is bundled inside that entry and has no separate installation/discovery prerequisite. A full engineering suite also resolves the four existing packages `al-ra`, `al-spec`, `al-coding`, and `db-operator`; these remain implementation details selected by ae-sdd. Do not expect hosts to discover private capability documents.

With `repo` as the resolved ae-sdd source checkout and `root` as the chosen host Skill search directory, deploy this explicit mapping:

| Source | Target relative to root |
| --- | --- |
| `repo/skills/ae-sdd/SKILL.md` | `ae-sdd/SKILL.md` |
| `repo/skills/ae-sdd/capabilities/al-knowledge/` (verified generated payload) | `ae-sdd/capabilities/al-knowledge/` including CAPABILITY.md and resources |
| `workspace/registry.yaml` | `registry.yaml` at the installed `al-skills` root |
| `repo/capability-catalog.md` | `ae-sdd/references/capability-catalog.md` |
| `repo/references/installation-contract.md` | `ae-sdd/references/installation-contract.md` |
| `repo/references/agents-guidance.md` | `ae-sdd/references/agents-guidance.md` |
| `repo/references/install.md` | `ae-sdd/references/install.md` |
| `repo/references/uninstall.md` | `ae-sdd/references/uninstall.md` |
| `repo/scripts/manage_agents.py` | `ae-sdd/scripts/manage_agents.py` |
| Each of the four separately resolved capability packages | Its own capability-name directory, with required resources |

The ae-sdd plugin exposes one entry Skill; knowledge instructions use CAPABILITY.md, not a nested SKILL.md or plugin manifest. Installation/removal remain references. Every ae-sdd plugin distribution must include the complete private knowledge payload, so knowledge tasks work without the canonical checkout, registry or a standalone knowledge package. Preserve historical independent al-knowledge installations; never choose them instead of the built-in capability or take them over merely because the names match.

The canonical source for the five AL modules is the `al-agent-workspace` root declared in `registry.yaml`: `D:\al-agent-workspace\al-skills`. Resolve exact registered paths. Knowledge is generated by `repo/scripts/bundle_knowledge.py`, preserving resource-relative paths and recording file hashes in `.bundle.json`; verify against its canonical source before packaging. Do not manually maintain copies. `_agents/`, `dist/`, installed runtime directories and backups are products, never source candidates. The other four packages retain their existing independent resource validation and ownership rules.

Reuse an independent capability only when its frontmatter is valid, its `name` exactly equals the requested capability ID, its required local resource closure resolves, and it satisfies every compatibility requirement explicitly declared by the selected distribution or user (such as a version range or contract revision). Record those checks and their source in the dry-run. A mismatch is a conflict; a required version/contract that cannot be established is unresolved, not compatible. This baseline declares no minimum capability versions: absent an explicit requirement, do not invent a version floor or reject an otherwise valid package for lacking version metadata. Reuse then establishes file/package availability only, not semantic compatibility or service readiness. Ambiguous duplicate installations require source selection before reuse.

## Source, target and authorization

Resolve one selected Agent and its actual search root. Do not hard-code a universal host path or change marketplaces, hooks or search configuration. Change only the selected AGENTS targets' managed ae-sdd entry, including explicitly registered mirrors; preserve general/global user rules. A shared root is a shared installation: disclose its consumers and do not describe uninstall as affecting only one Agent. If those consumers are unknown, resolve them before mutation.

Before overwrite or move, resolve absolute source/target/backup paths and validate containment using path components and canonical existing parents. Reject unsafe relative paths, traversal, device/ADS paths, and symlink or junction escapes. A source equal to the target is an existing installation, not proof of managed ownership. Backups and staging must be outside host discovery and outside all source/target package directories.

The dry-run binds sources, targets, hashes and intended actions. Reuse explicit authorization already covering that operation and scope. A changed source, target or destructive action invalidates the affected plan; show the revised scope and resolve authorization before applying it. Dry-run alone never writes a record, backup or target.

## Installation record

Store one UTF-8 JSON record at `root/.ae-sdd-install/manifest.json`. It contains file-deployment facts only. No task, phase, Gate or runtime session state belongs here.

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Integer `1`; unknown versions require an explicit compatible reader |
| `suite` | Literal `ae-sdd` |
| `agent`, `runtimeRoot` | Selected host and canonical absolute search root |
| `packages[]` | Entries keyed by discoverable Skill name |
| `packages[].name` | ae-sdd or one of the four external capability package names; unique within the record. Retain historical standalone entries without taking ownership |
| `packages[].ownership` | `managed` or `external` |
| `packages[].source` | Resolved source directory or distribution identifier |
| `packages[].version` | Declared package version, or null when none exists; never infer it from the catalog version |
| `packages[].files[]` | For managed packages only: root-relative `path` and installed-byte `sha256` for every owned file |
| `guidanceRecord` | Optional reference to persistent guidance.json outside the removable plugin cache |

All Skill file paths must be unique and lie under the entry's own package-name directory. AGENTS ownership is separately managed in `<state-root>/.ae-sdd-install/guidance.json`: schemaVersion=1, suite=ae-sdd, markerId=ae-sdd-entry, and targets mapping canonical paths to region hashes, pre-install file hashes and exact owned whitespace. Explicit targets must match the record. Native package files remain owned by the host; do not fabricate a manual package manifest for them. Do not record secrets or full source contents.

The sole content source is `references/agents-guidance.md`, containing only the ae-sdd entry. General ALSDD/Git/user rules remain unowned. Use manage_agents.py for idempotent insert/update/removal, with backups before apply and hash conflicts preserved. Unmarked sections need explicit reviewed adoption and an exact digest. Preserve legacy `agent-engineering-guidance` aggregate blocks and old agentsGuidance[] records pending reviewed migration; never delete their general rules merely to adopt the narrower scope.

Private knowledge files belong to the ae-sdd package's file list, including its generated payload record. They are not a separate packages[] entry. Removing ae-sdd may remove its unchanged owned private capability files; project `.al-knowledge/` data and any independent historical installation are preserved. Use this same payload rule for Codex plugins and flattened host Skill layouts.

Create ownership only for files actually deployed into previously absent destinations or already owned by a valid record. An existing independent package remains `external`, even when bytes match. An independent version that cannot satisfy the requested suite is a conflict; replacement or ownership transfer requires a separate explicit decision and backup, not an automatic install action.

For updates, compare source bytes, target bytes and the previous record. Matching bytes are unchanged; an owned file whose current bytes differ from the recorded hash is a local modification. Unknown additional files are unowned. Preserve a conflicting package and report it. Remove obsolete owned files only when unmodified, with backup. Keep no-op operations byte-identical, including the record.

## Apply, recovery and removal

Back up every managed file and record that will change. Verify backup hashes before mutation; if backups cannot be made, do not overwrite or remove files. Stage and validate the complete payload, then promote files and record using the host's supported safe file operations. Persist an operation-local action list alongside the external backups: record original and intended hashes, backup paths and intended mutations before applying them, then update completion evidence. Retain it until recovery is no longer needed. Do not promise multi-package atomicity.

If apply fails or was interrupted, use that action list, backups and current hashes to reconcile only files changed by the operation. Restore original files and record, and remove only newly created files still matching this operation's payload. Preserve intervening edits and report incomplete recovery. Never fabricate a successful installation record for a partial deployment.

Uninstall compares recorded hashes against current files and moves only unchanged owned files to backup. Preserve independent packages and packages with local changes. Clean empty directories without recursively deleting unknown contents. Keep residual ownership and the entry and uninstall reference plus its contract until all managed conflicts are resolved; only then remove the entry and the active record. Existing backups are not automatically purged.

## Acceptance scenarios

- Fresh ae-sdd plugin: its single public entry and all private knowledge resources resolve, with no separate knowledge install. Full-suite installation additionally resolves the other four capability packages; every deployed file has ownership evidence.
- Existing independent capability: reused as external; subsequent uninstall preserves it.
- Repeated install: unchanged payload and record; no redundant backups or ownership takeover.
- AGENTS install/update/uninstall: template and owned region match, mirrors receive the same region, outside bytes are unchanged, repeated operations are no-ops and manual changes cause conflicts.
- Missing source/resource: reported before apply; no full-suite success claim or partial silent install.
- Managed update/local edit: update clean owned files; preserve and report conflicting packages.
- Uninstall with extra files or altered hashes: preserve them and retain retry information; report partial removal.
- Missing record, traversal or escaping link: no inferred deletion authority.
- Repeated uninstall: absent managed files are harmless; unrelated entries remain untouched.
- Failed/interrupted apply: recover from verified backups or report exact remaining differences.
- Relocated distribution: entry and both management references resolve, and the private knowledge CLI can check a fixture without the original source repository or a standalone al-knowledge package.

File/frontmatter checks establish package integrity. Claim live host discovery, service availability or actual install/uninstall success only when observed in that environment.
