## DR Review 总则（🔴 贯穿全 SKILL，违反 = 结论无效）

> 以下 4 条标尺是 DR Review 全部阶段必须遵守的执行准则。任何阶段产出的结论违反任一条 → 该结论视为无效，必须返工。

### 标尺 1：证据标准（🔴 禁止裸结论）

**每一条 ✅ / 🔴 结论必须附客观证据**（与 `[[evidence-bound-check-no-bare-checkmark]]` 一致）。

**证据格式强制要求：**

| 结论类型 | 必填证据格式 | 反例（❌ 不可接受） |
|---------|------------|------------------|
| "A1 设计目标与 RA 一致" | `DR §2.1` ↔ `RA §1.2` 的具体定位（章节号 / 表格行号 / 字段定义段落） | "目标对齐了"、"看着合理" |
| "B5 复用扫描覆盖所有实现点" | DR §4 决策清单（显式列出） + 项目资产 §D 复用扫描（显式列出） + 二者逐项打钩 | "扫描过了" |
| "C2 接口路径符合契约入口" | 项目资产 §7 路径模板（显式列出） + DR §8 接口契约（显式列出） + 二者映射矩阵 | "路径对得上" |
| "E1 Story 边界清晰" | DR §12 Story 矩阵（显式列出 N 个 Story）+ RA §3 场景清单（显式列出 M 个场景）+ 覆盖矩阵 | "拆得合理" |

**红线规则：**
- **未发现 ≠ 已确认无**。必须先有穷举清单，才能写"无"。
- 任何无法定位到 DR/RA/项目资产章节的 ✅ 视为"未审查"，不算结论。
- 引用 DR 章节必须 cite 章节号，引用 RA 必须 cite 章节号，引用代码必须 cite 文件:行号。

### 标尺 2：强弱分级（🔴 标尺贯穿，混级 = 风险被稀释）

所有检查项分为三级，reviewer 应把 **80% 精力放在硬门禁上**，不要平均用力。

| 等级 | 含义 | 违反后果 | 处置 |
|------|------|---------|------|
| **🔴 阻断型**（HARD） | 设计目标/架构/数据模型/接口契约存在硬错误 | 单条违反即阻断 Phase 1，必须修复后才能进入下一阶段 | 见各阶段标注 `[HARD]` 的项 |
| **🟠 严重型**（STRONG） | 关键设计缺陷 / 三确原则违反 / 漏报关键场景 | N ≥ 3 条违反阻断，否则记入整改 | 见各阶段标注 `[STRONG]` 的项 |
| **🟡 一般型**（WEAK） | 命名风格 / 章节排版 / 描述模糊 | 仅记录不阻断，列入建议改进 | 见各阶段标注 `[WEAK]` 的项 |
| **🟢 建议型**（INFO） | 经验性建议 / 最佳实践参考 | 不记录，reviewer 自评 | 见各阶段标注 `[INFO]` 的项 |

**漏报升级机制（🔴 标尺 2 配套强制规则）：**
- **一阶段漏报**：本阶段检查项未发现，但下一阶段发现 → 升级为 🟠 严重型
- **多阶段漏报**：同一缺陷在 2+ 阶段均未发现 → 升级为 🔴 阻断型
- **多 reviewer 冲突**：同一缺陷被多 reviewer 提及但等级判定冲突 → 按 [`agent-orchestration-skill.md §8.4.4 不一致项处理决策树`](../cross-cutting/agent-orchestration-skill.md) 处置（取最高等级 + 存疑项 root 复核），🆕 2026-06-25 改为引用横切规范，不再本节点自行定义冲突算法

### 标尺 3：完整性度量（🔴 "覆盖所有"必须先有穷举清单）

**禁止使用绝对化措辞（"覆盖所有"、"无遗漏"）除非有显式穷举清单**。

任何"覆盖"类结论必须遵循**两步法**：

1. **第一步：正向列清单**。在被审对象上穷举所有应被覆盖的项（场景/接口/字段/状态/Story/风险），标注清单来源。
2. **第二步：逐项打钩**。对照清单逐项判定是否覆盖，未覆盖的必须列入缺陷。

**清单模板（按审查对象分类）：**

| 审查对象 | 清单来源 | 穷举方法 | 失败示例 |
|---------|---------|---------|---------|
| 场景 | RA §3 业务场景 | RA 中所有声明的场景 | "场景覆盖了"——但未列场景清单 → 🔴 证据缺失 |
| 字段 | RA §5 数据要素 | RA 中所有业务实体及字段 | "字段都覆盖"——但未列字段清单 → 🔴 证据缺失 |
| 接口 | 项目资产 §7 契约入口 | 项目资产中所有声明的 REST/SPI 入口 | "接口一致"——但未列接口清单 → 🔴 证据缺失 |
| 状态 | DR §9 状态机 | DR 中所有声明的状态枚举值 | "状态机完整"——但未列状态清单 → 🔴 证据缺失 |
| Story | DR §12 Story 矩阵 | DR 中所有声明的 Story | "Story 拆分合理"——但未列 Story 清单 → 🔴 证据缺失 |
| 风险 | RA §9 隐性假设 | RA 中所有识别的隐性假设 | "风险识别了"——但未列风险清单 → 🔴 证据缺失 |
| 约束 | 项目资产 §standards/constraints/ | 9 个约束文件所有相关条款 | "约束承接了"——但未列约束清单 → 🔴 证据缺失 |

> 标尺 3 的工程化体现：阶段 A 加 **A0 应审查对象清单**（见阶段 A 开头），阶段 E 的 E1 是该标尺在 Story 维度的具体实施。

### 标尺 4：语言精确性（🔴 禁用纯主观词）

**禁止使用纯主观形容词做结论。**

| ❌ 禁用 | ✅ 替换为 |
|--------|---------|
| 合理 / 合理吗 | "符合 B3 三确原则的可行性/必要性/合理性 N/M 维度" |
| 清晰 / 清晰吗 | "DR §12 列出 N 个 Story，每个有核心范围/依赖/预计时间（覆盖率 N/M）" |
| 完整 / 完整吗 | "应覆盖 X 项，已覆盖 X 项，缺 X 项（缺失项编号）" |
| 充分 / 充分吗 | "风险识别覆盖 N 种风险场景（应覆盖 N 种）" |
| 必要吗 | "该决策在 N 个备选方案中 P/M 选项被采纳，影响范围 Y" |
| 合理原因 | 引用具体业务/技术依据（"RA §3.2 第 2 条"） |
| 符合规范 | 引用具体规范条款（"project-structure.md §2.3 分层职责第 3 条"） |

**语言精确性红线：**
- 任何"看起来" / "似乎" / "大概" / "应该" / "差不多" / "基本"——一律视为结论无效，必须重写。
- 结论必须可量化或可定位：**测量值（数字/比例）**或**锚点（文件:行号/章节号）**。

## 整体流程

```
触发（dr-generate 完成 / 手动 / 重入）
    ↓
第零步：DR Review 准入检查
    ↓
第一步：读取输入（DR 草稿 + RA 文档 + PRD + 项目资产 + dr-template + 约束）
    ↓
第二步：5 阶段评审（A-E 并行）
    ├─ 阶段 A：业务价值与目标对齐
    ├─ 阶段 B：架构合理性与技术债务
    ├─ 阶段 C：接口契约完整性
    ├─ 阶段 D：数据模型与不变量
    └─ 阶段 E：Story 拆分合理性
    ↓
第三步：缺陷汇总（🔴/🟠/🟡/🟢 分级 + 漏报升级）
    ↓
第四步：生成 DR Review UpdatePlan
    ↓
第五步：🔴 人工审核点（双支柱呈现）
    ↓
第六步：触发 dr-update-skill（按 UpdatePlan 修订）
    ↓
第七步：8 道闸
    ↓
完成 → 进入 dr-update-skill
```

> **并行/串行原则：** 第二步的 5 阶段评审是**只读分析**，可并行（A-E 各派一个子 Agent，读同一份 DR+RA+项目资产，各自产出缺陷清单，主 Agent 汇总）。第三步之后的判定、计划、修复、循环是**写操作**，必须串行（修复会改 DR，影响下一轮所有阶段的判断）。

## Plan-first 更新原则（🔴 DR 修改硬前置）

> **核心规则：DR Review 不直接修改 DR 主文档。** Review 先产出"问题事实 + 判定 + 修复计划"，再由 DR Update 按计划执行。这样避免 AI 一边改一边补理由，也避免计划外重写导致文档漂移。

**强制产物：** `CR-DR-XXX-vN.m-UpdatePlan.md`

**模板：** `templates/design/dr-review-update-plan-template.md`（如不存在则按本文 §第四步 模板生成）

**Plan 必须包含：**
- DR 与 RA / 项目资产 / dr-template / 约束不一致的地方
- 存疑项：需要人工确认，未确认前不得强改
- 模糊项：描述不够可验证、字段来源不清、边界不清
- 每个确认缺陷的目标章节、修改方式、修改摘要、验证方式
- 字段链路与数据模型修订计划（涉及字段、接口、DB、外部依赖时必填）
- 影响分析：是否触发 Story / Story Review / PRD / 项目资产更新

**门禁：**
- 🔴 未生成 `DR Review UpdatePlan` → 禁止触发 dr-update-skill
- 🔴 Plan 中存在 `⚠️ 待讨论` 且无人工确认结果 → 禁止执行对应修改
- 🔴 DR Update 后出现 Plan 未列出的设计变更 → 本轮更新无效，必须回滚该计划外修改或补充新 Plan 后重做

## 第零步：DR Review 准入检查（🔴 硬门禁，未通过禁止进入 Review）

> **为什么需要准入：** 必填章节空白的 DR 进入 Review 会导致 reviewer 产出大量"章节缺失"伪缺陷、修复后又要重审，浪费双方精力。准入检查是**结构性成本控制**。

**准入检查清单（任一未通过 → 拒绝进入 Review，提示作者补完）：**

| # | 准入项 | 判定方式 | 失败提示 |
|---|--------|---------|---------|
| 0-1 | DR 必填章节全部非空 | 检查 dr-template 标注 `核心` 的章节（§2/§3/§4/§5/§7/§12）是否都有实质内容（非占位符、非"待补充"、非"TBD"） | "必填章节 [X/Y] 为空，请补完" |
| 0-2 | RA 文档已生成 | RA 文档存在且 12 章节完整 | "无 RA 文档，DR Review 缺少需求对照基准" |
| 0-3 | PRD 已提供 | PRD 文档存在或用户明确说"无 PRD" | "无 PRD，无法做 A 阶段业务目标对齐" |
| 0-4 | 项目资产已加载 | 调用 `ae-sdd assets read dr-generate --project <projectKey>` 返回 §3 + §5 + §6 + §7 + §D + §E（**禁止**直接全文读取 assets.md） | "项目资产未加载，无法做 B 阶段架构对齐" |
| 0-5 | 设计目标 ≥ 3 条 | 统计 DR §2 设计目标数量 | "设计目标不足 3 条，颗粒度过粗" |
| 0-6 | 关键决策 ≥ 1 条 | 统计 DR §4 关键决策数量，且每条必须有"接受的代价" | "无关键决策或决策缺'接受的代价'" |
| 0-7 | 至少 1 个 Story | DR §12 已拆分至少 1 个 Story | "无 Story 拆分，DR 未向下输出" |
| 0-8 | DR ID 唯一 | DR ID 全局唯一，格式符合 `DR-<PRD-ID>-<序号>` | "DR ID 重复或格式不规范" |
| 0-9 | DR 版本号递增 | 本次进入 Review 的 DR 版本号 ≥ state.json 中记录的上一版本号 | "DR 版本号未递增（当前 v{N-1}，需 v{N} 或以上）" |

**准入失败处置：**

```
【DR Review 准入未通过】
DR ID：{DR-ID}
不通过项：[0-X] xxx
修复建议：[具体补什么]
是否已询问用户授权继续？[否 → 等待用户确认]
```

> **🔴 强制门禁：** 准入未通过 → 拒绝进入第一步读取输入 → 拒绝进入第二步评审。reviewer 不得以"边审边补"绕过准入。

**🔴 机械门禁（v3.9.1，对齐 RA/Coding 三合一）：** 上述 prose 准入清单之外，上下文加载部分必须跑：

## 第一步：读取输入

> **输入清单（5 件套）：**
> 1. DR 草稿（18 章节）
> 2. RA 文档（12 章节）
> 3. PRD 文档（用户提供）
> 4. 项目资产（调用 `ae-sdd assets read dr-generate --project <projectKey>` 加载，**禁止**直接全文读取 assets.md）
> 5. dr-template + 约束文档（standards/constraints/）

### 1.1 读取 DR 草稿

DR 是技术方案的设计产出，Review 需覆盖全部 18 章节，重点关注：
- §1 元信息（DR ID / PRD 引用 / 状态）
- §2 设计目标（核心）
- §3 约束承接（核心）
- §4 关键决策（核心）
- §5 架构概览（核心）
- §6 关键时序
- §7 数据模型（核心）
- §8 接口契约
- §9 状态与业务规则
- §10 故障模式
- §11 权限、安全与审计
- §12 Story 拆分（核心）
- §13 测试策略
- §14 可观测性
- §15 发布、迁移与回滚
- §16 风险
- §17 未决问题
- §18 追踪

### 1.2 读取 RA 文档

RA 是 DR 的需求源头，所有 DR 决策必须可追溯到 RA：
- 业务全景
- 业务场景清单
- 数据要素
- 隐性假设
- 设计方向论证

### 1.3 读取 PRD 文档

PRD 是需求的源头，DR 是 PRD 的技术化映射。**PRD 是 A 阶段业务目标对齐的基准。**

**读取内容：**
- 用户场景清单
- 业务目标（量化指标）
- 功能优先级（P0/P1/P2 标注）
- 业务流程图（高层）
- 涉及角色与权限矩阵

### 1.4 调用项目资产服务

> 🔴 **强制：** 禁止直接读取 `{projectKey}.assets.md` 全文。
> 调用 `ae-sdd assets read dr-generate --project <projectKey>` 返回：

| 返回章节 | DR Review 用途 |

## 第一步 bis：多 reviewer 视角切分（🆕 2026-06-25 — 落地 §8.4.2 节点专属配置）

> **📍 归属：** 本节是 [`agent-orchestration-skill.md §8.4 多 reviewer 默认编排框架`](../cross-cutting/agent-orchestration-skill.md) 在 DR Review 节点的**视角切分配置**。Tier 判定（选几个 reviewer）、交叉对比算法、冲突决策树、降级规则统一查 §8.4；本节只写"DR Review 的 reviewer 视角怎么切"。

### Tier 判定（引用 §8.4.1，本节点关键决策点识别已有支撑）

DR Review 在第零步准入通过后、第二步评审前，按 [`§8.4.1`](../cross-cutting/agent-orchestration-skill.md) 判定 Tier。**本节点准入门禁 0-6（关键决策 ≥ 1 条）天然提供关键决策点识别**：

| Tier | DR Review 触发条件（任一命中即取高 Tier） | reviewer 数 |
|------|------------------------------------------|------------|
| Tier 1 | 微/小规模 DR **且** 无状态机/事务/接口契约/跨服务集成（关键决策 = 0 或均为低风险） | 1 |
| Tier 2 | 中规模 DR **或** 含状态机/事务/接口契约/跨服务集成等关键决策（门禁 0-6 命中） | 2 |
| Tier 3 | 大规模 DR **或** 全新微服务/全新表/涉及资金·状态·权限/跨服务集成 | 3 |

**判定结果写入报告头部** `## Review 元信息` 的 `reviewerTier` 字段。

### DR Review reviewer 视角分工（§8.4.2 三原则落地）

| 视角 | Tier | 审视重点 | 覆盖阶段/检查项 |
|------|------|---------|---------------|
| `reviewer-业务价值` | Tier 2/3 | A 阶段业务目标对齐 + B 阶段场景覆盖（DR 是否真正解决 RA 提出的问题）| A + B 阶段重点 |
| `reviewer-架构拆分` | Tier 2/3 | C 阶段架构设计 + D 阶段数据模型 + E 阶段 Story 拆分合理性 | C + D + E 阶段重点 |
| `reviewer-跨边界` | 仅 Tier 3 | E 阶段 Story 边界无交叉 + 跨 Story 接口/数据变更归属唯一 | E 阶段 E1/E2 重点 |

**视角正交性核查（§8.4.2 原则①/②）：**
- Tier 2：业务价值视角（A+B）∩ 架构拆分视角（C+D+E）= 无交集 ✅；并集 = A+B+C+D+E 全部 HARD 项 ✅
- Tier 3：三视角并集覆盖全部 5 阶段 HARD 项 ✅

### 与 5 阶段并行挖掘的关系（引用 §8.4.6）

> **📍 叠加规则（2026-06-25）：** 5 阶段并行挖掘 = **单 reviewer 内部机制**（每个 reviewer 各自完整跑 A-E 五阶段，满足"不得跳过任何阶段"硬门禁）；多 reviewer 之间**串行**，sub-agent 总数按 reviewer 数计（≤3），不超 §2.2 硬上限 5。视角差异靠 prompt lens 制造（业务价值视角在 A/B 投入更深，架构拆分视角在 C/D/E 投入更深），不靠切分阶段。

## 第二步：5 阶段评审（并行挖掘）

> **执行方式：5 阶段（A-E）是相互独立的只读检查维度，必须并行挖掘以提升效率。**
>
> **并行机制（强制）：**
> 1. 主 Agent 派发 5 个子 Agent，分别负责阶段 A / B / C / D / E
> 2. 每个子 Agent 读取同一份 DR + RA + 项目资产 + dr-template，独立执行本阶段全部检查项，产出本阶段缺陷清单
> 3. 子 Agent 之间不共享中间状态，互不依赖（只读，无写操作）
> 4. 主 Agent 等待 5 个子 Agent 全部返回后，汇总 5 阶段缺陷清单，进入第三步
>
> **降级规则：** 若运行环境不支持并行 Agent，则按 A → B → C → D → E 顺序串行执行，每阶段产出结论后进入下一阶段。无论并行还是串行，**五个阶段的全部检查项都必须执行，不得跳过任何阶段或检查项**。
>
> **重要：** 并行的只是"评审挖掘"（只读）。第三步起的判定、记录、修复都是写操作，必须由主 Agent 串行执行。子 Agent 只负责挖掘和报告缺陷，不得修改任何文档。

## 第三步：缺陷汇总（合理性判定 + 漏报升级）

> **核心原则：** 不是所有挖掘出来的"缺陷"都是真正的缺陷。必须通过 RA 设计意图和合理性分析做决策。

### 3.1 判定流程

```
发现疑似缺陷
    │
    ├── 与 RA 对比：RA 是否有明确设计意图？
    │       │
    │       ├── RA 明确说明了 → 不是缺陷，DR 遵循 RA 设计
    │       │
    │       └── RA 未提及 → 继续判定
    │
    ├── 合理性分析：当前写法是否有合理的业务/技术原因？
    │       │
    │       ├── 有合理原因 → 不是缺陷，记录为"已确认合理"
    │       │
    │       └── 无合理原因 → 确认为缺陷
    │
    └── 影响评估：修复是否会引入新问题？
            │
            ├── 会引入新问题 → 标记为"待讨论"，不自动修复
            │
            └── 不会 → 确认为缺陷，进入修复流程
```

### 3.2 判定结果分类（🔴 必须带归属标签）

> **为什么要带归属标签：** 缺陷根因可能在 DR、可能在 RA、可能在 PRD、可能在项目资产。如果不区分归属，DR 作者会把所有上游问题"翻译"成 DR 缺陷自己修，导致上游问题一直不修。归属标签强制走正确的修复链路。

**判定结果必须同时带两个属性：结果状态 + 缺陷归属。**

| 结果 | 归属标签 | 含义 | 修复链路 |
|------|---------|------|---------|
| ✅ 确认缺陷 | `DR-DEFECT` | DR 设计与 RA 一致，但 DR 本身有缺陷（漏/错/含糊） | 当前 DR 自己修 |
| ✅ 确认缺陷 | `RA-DEFECT` | DR 正确反映了 RA，但 RA 本身有缺陷（漏/错/含糊） | 🔴 必触发 RA Update 改 RA，再同步 DR |
| ✅ 确认缺陷 | `PRD-DEFECT` | DR/RA 都正确反映了 PRD，但 PRD 本身漏了场景 | 🔴 必反馈给 PRD owner，标记为"PRD 修订待办" |
| ✅ 确认缺陷 | `ASSET-DEFECT` | DR 设计违反项目资产（assets/）定义 | 当前 DR 修正以符合项目资产，必要时触发项目资产更新 |
| ✅ 确认缺陷 | `CONSTRAINT-DEFECT` | DR 设计违反约束（standards/constraints/） | 当前 DR 修正以符合约束 |
| ⚠️ 待讨论 | `[归属标签]` | 缺陷归类有歧义，需人工裁定 | 标记为"待人工确认" |
| ❌ 误报 | — | 不是缺陷 | 记录为"已确认合理"，下一轮重新判定 |

**漏报升级机制（🔴 强制执行）：**

| 漏报场景 | 升级结果 |
|---------|---------|
| 一阶段漏报 → 下一阶段发现 | 升级为 🟠 严重型 |
| 同一缺陷在 2+ 阶段漏报 | 升级为 🔴 阻断型 |
| 同一缺陷被多 reviewer 提及但等级冲突 | 按 [`§8.4.4 冲突决策树`](../cross-cutting/agent-orchestration-skill.md) 处置（取最高等级 + 存疑项 root 复核），🆕 2026-06-25 引用横切规范 |
| 🔴 阻断型 + 🟠 严重型 ≥ 5 项 | 整篇 Review 标记为 🔴 不通过，要求重做 DR |

### 3.3 常见误报场景

| 场景 | 为什么不是缺陷 |
|------|--------------|
| DR 缺少某个字段，但 RA 明确说"本期不实现" | RA 设计意图 |
| 表结构缺少 deleted_flag，但业务无逻辑删除需求 | database.md 说"有需求时才加" |
| 接口未使用 PageRequest，但使用游标分页 | DR 偏离声明已记录 |
| AC 未覆盖某个极端边界，但 RA 明确标注为"非目标" | RA 范围定义 |
| 决策"接受的代价"写"无"，但确实是单选项 | 决策人已记录且无备选 |

### 3.4 RA-DEFECT 闭环触发流程（🆕 v3.2 加固 — 2026-06-24）

> **🆕 v3.2 新增：** v3.1 之前的归属标签表已说"RA-DEFECT → 必触发 RA Update 改 RA，再同步 DR"，但**没有显式定义"谁负责闭环 / 怎么闭环 / 何时回到 DR 重审"**。本节固化闭环流程。

#### 3.4.1 触发条件

DR Review 发现缺陷归属为 `RA-DEFECT`（即 DR 正确反映了 RA，但 RA 本身有缺陷）时触发本流程。

#### 3.4.2 闭环 SOP（5 步强制）

```
DR Review 发现 RA-DEFECT
    ↓
第 1 步：标记缺陷为 RA-DEFECT 归属（§3.2 表）
    ↓
第 2 步：触发 requirement-analysis-skill §RA 修订影响分析（见 RA SKILL §3.4.3）
    ├─ RA 修订前：评估"该缺陷是否会让已生成的 DR/Story/Task 进入过期态"
    │   ├─ 是 → 列出受影响的 DR/Story/Task 清单
    │   └─ 否 → 仅修 RA 即可
    ↓
第 3 步：RA 修订完成（新版本 RA 落盘）
    ├─ RA §13 关联矩阵显式标注"本次修订影响了 N 个 DR/Story/Task"
    └─ 通过 `ae-sdd doc save`/`ae-sdd doc finalize` 写新版本
    ↓
第 4 步：🔴 触发下游重审（按影响清单）
    ├─ DR 在草稿/Review 阶段 → 触发 dr-update-skill（按 RA 修订内容回改 DR）
    ├─ DR 已 Review 通过 → 触发 dr-review-skill 新一轮 Review（CR-DR-XXX-vN.m+1.md）
    ├─ Story 已生成 → 触发 story-update-skill（按 RA 修订内容回改 Story）
    └─ Task 已生成 → 触发 task-generate-skill §5bis 全局 Task Review
    ↓
第 5 步：闸门检查
    ├─ 🔴 RA-DEFECT 修复完成
    ├─ 🔴 下游 DR/Story/Task 已重审通过
    └─ 才能标记 DR Review 整轮为 ✅ 通过
```

#### 3.4.3 闭环产物清单（🔴 必填）

### 支柱 1：叙述性讲解

- 决策影响范围是否标注？

- 颗粒度是否在 1~3 天？
- 优先级是否合理？
- 跨服务/跨团队依赖是否清晰？

| 5 | 人工审核点只丢报告不讲故事 | 必须双支柱（叙述 + 表格）呈现 |
| 6 | 不调用 document-storage-skill 落盘 | 必须先调用，再写文件 |
| 7 | 不触发 dr-update-skill | UpdatePlan 通过出闸条件后必须触发 |
| 8 | 漏报升级机制不执行 | 一阶段漏报升级 🟠，多阶段漏报升级 🔴 |
| 9 | 多 reviewer 结论冲突不解决 | 按 [`§8.4.4 冲突决策树`](../cross-cutting/agent-orchestration-skill.md) 处置（取最高等级 + 存疑项 root 复核 + 人工裁定），🆕 2026-06-25 引用横切规范 |
| 10 | 不更新 DR Review ChangeLog | 每轮 Review 必须在 ChangeLog 追加记录 |

## 退出条件

> **📍 Review Loop 公共协议：** 本节退出条件/循环上限/Plan-first 遵守 [`review-loop-skill.md`](../cross-cutting/review-loop-skill.md) 公共协议（v3.4.3），本节只列 dr-review 专属配置。

| 条件 | 说明 |
|------|------|
| 无新增缺陷 | 本轮 5 阶段全部检查项完成后，未发现任何新的确认缺陷 |
| 连续 3 轮无新增缺陷 | 连续 3 轮均未发现新的确认缺陷。本轮发现新缺陷 → 计数器归零；连续 3 轮无新增 → 满足退出条件 |
| DR 已达到 Approved 状态 | DR 主文档状态从 Review → Approved，退出 Review 流程 |

**循环上限：** 3 轮。3 轮仍有 🔴 阻断型缺陷 → 升级用户决策（不无限循环）。

> **🔴 v3.4.3 废弃"每 3 轮暂停问人"：** 之前本节有"每完成 3 轮 A-E 阶段循环自动暂停询问用户"规则，与退出条件矛盾且违反 Loop Engineering 自评估原则，已废弃。AI 自评估达标（连续 3 轮无新增）即退出；3 轮仍有 🔴 才升级用户。

> **🆕 2026-06-25 降级提示落地（§8.4.5）：** 退出流转新增 `reviewerMode` 字段，下游 Story Review 读取后须标注上游逻辑多视角风险，避免 §8.4.5 下游提示沦为空头门禁。
