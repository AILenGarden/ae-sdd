# 测试用例生成策略模板

## 核心原则：有界风险驱动

> 测试组合必须同时回答两件事：它能发现哪一类独立缺陷，以及为什么现有用例不能替代它。测试数量、边界值数量和证伪用例比例都不是质量目标。

**三项原则：**

| 原则 | 含义 | 约束 |
| --- | --- | --- |
| **风险驱动** | 从 AC、契约、不变量、改动分支、历史缺陷、项目坑库和高影响风险建立有限风险登记 | 无证据来源的候选不得准入 |
| **行为等价类** | 按控制流、错误码、持久化约束、外部协议、副作用和失败影响合并候选 | 同一行为分区默认一个代表用例 |
| **最小充分组合** | 在能暴露缺陷的最低充分层级验证，覆盖已准入风险后停止 | 不因层级、字段或状态数量机械扩张 |

### 场景推导前置

风险登记之前先从 Story/API contract 建立 `能力 → 状态 → 独立观察面 → 不变量 → 扰动 → 失败机制` 推导链，再用风险登记裁剪等价候选。`create→read`、`update→read` 只在能力模型命中时产生；查询、异步、批处理、鉴权和并发接口按自身关系生成场景。每条保留用例必须能说明它会抓住什么具体缺陷。

### 有限风险登记

生成用例前先建立候选表。只有选择决策为 `keep` 的候选才形成独立用例；`merge` 必须指向覆盖它的用例，`exclude/defer` 必须写理由。

| 字段 | 要求 |
| --- | --- |
| 证据来源 | AC / 接口契约 / 业务不变量 / 改动分支 / 历史缺陷 / 项目坑 / 高影响风险 |
| 风险等级 | high / medium / low；说明失败影响 |
| 行为分区 | 触发的控制流、错误码、约束、协议或副作用 |
| 独立失败机制 | 现有用例不能暴露的具体缺陷 |
| 目标层级 | L1/L2/L3/L4 中能暴露该缺陷的最低充分层级 |
| 选择决策 | keep / merge / exclude / defer |
| 覆盖关系 | keep/merge 后对应的 TestCase ID |

### 边界测试准入

边界候选满足至少一项才可作为独立用例：

1. 契约显式定义 `min/max/nullability/enum/长度/精度` 或业务不变量。
2. 边界两侧触发不同控制流、错误码、存储约束、外部协议或副作用。
3. 存在历史缺陷、项目坑或本次改动分支证据。
4. 涉及安全、权限、金额、数据丢失、事务、并发、幂等或不可逆状态。

以下候选不得独立保留：任意极值但无契约；同一 validator 和错误分支的重复无效输入；独立字段的全排列；同一缺陷机制在多个测试层级的无差别复制。

### 局部数量上限

| 候选类型 | 默认上限 | 可扩展条件 |
| --- | --- | --- |
| 同一验证规则/错误分支 | 1 个代表无效用例 | 输入触发不同分支、错误码或副作用 |
| 单个显式范围 | 每个行为不同的边界侧 1 个 | `just-inside` 仅在有 off-by-one 证据时增加 |
| 字段组合 | 每个独立业务约束 1 个代表 | 有交互缺陷证据时使用 pairwise；禁止笛卡尔积 |
| 状态转换 | 每个 guard/side effect/失败机制分区 1 个合法和/或非法代表 | 安全关键、不可逆或契约逐项定义时可扩展 |
| 跨测试层级 | 1 个最低充分层级 | HTTP、DB、容器或跨服务带来独立失败机制 |

### 停止条件与预算例外

满足以下条件必须停止继续生成：

- 每个 AC 已被至少一个用例覆盖，一个用例可覆盖多个 AC。
- 所有 `keep` 风险已被映射，关键变更分支和历史回归缺陷已有代表用例。
- 剩余候选不增加新的独立失败机制、控制流、契约、外部协议、断言或测试层级证据。

超出局部数量上限必须登记**预算例外**：新增价值、执行成本、维护成本、不可合并原因和确认人缺一不可。高影响风险不得仅因预算已满而排除，但仍须合并行为等价的重复候选。

## 通用缺陷假设库（🆕 v3.6.3 — 假设驱动的主素材库）

> **定位：** 本库是 testcase-generate「第一步半：缺陷假设挖掘」的**通用素材源**，供"自上而下匹配"使用。素材提炼自 CodeReview T1-T5 真实场景强制 + DB 反模式 + 分层职责红线 B1-B4 + 领域经典 bug 模式（**不**含 D1-D8 测试伪造手段，那属 CodeReview 测试真实性校验职责）。
>
> **使用方式：** testcase-generate 拿本库逐条对照当前 Story，判定"这条假设在本 Story 可能触发吗？"，命中的进入假设清单。本库是**通用基线**，项目特有坑由 §项目特有坑信号源指引补充。

### 降级规则（遵循 ae-sdd 输出核心原则）

- 信号源缺失（项目未沉淀 / 同类 Story 无历史报告）→ 标注"未加载"，**禁止编造**坑内容
- 信号源加载率只影响风险结论的置信度和优先级，不产生测试数量或占比配额
- 项目初期信号源稀少时，使用通用假设库 + Story 业务分析建立有限风险登记；不得为补数量扩大候选

## 风险查漏：三层候选矩阵

> 三层矩阵只用于发现候选，不直接产生用例。每个候选仍须经过边界测试准入、行为等价类合并、局部数量上限和停止条件。

- **第一层：Story 类型风险** — 找该类型常见的独立失败机制
- **第二层：通用风险维度** — 仅在当前 Story 有证据或适用条件时加入候选
- **第三层：测试分层** — 为已准入风险选择最低充分层级

---

## 第三层：测试分层策略

> 第三层决定每个已准入风险在哪个最低充分层级验证。跨层重复只在框架、容器、DB 或外部集成产生独立失败机制时保留。

### 分层定义

| 层级 | 验证目标 | 外部依赖 | 执行速度 | 工具 |
|------|---------|---------|---------|------|
| L1 单元测试 | 业务逻辑正确性 | 可使用 test double 隔离非验收边界；不得关闭接口 AC | 快（ms级） | JUnit + Mockito |
| L2 接口验收 | HTTP 契约 + Controller→Service→Repository/Mapper→测试 DB 完整内部链 | 内部主链真实；外部依赖优先 sandbox，stub 仅作补充故障注入 | 中（s级） | **真实 HTTP：`SpringBootTest(webEnvironment=RANDOM_PORT)` + `TestRestTemplate`** |
| L3 集成测试 | 真实数据库交互（事务、索引、SQL） | 真实 DB（H2/TestContainers） | 中（s级） | SpringBootTest + @Transactional |
| L4 部署环境验收 | 已部署测试环境中的完整业务路径 | 测试环境真实构建；外部 sandbox/stub 证据不得替代主链 | 慢（s级） | HTTP client + test-env base URL + buildId evidence |

> ### 🔴 强制原则：能走真实 HTTP 的接口测试，必须走真实 HTTP
>
> **L2/L4 凡是验证 HTTP 接口行为的用例，必须经过真实网络端口**——本地使用 `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate`（或 server-bound `WebTestClient`/RestAssured/标准 HTTP client），并保持 Controller→Service→Repository/Mapper→测试 DB 内部主链真实。`RANDOM_PORT + @MockBean/@SpyBean` 替换内部 Service、Repository、Mapper 或 Application 组件仍是假链路，不能关闭接口 AC。
>
> **MockMvc 不属于接口验收：** MockMvc 直接调 `DispatcherServlet`，不开真实端口、不走真实网络，不能提供 HTTP acceptance evidence。它也不得作为“降级通过”关闭接口 AC。
>
> **双阶段强制：** 每个 HTTP AC 的 executionPlan verification 必须声明 `boundary=http`、`stages=[local,test-env]`、`internalMocksAllowed=false`。先记录 `http-local` evidence，再把同一 `buildId` 部署到非 loopback 的测试环境并记录 `http-test-env` evidence。缺测试环境、阶段顺序错误、buildId 不同或内部 mock 不为 false 时，结果只能是 FAIL/BLOCKED。
>
> 外部服务优先使用测试 sandbox。WireMock/stub 仅可记录为 `http-external-supplemental` 故障注入证据，不计入 local/test-env 两个必需阶段。

### 各层级验证重点

#### L1 单元测试

| 验证内容 | 示例 |
|---------|------|
| 业务逻辑分支 | 仅覆盖有独立业务语义、控制流或失败影响的分支；等价分支合并 |
| 状态流转规则 | 合法/非法转换判定 |
| 异常抛出 | 条件满足时抛出正确异常 |
| 方法调用顺序 | 钩子按注册顺序调用 |
| 数据转换 | Converter 字段映射正确 |

**不验证：** HTTP 状态码、参数校验注解、数据库约束、事务回滚

#### L2 接口测试

| 验证内容 | 示例 |
|---------|------|
| HTTP 状态码 | 正常 200、签名失败 401、参数错误 400 |
| 参数校验注解生效 | @NotBlank、@Pattern、@Size 拦截无效入参 |
| 请求反序列化 | JSON → Request 对象映射正确 |
| 响应序列化 | Response 对象 → JSON 格式正确 |
| 异常映射 | 业务异常 → 对应错误码和 HTTP 状态码 |
| @SkipAuth 生效 | 无 Token 也能访问 |

**必须验证：** 接口 AC 对应的真实业务规则和持久化结果；只测状态码/序列化而 mock 掉内部主链不算接口验收

#### L3 集成测试

| 验证内容 | 示例 |
|---------|------|
| 唯一索引幂等 | 重复 source_event_id 插入被拦截 |
| 事务回滚 | 异常时数据不落库 |
| SQL 正确性 | 复杂查询条件返回正确结果 |
| 级联更新 | 更新 session 时 latest_message_at 正确 |
| 自动填充 | created_date、last_updated_date 自动写入 |
| 数据隔离 | 测试数据不污染其他测试 |

**不验证：** HTTP 层、外部服务调用

#### L4 端到端测试

| 验证内容 | 示例 |
|---------|------|
| 完整业务路径 | 用户发消息 → 回调落库 → 未读数+1 → 钩子触发 |
| 多 Story 协作 | STORY-001 注册身份 → STORY-002 发消息 → STORY-012 工单重开 |
| 外部服务交互 | 调用融云 SDK 发送消息（WireMock 模拟） |
| 数据最终一致性 | 全链路执行后各表数据状态正确 |

**不验证：** 真实外部服务（用 WireMock/Mock Server 替代）

### 用例层级分配规则

| 场景 | 应在哪层测试 | 原因 |
|------|------------|------|
| 有独立业务语义的逻辑分支 | L1 | 快速验证，无需外部依赖；等价分支合并 |
| 状态机合法/非法判定 | L1 | 纯逻辑 |
| HTTP 参数校验（@NotBlank 等） | L2 | 需要 Spring MVC 框架参与 |
| HTTP 状态码映射 | L2 | 需要异常处理器参与 |
| 唯一索引幂等 | L3 | 需要真实数据库 |
| 事务回滚 | L3 | 需要真实事务管理器 |
| SQL 执行计划 | L3 | 需要真实数据库 |
| 完整业务流程 | L4 | 需要多组件协作 |
| 外部 API 调用 | L4 | 需要 Mock Server |

同一风险不得因“层级完整”在 L1-L4 重复复制。例：业务规则在 L1 已充分证伪时，不再为同一断言补 L2/L3/L4；若 L2 另有序列化风险或 L3 另有数据库约束，则作为独立失败机制分别准入。

## 第一层：按 Story 类型选策略

### 场景类型识别

> 一个 Story 可能同时属于多种类型。类型用于发现候选风险，不代表把每种策略的示例全部转成用例。

| Story 类型 | 识别特征 | 覆盖策略 |
|-----------|---------|---------|
| 状态机 | 包含状态流转、transition、状态枚举 | 按 guard、副作用和失败机制分区 |
| CRUD | 增删改查接口 | 按业务规则、约束和权限风险分区 |
| 回调/Webhook | 外部系统推送、幂等处理 | 签名、幂等、一致性和恢复机制 |
| 定时任务 | 定时触发、批量处理 | 阈值、锁、部分失败和资源风险 |
| 集成/编排 | 调用多个服务、事务编排 | 补偿/回滚语义不同的失败分区 |

---

### 策略一：状态机

1. 列出合法转换与非法转换候选，并按相同 guard、错误码、状态不变断言和副作用分组。
2. 每个行为分区选择一个代表；合法和非法只有行为不同时才分别保留。
3. 多步序列只保留关键生命周期、补偿/重开/超时等会产生独立中间状态风险的路径。
4. 并发与幂等仅在同一资源可能并发写或请求可能重复时准入。
5. 只有安全关键、不可逆、金额/权限状态或契约逐项定义转换语义时，才可通过预算例外扩大为完整转换审计。

---

### 策略二：CRUD

CRUD 按独立业务规则和基础设施约束选择，不按“操作数 × 固定场景数”生成。

| 操作 | 候选风险 |
|------|-----------|
| Create | 代表性成功、显式必填规则、唯一约束、关键关联不存在 |
| Read | 代表性成功、不存在语义、契约定义的分页边界 |
| Update | 代表性成功、目标不存在、适用时的乐观锁或状态规则 |
| Delete | 代表性成功、目标不存在、适用时的关联保护或权限规则 |

同一 validator、同一异常映射或同一 Repository 约束的重复输入合并；没有长度/范围契约的任意极值排除。

---

### 策略三：回调/Webhook

| 场景分类 | 候选风险 |
|---------|-----------|
| 签名 | 成功基线 + 每个独立拒绝机制的代表（格式、缺失、过期只有行为不同才拆分） |
| 幂等 | 首次处理 + 重复事件对唯一索引/幂等键的影响 |
| 数据一致 | 关键关联不存在或状态异常的独立处理机制 |
| 字段校验 | 每个独立 validator/error mapping 一个代表 |
| 异常恢复 | 每种不同回滚、重试或补偿语义一个代表 |

---

### 策略四：定时任务

| 场景分类 | 候选风险 |
|---------|-----------|
| 正常执行 | 有待处理数据、批量处理正确 |
| 空跑 | 无待处理数据，任务正常结束 |
| 边界 | 阈值两侧行为不同或有 off-by-one 证据时准入 |
| 并发 | 多实例可能同时触发且存在锁/幂等机制时准入 |
| 异常 | 按 fail-fast、跳过、重试、隔离等不同语义分区 |

---

### 策略五：集成/编排

| 场景分类 | 候选风险 |
|---------|-----------|
| 全链路成功 | 一条代表性关键路径 |
| 环节失败 | 按回滚、补偿、重试、降级结果分组，不按步骤序号穷举 |
| 事务回滚 | 真实事务边界存在时准入 |
| 超时 | 有超时/重试/熔断设计时准入 |
| 降级 | 核心与非核心依赖具有不同降级语义时分别验证 |

---

## 第二层：通用覆盖维度

> 以下维度是候选发现清单，不是每个 Story 的强制用例清单。只有命中适用条件并通过准入时才保留。

### 维度一：输入字段边界

先识别契约中的 validator、范围、不变量和错误映射，再按行为等价类选择代表。

| 字段类型 | 有效等价类 | 无效等价类 | 边界值 |
|---------|-----------|-----------|--------|
| String（必填） | 正常值 | null、空串、纯空格 | 同一 validator/错误码时选一个代表 |
| String（枚举） | 枚举内的值 | 枚举外的值 | null/空串只在独立规则时增加 |
| Number（范围） | 范围内代表 | 范围外代表 | 上下界行为不同才分别保留 |
| ID | 存在的 ID | 不存在的 ID | null/0 只有契约或独立分支时准入 |
| List | 非空代表 | null 或空列表 | 最大数量仅在显式约束时准入 |

**生成规则：**

- 一个正常路径可同时覆盖多个字段的有效等价类，无需逐字段复制成功用例。
- 同一验证规则、错误码和失败影响默认选择一个无效代表。
- 上下界、`just-inside` 和 `just-outside` 仅在触发独立行为或有 off-by-one 证据时增加。

---

### 维度二：权限与鉴权

| 场景 | 准入条件 |
|------|--------|
| 正常权限 | 接口有权限约束时作为成功基线 |
| 无权限 | 存在鉴权分支时必须保留 |
| 跨资源 | 存在资源所有权/租户边界时必须保留 |
| @SkipAuth 接口 | 存在签名、IP 白名单等替代验证时验证独立机制 |

---

### 维度三：并发

| 场景 | 准入条件 |
|------|--------|
| 同一资源并发写 | 两个请求同时修改同一条记录 |
| 乐观锁冲突 | 版本号不一致时的处理 |
| 分布式锁竞争 | 获取锁失败时的处理 |
| 幂等重复提交 | 相同请求短时间内重复提交 |

**适用条件：** Story 涉及同一资源并发写、锁、版本号或重复请求时准入；同一并发控制机制选一个代表，除非失败影响不同。

---

### 维度四：关联数据状态

对关键关联数据按下游行为分区；多个查询若共享相同不存在处理和错误码，可由一个代表用例覆盖。

| 关联数据 | 必覆盖状态 |
|---------|-----------|
| 存在且状态正常 | 正常路径 |
| 不存在 | 异常路径（抛异常/返回错误码） |
| 存在但状态异常 | 如 session 已关闭、用户已禁用 |

**生成规则：** 只有“查不到”或“状态异常”触发独立业务分支、错误码或补偿行为时才准入；禁止按查询步骤数量机械复制。

---

### 维度五：多步序列（端到端）

选择会验证独立中间状态、回滚、重试或补偿语义的关键业务路径：

| 类型 | 说明 |
|------|------|
| 正常完整路径 | 从创建到结束的完整生命周期 |
| 异常中断路径 | 中间某步失败后的状态一致性 |
| 重试恢复路径 | 失败后重试是否能恢复 |

**适用条件：** Story 涉及多步操作且中间状态或失败恢复有独立风险时准入。相同恢复机制的多个失败点合并为代表场景。

---

### 维度六：字段组合

**当多个字段之间存在业务约束时，覆盖组合场景：**

| 场景 | 示例 |
|------|------|
| 合法组合 | senderType=USER + msgType=TEXT |
| 非法组合 | senderType=USER + msgType=SYSTEM（系统消息不应由用户发送） |
| 条件依赖 | 当 status=RESOLVED 时 closedReason 必填 |

**生成规则：** 仅为显式或可追溯的字段依赖生成代表用例；独立字段禁止笛卡尔积。多个交互因子确有证据时优先 pairwise，完整组合须走预算例外。

---

## 有界性自检清单

生成测试用例后，逐项确认：

- [ ] 有限风险登记中的每个候选都有证据来源、风险等级、行为分区、独立失败机制和选择决策。
- [ ] 每个 AC 至少被一个用例覆盖，且已复用可同时覆盖多个 AC 的用例。
- [ ] 每个 `keep` 风险都有对应 TestCase；每个 `merge` 候选都指向覆盖用例。
- [ ] 边界候选满足边界测试准入条件；任意极值和同 validator 重复输入已排除或合并。
- [ ] 高影响的安全、权限、金额、数据丢失、事务、并发、幂等和不可逆状态风险未因预算被静默排除。
- [ ] 字段组合没有笛卡尔积；状态机没有无依据全矩阵；跨层测试没有无差别重复。
- [ ] 每个用例位于最低充分层级；增加层级时已写明层级特有失败机制。
- [ ] 已满足停止条件，剩余候选不增加新的缺陷机制、控制流、契约、协议、断言或层级证据。
- [ ] 超出局部数量上限的用例都有预算例外记录和显式确认。
- [ ] 无纯凑数用例；用例数量不作为通过依据。
