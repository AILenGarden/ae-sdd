# AI Coding 反模式库

> **定位**：LLM 生成代码的专项防御参考。人类工程师撞这些反模式是「偶发」，LLM 是「高频」——必须在每个 Story / 微任务实现前过一遍。
>
> **使用方式**：
> - 设计阶段末尾：扫一遍 6 类反模式，确认本任务会触发的具体类别
> - 实现阶段每写完一个类：回查对应类别的「检测信号」
> - Coding / CodeReview 阶段：用「检测信号」清单逐项扫代码
> - CodeReview 前：运行 `ae-sdd gate coding-required`，由 `scripts/coding_authenticity_scan.py` 扫描可静态命中的 AP-1~AP-6 反模式
>
> **与主文件关系**：
> - 主文件 `be-coding-thinking-engine.md` §6 是索引 + 与 11 维决策树的交叉引用
> - 本文件是反模式的完整定义 + 实测案例 + 防御代码模板
>
> **配套文档**：
> - `be-coding-thinking-engine.md` — CodingModel 思维引擎主文件
> - `../../skills/phase2-coding/coding-skill.md` — Coding SKILL 执行入口

## 第0章·为什么需要独立反模式库

### 人类 vs LLM 撞反模式频率对比

| 反模式 | 人类工程师频率 | LLM 频率 | 危害等级 |
|--------|--------------|---------|---------|
| AP-1 幻觉 API | 低（IDE 即时报错） | **极高** | 🔴 P0 |
| AP-2 抄旧代码（带 bug 复用） | 中 | **极高** | 🔴 P0 |
| AP-3 过度设计（展示能力） | 低 | **极高** | 🟠 P1 |
| AP-4 注释撒谎 | 低 | **高** | 🟠 P1 |
| AP-5 默认值陷阱（hardcode 不查配置） | 低 | **高** | 🔴 P0 |
| AP-6 上下文漂移（写到中途忘原始需求） | 极低 | **极高** | 🔴 P0 |

> **关键差异**：人类工程师遇到不熟悉的 API 会查文档 / 报错后改；LLM 会「编一个看起来合理的方法签名」直接写。
> 人类工程师知道自己不知道，会停下来问；LLM 会「自信地填充细节」。

## AP-1 幻觉 API（Hallucinated API）

### 定义

LLM 生成代码时调用了**不存在的方法、字段、类、注解、常量、配置项**，看起来语法正确、语义合理，但运行时报 `NoSuchMethodError` / `ClassNotFoundException` / 配置不生效。

### LLM 触发场景

- 训练数据中见过相似 API 名，混合拼凑出「新 API」
- 把 v1 / v2 / v3 版本的方法混着用（如 Spring 5 的 `RestTemplate` 写法 + Spring 6 的 `WebClient` 调用方式）
- 把第三方库的 API 嫁接到另一个库上（如把 MyBatis-Plus 的 `LambdaQueryWrapper` 写法用到 JPA）
- 编造框架特有的注解（如 `@TransactionalEventListener(phase = AFTER_COMMIT, fallback = true)` — `fallback` 不存在）

### 检测信号（实现后 / CodeReview 时扫）

```
□ 方法签名是否在 IDE 中真实存在？（不是「我以为存在」）
□ 字段访问是否符合 getter/setter 命名规范？
□ 注解参数是否在该注解的合法属性列表内？
□ 第三方库调用是否查过该版本的官方文档？
□ 配置项 key 是否在配置中心的合法 key 列表中？
```

### 防御动作

**实现前（强制门禁）**：
1. 任何非 trivial 的第三方 API 调用 → 先在 IDE 里 `Go to Definition` 验证存在
2. 框架特有注解 → 查官方文档版本对应表（Spring / MyBatis-Plus / Dubbo / Nacos 等）

**CodeReview 时（硬门禁）**：
- 不熟悉的 API → 必须有「参考来源」标注（哪个文档 / 哪个版本 / 哪个 demo）

### 实测案例（life 项目）

> **STORY-007 r5 阶段**：自研 `CsTicketStateMachineAppService.transition()` 方案在 CodeReview 时被发现**未对接生产主链路的状态机引擎**（用的自定义枚举 + 自定义方法，对接方是 Spring Statemachine）。LLM 在没有真实 Statemachine 集成文档的情况下，编了一个「看起来对」的状态机方法。
>
> **修复**：删除自研方案，改为基于真实 `spring-statemachine-core` 的 `StateMachine.sendEvent()` 调用。

## AP-2 抄旧代码（带 Bug 复用）

### 定义

LLM 在训练数据中见过相似代码片段，会**直接复制旧实现**（包括其中的 bug / 过时 API / 错误约定），不做适配性修改就直接用到新场景。

### LLM 触发场景

- 「参考」了训练数据中见过的相似功能实现，未做版本/业务差异适配
- 复制了老项目的工具类 / 工具方法（如 `DateUtil.format()` 从 `fastjson` 1.x 时代复制到 2.x）
- 抄了示例代码但没适配项目的包结构 / 依赖版本

### 检测信号

```
□ 复制来的代码是否做过版本对齐？（JDK 8 写法 vs JDK 17 写法）
□ 工具类 / 常量类的 import 是否真的是本项目在用的？
□ 是否有「这个方法在我印象里见过，但我不确定它在本项目存在」？
□ 是否有未使用的 import / 未引用的依赖？
□ 是否有「注释里说 A，实际 import 的是 B」？
```

### 防御动作

**实现前**：
1. 明确列出**当前项目的真实依赖版本**（pom.xml / build.gradle）
2. 复制任何外部代码片段前，确认**版本对应表**

**实现后**：
1. `mvn dependency:tree` 验证 import 的类真实存在
2. IDE 的 `Optimize Imports` 跑一遍，清掉未使用的 import
3. 静态扫描：`grep -r "import xxx" --include="*.java"` 验证导入路径

### 实测案例

> **通用陷阱**：LLM 经常把 Spring Boot 2.x 的 `WebSecurityConfigurerAdapter` 写法用到 Spring Boot 3.x（后者已被废弃）。不报错但配置不生效，安全形同虚设。

## AP-3 过度设计（Over-Engineering）

### 定义

LLM 倾向「展示能力」——为了体现「我会这个模式」，会引入不必要的抽象层、设计模式、泛型化、配置化，**远超业务真实需要**。

### LLM 触发场景

- 「这里用策略模式更优雅」→ 实际上只有 1 种策略，且未来 3 个月内不会增加
- 「这个工具类应该做成 Spring Bean + 配置化」→ 实际上调用方只有 1 处，配置项永远不会变
- 「提取公共父类 / 接口」→ 实际上只有 2 个子类，且没有任何差异化扩展计划
- 「加一层防腐层」→ 上下游协议一致，没必要隔离

### 检测信号

```
□ 这个抽象 / 配置 / 模式服务的调用方有几个？≥ 2 才有价值
□ 这个抽象未来 3 个月内会增加新实现吗？业务方明确说要扩展吗？
□ 删除这个抽象，代码会变得多乱？（如果只是 10 行重复，删除更清爽）
□ 是否有「看起来很专业但实际没人用」的代码？
```

### 防御动作

**设计阶段门禁**：
- 三问原则：≥ 2 调用方？3 个月内会变？业务方明确说需要？
- 三个都是 → 抽象
- 任一否 → 写死，等真需要再重构（重构成本 << 过度设计的维护成本）

**CodeReview 时**：
- 看到 `Strategy` / `Factory` / `Builder` / `Template` / `Abstract` / `Base*` 等词，先问：**为什么要这层抽象？**
- 没有明确理由 → 标记 🟡 待删

### 实测案例（life 项目）

> **STORY-007 r5**：LLM 把状态机的 4 个事件类型（创建/分配/处理/关闭）做成 `StateEventStrategy` 接口 + 4 个实现类。实际上业务只有这 4 个事件，永远不会增加，第 5 个事件如果出现也只会改 1 处。
>
> **修复**：删除 `StateEventStrategy`，4 个事件改成 4 个具名方法或 `switch case`。

## AP-4 注释撒谎（Comments Lie）

### 定义

注释描述的是**「代码在做什么」或「为什么这么写」的谎言**——可能是 LLM 抄旧注释、推断错了业务意图、或后期改代码没改注释。

### LLM 触发场景

- 看到方法名 `validateUser()` → 注释写「校验用户输入合法性」，实际代码校验的是「用户是否有权限」
- 改了实现但没改注释（最常见的「注释漂移」）
- 抄了一段代码，注释也一起抄过来，但业务已经变了

### 检测信号

```
□ 注释和代码逻辑是否一致？（重读代码验证，不要相信注释）
□ 注释里的「为什么」是否还有效？
□ 是否有 @Deprecated / @SuppressWarnings 但没说明原因？
□ TODO / FIXME 是否还有效？是否已经过期？
```

### 防御动作

**实现时**：
- 注释只写「**为什么**」，不写「**是什么**」（代码本身就是「是什么」）
- 改代码 → 同步改注释（CodeReview 检查项）

**CodeReview 时**：
- 注释错误 / 过期 = 🔴 必须删 / 改
- @Deprecated 必须有 `since=yyyy-MM` + `forRemoval=bool` + 替代方案

## AP-5 默认值陷阱（Hardcoded Defaults）

### 定义

LLM 在不确定时倾向**写一个「看起来合理」的默认值**，而不是去查配置中心 / 数据库 / 外部接口拿真实值。

### LLM 触发场景

- 超时时间写 `3000ms`（应该查配置中心）
- 重试次数写 `3`（应该查配置中心）
- 分页大小写 `20`（应该查配置中心 / 用户偏好）
- 缓存 TTL 写 `60s`（应该查配置中心）
- 业务开关写 `true` / `false`（应该读功能开关中心）

### 检测信号

```
□ 代码里所有数字字面量是否都有出处？（grep `\d+`）
□ 是否有 magic number？
□ 是否有 hardcoded URL / IP / 端口？
□ 是否所有「可配置项」都走配置中心，而不是常量？
```

### 防御动作

**实现时门禁**：
- 所有「可能变化」的数值 → 必须从 `@Value` / `@ConfigurationProperties` / Nacos / Apollo 读
- 数字字面量 = 🔴 CodeReview 必须追问来源

**CodeReview 时**：
- 见到 `Integer.parseInt("3000")` / `Thread.sleep(5000)` / `timeout = 3000` → 立即标记
- 见到 `if (flag == true)` / `while (retryCount < 3)` → 立即标记

## AP-6 上下文漂移（Context Drift）

### 定义

LLM 在长上下文（> 500 行代码 / > 30 分钟对话）中会**逐渐偏离原始需求**——写到后半段时，前半段的设计约束已经被「稀释」或「遗忘」。

### LLM 触发场景

- 写到第 N 个类时，已经忘了第 1 个类应该实现什么接口
- 写到第 500 行时，命名风格已经偏离（驼峰改了下划线、动词改成了名词）
- 写到中途，需求被「无意识地扩展」（用户没说要加 XX，LLM 自己加了）
- 多个 Session 接力时，前一个 Session 的约束丢失

### 检测信号

```
□ 当前代码是否符合 §1.1 需求理解的 5 项？
□ 当前实现是否在做需求里没说的事情？（scope creep）
□ 命名 / 风格 / 错误处理模式是否和前几个类一致？
□ 多 Session 接力时，是否重新读过设计文档？
```

### 防御动作

**Session 内**：
1. 每写完一个类 → 回到 §1.1 需求理解 5 项核对一遍
2. 每写完 200 行 → 检查命名 / 风格 / 错误处理是否漂移
3. 长任务拆成多个小任务，每个小任务独立验证（不写超 500 行不验证）

**多 Session 接力**：
1. 每个 Session 开始前，强制重读 `coding-plan.md` / `RA 文档`
2. 不依赖「我记得」——依赖「文档里写的是」

### 实测案例（life 项目）

> **STORY-007 r3→r7 cascade**：5 轮修订中，第一轮明确「不需要做 A」，但到 r5 / r6 轮时，新引入的代码又开始做 A，导致 r7 阶段需要删代码回到原始边界。
>
> **修复**：r7 阶段在 RA 文档 §0.1 显式写了「**反 scope creep 边界清单**」，每次 Session 开始先读这个清单。

## 反模式扫描清单（实现完成 / CodeReview 时强制使用）

```
□ AP-1 幻觉 API：所有非 trivial 的第三方 API 调用已 IDE 验证存在
□ AP-2 抄旧代码：所有复制片段已版本对齐 + import 验证
□ AP-3 过度设计：所有抽象 / 配置 / 模式都已过「≥2 调用方 + 3 个月会变」门禁
□ AP-4 注释撒谎：所有注释和代码逻辑一致，过期 TODO / FIXME 已清理
□ AP-5 默认值陷阱：所有数字字面量都有出处，无 magic number
□ AP-6 上下文漂移：当前实现符合 §1.1 需求 5 项，无 scope creep
```

**判定**：
- 任一未过 → 🟠 必须修订
- AP-1 / AP-2 / AP-5 任意一个未过 → 🔴 阻断，本轮不允许 merge

## 反模式库维护

- **新增**：当发现新的 LLM 撞反模式频率高、有明确防御动作的，反模式条目 + 实测案例 → 提交 PR
- **废弃**：当某个反模式在主流模型上已不再触发（如 GPT-5 解决了幻觉问题），可标记为「legacy」
- **频率跟踪**：每次 CodeReview 扫到某个反模式 → 记录到 `postmortem.md`，季度回看时统计高频反模式 → 重点训练防御
