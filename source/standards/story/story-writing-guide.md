# Story 撰写指南

本指南定义 Story 各章节的适用条件、必填性、来源、写法和 Review 口径。章节顺序、标题、层级和可输出章节只以 `STORY_TEMPLATE` 的 section 元数据为准；本指南不维护章节清单。

## 使用协议

1. 通过 Document Storage 获取 `STORY_TEMPLATE`、`STORY_WRITING_GUIDE` 与 `DOC_DENSITY_STANDARD` 的 `content/sha256`。
2. 把模板正文交给 `story_template_sections` 纯函数，按返回顺序处理章节。
3. 先生成并 Review Primary，再派生 Secondary；正式 Story 只输出适用章节。
4. 每个输出 H2 前保留 ID-only section marker，并在 marker 前保留与 section ID 相同的显式 ASCII 锚点。
5. 总章节目录只列实际输出章节；接口目录只列实际 SPI/REST 接口，所有链接必须可达。
6. 接口详情块使用唯一 `spi-N` / `rest-N` 锚点、三级标题和水平分隔线；复制接口块时同步目录与编号。

## 通用写法

- `必填` 表示所有适用 Story 都必须有可验证结论；`条件必填` 表示条件成立时填写，否则在适用的风险或未决信息中保留判定依据。
- 条件章节不适用时直接从正式 Story 省略，不输出空表、不写无意义的“不涉及”。
- 占位符、示例行和模板说明必须删除或替换。
- 契约、字段、状态、错误码、AC 和风险标注权威来源；来源冲突时停止并请求决定。
- 核心章节按分析→设计→实现集中排列；补充章节不得新增核心业务规则、范围、状态或错误语义。

<!-- ae-sdd:story-guide section-id=metadata -->
## 元信息

- 必填性：必填；作为文档头部信息。
- 内容：文档类型、Story ID、来源 PRD / DR、功能点 ID、标题、类型、优先级、规模、状态、作者、处理人和负责人；兼容关联字段不得与这些正式来源冲突。
- 来源：Work Item state、PRD/RA/DR 绑定关系。
- 红线：正式 ID 不一致，或用逻辑简称代替正式文档 ID。

<!-- ae-sdd:story-guide section-id=user-story -->
## 用户故事

- 必填性：必填。
- 内容：角色、场景、能力、直接价值；用户故事后保留独立“业务价值”章节，写可验证结果或指标。
- 来源：用户决定、PRD 角色与场景、RA 用户问题。
- 红线：技术方案代替用户目标；价值不可观察或无口径。

<!-- ae-sdd:story-guide section-id=business-value -->
## 业务价值

- 必填性：必填；至少填写一个可观察的业务结果，能量化时补充指标。
- 内容：独立说明收益、指标、用户影响和不做该能力的成本；不得只重复用户故事句子。
- 来源：PRD 目标、用户决定、RA 结果和 DR 范围。
- 红线：使用无法验证的口号；把技术实现指标冒充业务价值。

<!-- ae-sdd:story-guide section-id=scope -->
## 范围

- 必填性：必填。
- 内容：明确包含项和不包含项，边界必须能约束实现与验收。
- 来源：PRD/RA 范围、用户决定、DR 边界。
- 红线：把未决事项偷偷写进“不包含”；包含项无法映射到流程或 AC。

<!-- ae-sdd:story-guide section-id=prerequisites -->
## 前置条件

- 必填性：条件必填。
- 内容：业务、权限、数据、配置和依赖条件，并标责任方与验证方式。
- 来源：DR、项目约束、依赖 Story、外部契约。
- 红线：把实现步骤误写成前置条件。

<!-- ae-sdd:story-guide section-id=affected-projects -->
## 涉及工程

- 必填性：必填。
- 内容：受影响工程、父工程、工程类型（BFF / SPI / Service / API）、模块、变更类型和影响方向；新模块需说明父工程注册位置。
- 来源：项目资产、代码核对、DR 工程映射。
- 红线：凭名称猜工程；遗漏只读消费者、配置仓库或前端工程。

<!-- ae-sdd:story-guide section-id=trigger-entry -->
## 触发入口

- 必填性：必填。
- 内容：REST、SPI、事件、任务、UI 或外部入口及触发条件；不适用类型删除。
- 来源：DR 流程、接口资产、调度与事件定义。
- 红线：只写 URL 或方法名，不写调用方与触发条件。

<!-- ae-sdd:story-guide section-id=main-flow -->
## 主流程

- 必填性：必填。
- 内容：从触发到可观察终态的顺序步骤、决策点和用户可见结果。
- 来源：DR 业务流程、规则、状态模型和用户决定。
- 红线：跳过权限、持久化或外部调用；只描述代码调用栈。

<!-- ae-sdd:story-guide section-id=exception-flow -->
## 异常流程

- 必填性：必填；确无异常分支时保留分析依据。
- 内容：场景、触发条件、处理、终态、补偿、用户可见结果和对应 AC ID。
- 来源：主流程、错误码、依赖失败模型、业务规则。
- 红线：只列异常名；吞错后仍宣称成功；终态不明确。

<!-- ae-sdd:story-guide section-id=dependencies-risks -->
## 依赖与风险

- 必填性：必填；无已知风险也要给出核对结论。
- 内容：依赖、风险、第三方服务、偏离基线、SLA、降级和批准方。
- 来源：项目资产、约束、外部契约、DR 风险和用户决定。
- 红线：把未决问题写成已批准决策；凭证或密钥进入 Story。

<!-- ae-sdd:story-guide section-id=interface-contract -->
## 接口契约

- 必填性：条件必填；存在 REST 或 SPI 接口时填写。
- 分组：先按代码和已发布契约的真实现状分为“新增接口”与“复用 / 既有接口”，新增在前、既有在后；每个接口只出现一次。当前不存在且由本 Story 创建的接口才算新增；直接复用、既有扩展和回归验证都归入既有组。
- 既有接口：不能只列接口名或文档链接，必须给出现状证据、本次关系和本次变更边界，并按对应协议完整填写；禁止把设计目标写成当前事实。
- SPI 内容：必须覆盖签名、调用双方、Request / DTO 字段语义、超时、重试、幂等、错误和降级；保持协议中立，不引入 REST 专属字段。
- REST 内容：每个 `REST-N` 按固定顺序覆盖：1) 基本信息（名称、描述、方法、路径、版本、维护人、本次关系、现状证据、本次变更边界）；2) 鉴权安全（Token 方式、参数位置、权限要求）；3) 请求定义（Path/Query/Header/Body 参数表，名称、类型、必填、范围/约束、说明）；4) 响应定义（业务码、消息、data、分页、traceId 和响应示例，其中 envelope 字段必须服从项目 API 约束，不适用字段显式填 `—`）；5) 错误码表（错误码、含义、触发场景、处理建议）；6) 非功能（幂等、限流、超时、重试）；7) 调用示例（cURL/SDK）；8) 版本变更（仅 `CHANGELOG/` 引用）。
- 写法：REST 与 SPI 在分组内继续使用独立的 `REST-N` / `SPI-N` 编号、锚点、三级标题和水平线；接口目录的分组、编号与详情一一对应。
- 红线：新增与既有接口混排；既有接口缺少事实证据；字段只有类型没有语义；只给 JSON 示例不定义字段契约；遗漏四类 REST 请求参数或响应 envelope 字段；在正文写版本历史；用内部 Mock 代替 HTTP 边界验收；接口块上下黏连。

<!-- ae-sdd:story-guide section-id=state-transition-overview -->
## 状态流转总览

- 必填性：条件必填；存在状态变化时填写。
- 内容：当前状态、事件/条件、下一状态、副作用和非法转换处理。
- 来源：RA/DR 状态模型、枚举定义、业务规则。
- 红线：遗漏非法转换；状态名与数据模型不一致。

<!-- ae-sdd:story-guide section-id=error-codes -->
## 错误码

- 必填性：条件必填；存在业务失败或外部可见失败时填写。
- 内容：错误码、协议状态、触发条件、对外信息和重试规则。
- 来源：错误码规范、接口契约、异常流程。
- 红线：同一条件映射多个错误码；泄露内部异常或敏感信息。

<!-- ae-sdd:story-guide section-id=data-model -->
## 数据模型

- 必填性：条件必填；存在持久化变更或字段链路时填写。
- 内容：表字段、索引、DDL、字段链路、枚举、CRUD 和迁移影响。
- 来源：DR 数据视角、schema、代码核对、接口字段。
- 红线：DDL 与字段表不一致；只写表结构不说明读写和迁移。

<!-- ae-sdd:story-guide section-id=configuration-changes -->
## 配置变更

- 必填性：条件必填；新增或改变配置时填写。
- 内容：载体、Key、默认值、环境差异、敏感性、生效和回滚方式。
- 来源：项目约束、配置中心、部署资产。
- 红线：密钥或凭证进入 Story；默认值静默改变线上行为。

<!-- ae-sdd:story-guide section-id=non-functional-design -->
## 非功能设计

- 必填性：条件必填；写操作、外部依赖、权限、性能或失败场景至少覆盖适用维度。
- 内容：幂等、一致性、补偿、性能、安全、观测、灰度和回滚，并给指标与验证方式。
- 来源：约束、CodingModel、SLA、DR 风险。
- 红线：只写“保证高可用”，没有阈值、失败处理或验证方式。

<!-- ae-sdd:story-guide section-id=implementation-design -->
## 实现设计

- 必填性：条件必填；存在非平凡实现决策时填写。
- 内容：先写现有能力复用、方案决策、能力归属和分层边界，再写关键伪代码、事务/锁边界、错误传播和副作用。
- 来源：代码核对、项目资产、CodingModel、接口/数据契约。
- 红线：没有复用扫描就新建；伪代码把业务规则塞进 Repository；伪代码替代完整实现。

<!-- ae-sdd:story-guide section-id=acceptance-criteria -->
## 验收标准

- 必填性：必填。
- 内容：Given/When/Then AC 和验证矩阵；验证项说明边界、真实协议/环境、方法和预期证据。
- 来源：用户目标、范围、流程、契约、风险和测试约束。
- 写法：测试策略与用例映射直接并入验证矩阵；凡进入 Story 路线，必须为该 Story 单独生成并绑定 TestCase，复杂度只影响 TestCase 的场景深度，不影响其是否存在。
- 红线：AC 不可观察；内部 Mock 单独证明集成成功；把计划写成已完成证据。

<!-- ae-sdd:story-guide section-id=testcase-mapping -->
## 用例设计映射

- 必填性：必填；每个 Story 都必须有对应 TestCase 追踪入口。
- 内容：引用 TestCase 覆盖矩阵，并保持 Story ID、AC ID、用例 ID 和自动化状态一致。
- 来源：验收标准、验证矩阵和 TestCase 文档。
- 红线：只写“见测试”而没有文档链接或 AC 映射；在 Story 与 TestCase 中维护冲突的覆盖状态。

<!-- ae-sdd:story-guide section-id=implementation-task-mapping -->
## 实现任务映射

- 必填性：条件必填；需要跨工程、并行或分阶段实现时填写。
- 内容：任务、覆盖章节/AC、工程、依赖和验证。
- 来源：验收标准、实现设计、工程边界。
- 红线：新增 Story 未确认的范围或替代 `executionPlan` 的完整步骤。

<!-- ae-sdd:story-guide section-id=manual-tasks -->
## 人工任务

- 必填性：条件必填；存在审批、配置、数据准备、发布或人工操作时填写。
- 内容：任务、责任方、前置、完成标准和状态。
- 来源：前置条件、配置变更、发布约束和用户决定。
- 红线：把自动化代码步骤重复写成人工任务；没有完成标准或责任方。

<!-- ae-sdd:story-guide section-id=open-questions -->
## 未决问题

- 必填性：条件必填；存在未获权威答案的问题时填写。
- 内容：问题、影响章节/AC、决策人、截止时间和状态。
- 来源：Review finding、上游冲突、依赖确认和用户决定。
- 红线：把已确定事实写成问题；没有影响范围或决策责任人。
