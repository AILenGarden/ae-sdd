# Story 生成标准

> 适用于 `story-generate-skill.md` 的执行标准。此文件只定义生成 Story 时必须满足的输入、决策、阶段输出和验收门禁，不承载流程编排。

## 1. 输入范围

Story 生成前必须读齐以下内容：

- DR 文档
- PRD 文档
- 产品原型
- 项目资产
- `templates/design/story-template.md`
- `strategies/be-testcase-strategy.md`

缺任一项，必须停止并补齐。

## 2. 方案决策基线

在写接口契约、伪代码、第三方服务和 Task 之前，必须先完成实现方案决策。所有非平凡实现点都必须按下面顺序判断：

1. 现有能力复用
2. 成熟方案参考
3. 候选方案比较
4. 五维质量评估
5. 核心能力归属

决策结论必须落到以下三类之一：

- 复用现有能力
- 扩展现有能力
- 新建能力

任何“新建能力”结论都必须说明对可用性、高效性、可维护性、健壮性、可读性的影响。

## 3. 七阶段输出标准

### A. 业务背景与核心价值

必须说明：

- 业务问题
- 目标用户
- 核心价值

### B. 主流程与异常流程

必须说明：

- 关键操作步骤
- 正常链路
- 异常链路
- 触发条件、检测点、处理动作、用户提示

### C. AC 验收标准

必须说明：

- 每条 AC 都能独立测试
- 形式采用 Given-When-Then
- AC 覆盖基线来自 `strategies/be-testcase-strategy.md`

### D. 接口契约

必须说明：

- URL
- Method
- Request 字段
- Response 字段
- 错误码
- 调用时机
- 幂等性

### E. 数据模型

必须说明：

- 表用途
- 字段定义
- 主键 / 唯一索引 / 普通索引
- 审计字段
- 逻辑删除字段

### F. 实现任务映射

必须说明：

- DDD 分层
- 每个 Task 的原子边界
- 依赖关系
- 公共依赖

### G. ①bis 前端接口契约

必须严格遵循：

- [`story-frontend-contract-standard.md`](story-frontend-contract-standard.md)

本阶段不重复制定六维度内容，只负责按标准填充。

## 4. 自检门禁

生成 Story 后必须通过以下门禁：

| # | 门禁 | 通过标准 |
|---|------|----------|
| 1 | 完整性 | 6 个必填章节 + ①bis 六维度齐全 |
| 2 | DR 一致性 | 业务规则 / AC / 接口 / 数据模型 / 任务映射与 DR 100% 一致 |
| 3 | 可执行性 | 每条 AC 可独立测试，每个 Task 可拆解为可执行动作 |
| 4 | 语言精确性 | 禁止纯主观词和空泛判断，必须可定位到原文或证据 |
| 5 | 方案基线 | 非平凡实现点均已完成复用 / 成熟方案 / 候选 / 质量 / 归属判断 |
| 6 | 可评审性 | 命名、路径、结构符合项目资产约束 |
| 7 | 能力归属 | 核心能力只有一个唯一实现点，不得重复实现 |
| 8 | 前端契约 | 六维度完整，无空项，无缺失 |

任一门禁未过，禁止写入 Story 正文。

## 5. 退出条件

Story 生成只有在以下条件同时满足时才算结束：

- Story 主文档已写入
- StoryGeneratePlan 已生成并确认
- Story Review 已触发
- 循环与退出条件符合 `review-loop-skill.md`

## 6. 人工审核讲解

在人工审核点 1 之前，必须主动说明以下 5 个维度：

1. 这个 Story 在做什么
2. 核心流程是怎样跑的
3. 为什么这么设计
4. AC 如何覆盖关键行为
5. 已识别的风险点与未决问题

讲解必须引用 Story 的真实内容，不得只说抽象判断。

## 7. 多 Agent 约束

Story 生成默认只使用 1 个 `story-writer`。

只有在以下情况才考虑拆分为多个子任务或多个 Agent：

- 涉及多个独立文件
- 涉及多个独立评审维度
- 单个 Agent 的输出会明显互相干扰

使用多 Agent 时，必须通过 [`story-writer-prompt-template.md`](../../templates/design/story-writer-prompt-template.md) 约束输入、输出、标准和回写格式。
