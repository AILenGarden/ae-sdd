# v3.6.1 — CodingSKILL 拆分：适配器注册加载协议 + Java3D 适配器（2026-06-30）

## 摘要

把 CodingSKILL 拆成**共有能力库**（语言/项目无关的编码决策知识）+ **语言/项目适配器**（特有编码决策知识）。
共有 `coding-skill.md` 新增 §13「语言/项目适配器注册加载协议」：按项目技术栈（project assets tech-stack）
解析适配器 key（如 `coding-adapter-java`），通过现有 `skill-new` 注册机制 + `plugin_loader.resolve_skill`
命中后，由 AI 运行时读共有 + 适配器两份文件**叠加**应用。**零 loader 代码改动、零破坏**（无适配器注册时
退化为仅共有能力，行为同 v3.5.17）。

首例适配器 `java3d-coding-skill.md` 落地：承载 Java 语言 + icec/life 项目族的「编码决策知识层」
（技术栈锁、DDD 4 层落点、骨架特化、验证姿态特化、命名/错误码、静态扫描特化、14 项踩坑决策库），
不复述项目 `constraints/`+`assets` 的纯规则（指针引用，DRY）。

## 三个设计决策（与用户三轮确认）

| 决策 | 内容 | 备选（未选） |
|------|------|------------|
| 既有改动处理 | v3.5.17 + v3.6.0 两批未提交改动不单独提交，本次拆分叠在脏树上一次性合并提交 | 先分别提交再开拆分（未选） |
| 组装方式 | **共有块 + 运行时叠加**（loader 零改动，适配器走现有 skill-new，AI 运行时读两份叠加） | 实现 skill-extends 章节合并（工作量大，未实现）/ skill-override 整文件替换（DRY 违规） |
| 适配器范围 | **合并单适配器（Java 语言 + icec/life）放母版 L3** 注册进 `plugins/registry.yaml` | 语言与项目分两层 / 只放 life 项目 L1（未选） |

## 为什么用注册表而非合并引擎（探查证据）

ae-sdd 注册表是**路径解析系统**（`plugin_loader.resolve_skill`：一 target → 一文件），**非组合系统**。
`skill-extends`（章节级合并）虽在 spec 文档留位，但**未实现**（甚至不在 `VALID_TYPES` 中，声明会被 🔴 阻断）。
故"叠加"放共有 `coding-skill.md` §13 用 SOP 描述，由 AI 运行时执行（读两份叠加），不依赖未实现的合并能力。
适配器用已实现已测试的 `skill-new`（`provides` 自由路由 key），符合 spec §5.2。

## 触发原因

用户需求："CodingSKILL 要继续拆，CodingSKILL 分为两大块，第一大块是共有能力，第二大块则是加载注册表的，

## 影响范围

- **能力库边界重构**：共有 coding-skill §1-§12 不变，§13 是纯新增（叠加协议，零破坏）
- **注册表首例**：母版 L3 首个真实 skill-new 适配器落地（之前只有 `_example-coding-style` 示例目录）

## 风险与边界

- **风险 A：AI 不执行 §13 叠加协议**（依赖 AI 读两份文件）——同 plugin_loader 现状（注入是建议非强制），属已知设计；后续可演进为 prompt_inject 强制注入，本版不引入。
- **风险 B：adapter 与 constraints/ 规则双源漂移**——靠 adapter 全程指针引用 + 注释"不复述规则"约束；CI 无自动校验，属文档治理债。
- **不做**：不实现 skill-extends 章节合并（留 v3.6+）、不动 prompt_inject 映射表、不拆 be-coding-plan-template（保留原状，adapter 引用）。
