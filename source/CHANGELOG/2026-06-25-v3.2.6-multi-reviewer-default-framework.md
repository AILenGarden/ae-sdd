# 2026-06-25 | ae-sdd v3.2.6 - 多 reviewer 默认编排框架（横切规范 SSOT）

## Summary

**背景/痛点：** ae-sdd 各 Review 节点的"多 reviewer 交叉审"分布不均——Code Review 已有成熟的 A/B/C 三模式（1/2/3 reviewer），但 DR/Story/Task Review 把交叉验证放在"反应式兜底"（准确率<70% 或检测到关键决策点才升级），且"5 阶段并行挖掘"与"多 reviewer 交叉审"两个正交概念在文档里未区分清楚。这导致设计阶段的缺陷（会下游放大）反而防护最弱，且 AI 审自己产出时存在"逻辑自洽陷阱"无法自纠。

**本次做了什么：** 在 `agent-orchestration-skill.md §8.4` 新增"多 reviewer 默认编排框架"作为横切规范 SSOT（所有 Review 节点的多 reviewer 决策唯一真相源），把多 reviewer 从"反应式兜底"升级为"按 Tier 默认分级启用"（Tier 1/2/3 = 1/2/3 reviewer，与 Code Review A/B/C 对齐）。DR/Story/Task/Code Review 四节点落地视角切分配置，code-review 重复算法去重为引用 §8.4.3/§8.4.4，reviewerMode 降级提示链路 DR→Story→Task 全闭合。

**达成的效果：** 设计阶段（DR/Story）缺陷防护强度对齐 Code Review；对抗 AI 逻辑自洽陷阱有了默认机制而非事后补救；横切算法归 agent-orchestration、节点视角配置归各子 SKILL，职责边界清晰。

## 触发原因

- 用户反馈：AI 审自己写的东西容易逻辑自洽，ae-sdd 各 Review 节点的多 reviewer 应该默认启用而非事后补救。
- 设计缺口：DR/Story/Task Review 把交叉验证放"反应式兜底"，与"缺陷越早发现代价越低"原则矛盾；设计阶段缺陷会下游放大，防护反而最弱。
- 概念混淆：文档未区分"5 阶段并行挖掘"（按检查维度拆，防效率）与"多 reviewer 交叉审"（按审视视角拆，防逻辑自洽），两者正交但被混为一谈。
- 重复定义：Code Review 自带交叉对比算法，应上提为横切规范供所有 Review 节点复用。

## 影响范围

- **纯文档/方法论改动**，不涉及运行时代码、门禁行为、CLI 命令（除 `ae-sdd bump` 同步版本号外无工具链改动）。
- **改变多 reviewer 启用策略**：DR/Story/Task Review 从"反应式兜底"改为"按 Tier 默认启用"，执行 Review 时 reviewer 数量行为变化。
- **改变子 SKILL 职责边界**：交叉对比算法/冲突决策树归 agent-orchestration（横切），节点 SKILL 只管视角切分配置（符合 ae-sdd-update-skill 边界原则）。
- **版本号推进** 3.2.5 → 3.2.6，UC-01 三处一致。
- **无破坏性变更**：Code Review A/B/C 模式原样保留（作为 Tier 1/2/3 实例化范本）；5 阶段并行挖掘机制保留；各节点检查清单/门禁条目不变。
