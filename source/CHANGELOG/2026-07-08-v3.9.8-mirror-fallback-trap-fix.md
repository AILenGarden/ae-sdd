# 2026-07-08 | ae-sdd v3.9.8 - mirror-fallback trap fix: .ae-sdd/state.json 镜像可缺

## Summary

2026-07-08 life 项目实测：`.ae-sdd/state.json`（顶层"镜像"）+ `.auto-engineering/Story-004/state.json`（work-item "源"）**两份数据完全相同**，违反 v3.9.0 nested state 单文件设计意图。用户追问："这东西根本就不允许存在，还镜像？"

本次回答：是的，是反模式。**v3.9.0 把它保留为镜像是为老 hooks 提供 O(1) 兼容桥**（CHANGELOG `2026-07-06-v3.9.0` line 14-22 "镜像没人刷新"实证了当时桥的痛点）；**v3.9.1 修了 gate_intercept 让 hooks 直接读嵌套真值后，镜像的最大存在理由已消失**——但 CLI fallback 链仍硬依赖镜像存在。

**本次让镜像从"必须存在"降级为"可缺"，删它也能用**：

1. `_active_state_from_mirror` 镜像缺失时扫描 `.auto-engineering/*/state.json`，按 mtime 选最近活跃
2. `_main_state_path_for_args` 第 213-235 行 fallback 同样扫描源（避免镜像缺失 → state 文件不存在 → default v1 state 的陷阱）
3. `health` 检查项 `'state.json 可读'` 改名 `'state.json 可定位'`——镜像 + 源任一可定位即 pass
4. `TestStateMirrorMissingFallback` 4 个 regression 用例覆盖 4 场景（state read / next-step / health 镜像 + 源 / health 双缺失）

**life 项目实测**：删除 `.ae-sdd/state.json` 后 `state read --json` 仍返回真实嵌套 state 数据，CLI 健康度 9/10 项 pass + 1 项 master-freshness（项目侧 .githooks 配置无关）= **镜像可以作为反模式被删除**。

## Why

### 镜像设计意图 vs 工程实现鸿沟

| 维度 | 设计意图 | 工程现实（v3.9.0-v3.9.6） |
|---|---|---|
| nested state 设计 | 单文件 state.json 在 `.ae-sdd/` 下（v3.9.0 第 4 行） | 实际写**两份**（`.ae-sdd/state.json` 镜像 + `.auto-engineering/{R6}/state.json` 源） |
| hook 兼容 | v3.5-v3.8 时代 O(1) 读镜像顶层 phase 字段 | v3.9.1 改 `gate_intercept` 用 `get_active_phase()` 直接读嵌套后**镜像最大价值消失** |
| CLI fallback | `--project-state` 等显式镜像入口 | 但 `_main_state_path_for_args` 第 213/217 行**硬要求镜像存在**——否则返回 default v1 state（错的） |

### v3.9.0 病灶（CHANGELOG line 14-22 实测）

> "新任务从未跑 `ae-sdd state new` 登记成 workitem，**镜像没人刷新**。"

也就是说"镜像本身"在 v3.9.0 实测里就是反模式设计——设计文档第 4 行写"单文件嵌套"工程实现却落两份。CHANGELOG 没**明确写"v3.9.X+ 镜像可废除"**——本次填补这个文档缺口。

### v3.9.8 之前会发生什么（实测）

```
.del .ae-sdd/state.json
$ ae-sdd state read --json
→ 返回 default v1 state（phase=initialized）
$ ae-sdd health --json
→ state.json 可读 = False（项目未初始化）
```

**这是 trap**：CI / hook / AI agent 跑 ae-sdd CLI 时，`.ae-sdd/state.json` 一删就掉进 default v1 state 的假象。修后：

```
.del .ae-sdd/state.json
$ ae-sdd state read --json
→ 返回真实嵌套 state（stateMachineId=Story-004, phase=story-generated）—— 走 .auto-engineering/Story-004/state.json 源
$ ae-sdd health --json
→ state.json 可定位 = True（"已 fallback 到 work-item 源 (2 个：state.json, state.json)"）
```

## 触发原因

- 用户反馈（2026-07-08 plan 阶段选择 "接受 R6 顶层名"）："关键是.ae-sdd怎么会有顶层的state" "这东西根本就不允许存在，还镜像？"——直指镜像反模式。
- v3.9.7 commit `da4fb57` 修了"`_check_memory_entered` 目录缺失死环"，但**没动镜像兜底**——本次填该坑。
- `tools/lib/state.py`、`paths.py`、`memory_store.py`、`gate_intercept.py` 都不动——**只动 ae-sdd CLI 这层 fallback 行为**。

## 影响范围

### 行为修复

- 镜像缺失时 CLI 不再陷入 "default v1 state" 假象，正确 fallback 到 work-item 源
- `state read` / `state next-step` / `health` 三个被镜像缺失 trap 影响的命令全部修好
- `state write` / `cmd_state_new` 这类**写命令**仍会通过 `_write_active_state_mirror` 自动重建镜像（line 220-227）—— 这是设计意图（写时主动 refresh 镜像），不影响

### 不改变

- **`--project-state` 显式镜像入口**（line 198 / line 1629）：保留 — flat 时代 caller 仍能用
- **`activeStatePath` / `activeWorkItem` 锚点字段**：镜像还在时仍生效
- **v3.8.x 双段目录兼容**：`find_work_item_state_path` 模糊匹配保留
- **R6 顶层命名**：不动
- **`gate_intercept.py` 行为**：不动（v3.9.1+ 已用 `get_active_*` 统一接口读嵌套真值，不依赖镜像）

### 向后兼容性

- 镜像存在时**行为完全等同 v3.9.7**（同用 `_active_state_from_mirror` 第一条优先级）
- 镜像缺失时**新增了 fallback 行为**（之前 throw "default v1 state"，现在走源）
- flat state 项目（`stateModel=flat`）不受影响——`paths.state_path(ade_sdd)` 仍为入口
- 1060 existing tests 无回归（1 重新打勾）

### 风险点

| 风险 | 概率 | 缓解 |
|---|---|---|
| 多 work-item 时误选活跃（mtime 在多目录下不可靠） | 中 | `TestStateMirrorMissingFallback` 仅覆盖单 work-item 场景；多 work-item 仍由 `_active_state_from_mirror` 第一条优先级走镜像 activeWorkItem 字段，mtime 仅作镜像缺失兜底 |
| post-commit install 没同步 3 处 CLI 实例 | **已遇到**（本次 step D-7b） | 手动 cp 同步；后续 install.py 应补一个 `git post-commit` 里强制 cp ae-sdd CLI（需单独 ticket） |
| `tools/bin/ae-sdd` md5 漂移 | 已知 | post-commit 钩子无法 100% 自动同步 3 处实例；交付前手动 cp 兜底 |

### 已知未修（不在本次范围）

- `gate_intercept` (line 2737) `_quick_channel_from_file` 的 mtime 不敏感——不在本次修改
- `prompt_inject` 直接读 `.ae-sdd/state.json` 顶层字段（无 fallback）——受未来 risk 影响
- ae-sdd v3.9.8 仍**保留镜像**作为"写时主动 refresh 的真值缓存"——彻底废除需等到 v3.9.8+ 评估
