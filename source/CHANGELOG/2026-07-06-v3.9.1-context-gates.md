# 2026-07-06 | ae-sdd v3.9.1 - 全流程上下文加载门禁统一强制化（注册表模式）

## Summary

ae-sdd 全流程 6 组 generate/review 中，只有 RA（G-RA-1~6）和 Coding（G-CODEPLAN-SRC/G-14/G-08）的「上下文加载」是「prose + CLI + 门禁」三合一机械阻断；**DR/Story/TestCase/Task 四组长期是软门禁**——`gate_intercept.py` 的 `PHASE_ENTRY_GATES` 只挂产物存在性门禁（G-01/02/04/05），不校验 AI 是否真读齐了 PRD/DR/项目资产/项目约束。`dr-review-skill.full.md:14-21` 和 `task-generate-skill.full.md:14-21` 还官方自认「report-only，无 GATE_REGISTRY 级机械校验」。TestCase generate/review 连「第零步准入检查」章节都没有。

本次采用**注册表模式**补齐：一个 `_check_context_loaded` 函数 + 一张 `CONTEXT_GATE_REGISTRY` 注册表服务 4 个门禁，流程一致用单函数封装，上下文差异走注册表，读文件统一走 `document-storage-skill` 的 `get_constraints/get_assets` API + `paths.find_doc`/`_iter_ra_files`/`_find_prd_files`。四组准入检查从 prose 变成机械阻断，治「AI 不读上下文就过门禁切相」的真空带。

## 设计决策

- **注册表模式 vs 每阶段独立实现**：4 个门禁流程一致（scale 豁免 → phase 感知 → 逐项校验 required），用单 `_check_context_loaded` 函数 + `CONTEXT_GATE_REGISTRY` 注册表，零重复代码；上下文差异（DR 查 RA+PRD，Story 查 DR+PRD，TestCase 查 Story，Task 查 Story+TestCase）走注册表 `required` 字段
- **微链特殊处理**：G-TASK-CTX 对微链豁免 Story/TestCase（微链无 Story/TestCase 产物），注册表用 `required_micro` 字段区分
- **phase 感知**：准入门禁挂在「切到 X-phase」入口，但 check 执行时 `st["phase"]` 仍是前一阶段，故注册表 key 用 gate_id（不用 target_phase）；`pre_phases` 列表判定 stub 通过，`passed_phases` 列表判定 skipped
- **复用现成 API**：`get_constraints(ade_sdd, project_key)` / `get_assets(ade_sdd, project_key)` / `paths.find_doc` / `_iter_ra_files`（G-RA-1 同款）/ `_find_prd_files`（新增），不重新发明读取逻辑
- **与 G-00 互补**：G-00 查资产 7 层索引齐全（结构），新门禁查 `get_assets` 返回非空（可读取），不重复

## 影响范围

- **门禁强度提升**：DR/Story/TestCase/Task 四组的上下文加载从 report-only 变成 blocker；AI 不读齐 PRD/DR/资产/约束将被 `ae-sdd state write --phase X` 的 PreToolUse hook 拦截
- **向后兼容**：pre-phase stub 通过（不阻断 initialized/ra-generated 等早期阶段）；scale 豁免小/微链对应阶段；已过该 phase 的历史 state 不回溯阻断
- **不改变**：RA/Coding 门禁（已是标杆）、phase flow 架构、document-storage API、skill 职责边界
- **软门禁声明精确化**：dr-review/task-generate 的「🟠 门禁强度声明」从「全部 report-only」改为「上下文加载已硬化，内容审查仍 report-only」，诚实反映当前覆盖
