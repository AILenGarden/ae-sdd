# 2026-06-27 | ae-sdd v3.5.3 - 设计-实现一致性迭代检查 SOP

## Summary

**背景/痛点：** ae-sdd 已有 UC-01~07 自动化一致性检查（版本号 / 门禁注册 / 命令注册 / 扫描器分发 / 清单覆盖 / HS 声明定位），但有 4 类盲区它查不到：① HS 规则"声明物理拦截"但实际零实现（HS-4/6/7/8 撒谎）② 幽灵命令整段描述残留（v3.0 sync-tools/rules.yaml/.mjs 与现 Python 实现脱节）③ F-1 交叉验证只覆盖 G-08（其余 gate 谎报不校验）④ 已实现未接入（document_storage.py untracked + 未 import）。2026-06-27 首次执行人工迭代检查即发现 6 项 🔴 文档撒谎 + 3 项 🟡 部分一致，证明 UC 自动检查不足以发现长期潜伏的文档-实现脱节。

**本次做了什么：** 按用户需求"执行一次迭代检查，把这个逻辑写进 SKILL"，将迭代检查方法论固化为 `ae-sdd-update-skill.md` 的可复用维护 SOP。新增 `## 设计-实现一致性迭代检查` 章节：4 步 SOP（① 跑 UC+health+gates 作基线 ② HS 规则 vs 物理实现交叉核对 ③ CLI 命令契约深挖 ④ 已实现未接入扫描）+ 《迭代检查报告》输出模板 + 与 UC 自动检查的关系定位（UC 是改完即跑的快速防线，本节是周期性深度体检，互补不替代）。

**达成的效果：** 迭代检查从"一次性人工动作"升级为"可复用 SOP"，每月/重大变更后可重复执行；明确补 UC 的 4 类盲区，防止文档撒谎长期潜伏；检查报告归档留痕，供下次对比。

## 触发原因

- 用户需求（原话）："执行一次迭代检查，看看有没有设计不一致的实现。把这个逻辑，写进我们的 ae-sdd-update-SKILL 里。"
- 2026-06-27 首次人工迭代检查实证：UC-06 全绿（仅 warn）但深挖出 6 项 🔴 文档撒谎（HS-7/8/4/6 + assets 4 幽灵命令 + sync-tools）+ 3 项 🟡 部分一致（F-1 仅覆盖 G-08 / HS-10 靠文本兜底 / document_storage.py 未接入），证明 UC 自动检查存在结构性盲区，需补人工/Agent 深度核对 SOP。

## 影响范围

- **不涉及运行时逻辑 / 门禁行为 / CLI 命令变更**：纯维护 SOP 文档改动，未新增硬门禁、未改 tools/ 代码、未改 CLI 命令契约。迭代检查本身是"人工/Agent 深度核对"流程，不是 CLI 子命令。
- **不改变已有 UC-01~07 自动检查**：本节定位为 UC 的"深挖层"，互补不替代。UC 仍在 dev-sync 前强制全绿；迭代检查不阻断 dev-sync（报告 + 修复建议，由用户决定是否本次迭代修）。
- **版本号推进 3.5.2 → 3.5.3**：需 UC-01 三处一致（SKILL.md / paths.py / README），已同步。
- **无破坏性变更**：新增维护 SOP，不影响现有流程。
- **按 ae-sdd-update-skill §边界判定表归位**：SKILL 维护工作流 → ae-sdd-update-skill（自身维护），符合"维护规则"职责。
