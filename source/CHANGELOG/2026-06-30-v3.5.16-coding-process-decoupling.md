# 2026-06-30 | ae-sdd v3.5.16 - Task→Coding 解耦：插入独立 CodingProcess 节点

## Summary

**背景/痛点：** 旧架构把"加载上下文 + 产出 CodePlan + 写代码"全塞进 coding-skill（Plan/Execute 双契约），且 CodePlan 产出动作散落在 task-generate 内部子动作（第四步ter + 第六步）。流程管理器无法独立监督"AI 是否走完了 CodingProcess"——AI 可凭记忆写代码绕过 CodePlan 阶段。这正是 coding 能力"垃圾感"的体系性根因（思考权错位 + 无监督）。

**本次做了什么（流程与能力分离）：** 在 Task-Review 和 Coding 之间插入**独立流程节点 CodingProcess**（新建 `coding-process-skill.md`），职责 = 加载 5 上下文（项目约束/技术约束CodingModel/Story/Task/项目资产）+ 调用 CodingSkill 能力做 CodeAnalysis + 出具 CodePlan + 跑门禁 + 移交。coding-skill.Plan 契约剥离为指针，CodingSkill 仅保留 Execute。state 4 子链插 `coding-process` phase。**两层监督**防绕过：硬层（关卡3 校验 coding-process confirm）+ 软层（stop_check ◆ LOADED 自报标记）。

**达成的效果：** CodePlan 产出从"散落 + 无监督"变为"独立节点 + 可监督"。AI 在 coding phase 写 src/ 前，关卡3 硬层强制校验 coding-process 已 confirm（不可谎报）；stop_check 软层校验 AI 响应含 ◆ LOADED 标记（可谎报但提高成本）。CodingSkill 退化为纯执行器，专注按 CodePlan 写代码。

## 触发原因

用户："task 到 codingSKILL 中间还该有一个 coding Process 来对接流程...CodingProcess 要确保加载五个上下文（项目约束、技术约束、Story、Task、项目资产）...流程管理器要始终监督 AI 在此阶段全程调用 CodingSkill"。诊断确认这是 coding 能力"垃圾感"的体系性根因（思考权错位 + 无监督）。

## 影响范围

- **新建**：coding-process-skill.md（独立流程节点）
- **改动**：coding-skill / task-generate / state.py / memory_gate / gate_intercept / stop_check / prompt_inject / SKILL.md / README + 4 测试文件
- **验证**：`ae-sdd update-check` 13/13 全绿；**756 测试全过**（含新增 TestCodingProcessHardGuard 2 用例）
- **监督机制**：硬层（关卡3，不可谎报）+ 软层（stop_check，提高成本）两层组合

## 关键技术决策

1. **形态**：独立 SKILL 文件（非编排层节点）——用户选定
2. **监督策略**：产物校验 + 自报标记——鉴于 Read 不触发 hook，"真加载"不可强证明（探索确认），改为两层组合
3. **CodeAnalysis 能力归属**：仍在 CodingSkill（④bis SOP），CodingProcess 调用而非持有
4. **task-generate 改造范围**：只移交编排动作，不丢门禁（TC-5,8,9/TR-7 保持，因产出内容不变只是调用方变）

## 已知限制

- **C2 软层 compact 后失效**：stop_check 只看最后一段响应，compact 后 ◆ LOADED 标记可能丢失。硬层关卡3 不依赖 transcript，兜底保护
- **Read 不触发 hook**："AI 真加载 SKILL" 物理不可观测，所有监督都是"提高绕过成本"而非"强证明"
- **关卡3 except 兜底放行**：session 异常时新校验静默放行（与现有兜底一致）
