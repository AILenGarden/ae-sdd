# 2026-06-25 | ae-sdd v3.4.0-proposal — 节点相对状态模型（覆盖小/微任务）

> **状态：设计提案（Proposal），未实施。** 本文件是对 ae-sdd 状态模型缺口的诊断 + 修订提案，按 `ae-sdd-update-skill.md §步骤 4.5` 落档 CHANGELOG 留痕。**未修改任何 SKILL 母版文件，未跑 dev-sync。** 实施需用户确认后走 §实施计划。

## Summary

ae-sdd v3.0 起 4 类需求路由引入了 3 种非 Story 任务形态（小任务 `Task-*` / 微任务 `Plan-*`），但状态持久化模型（state.json）自始至终只有 Story 作用域一种 schema：路径写死 `.auto-engineering/{STORY-ID}/state.json`，字段全是 Story 语义（`storyId / storyVersion / codingRound / currentPhase / completedSteps`）。

结果是**路由模型有 4 类任务，状态模型只接得住 1 类**——小/微任务成为"无状态孤儿"：不记日志、不可恢复、不可审计，ae-sdd 对它们的"编排"沦为空话（编排的前提是有状态可追踪）。本次 v3.4.0 提案引入**节点相对状态模型**：state.json 作用域从 Story 改为**任务（按 txnName）**，引入 `entryNode` 作为任务类型原语（而非规模枚举），按入口节点分生命周期深度；Story 任务的 Phase/step 作为 `entryNode=Story` 的兼容视图保留。

本提案与 v3.3.0 PRD 级状态机**互补不冲突**：v3.3.0 往上叠（PRD > Story），本提案往下覆盖（Plan/Task 入口节点也有自己的状态）。

## 根因诊断（实测案例）

**触发场景：** 用户在 life 项目（非 git 仓库）对一个已交付的 STORY-020 代码文件发起"代码质量优化"微任务。ae-sdd 路由判定为类型 4（微任务，套 Story 7 区 0 区），按路由表应直接交棒 `coding-skill.CodingSkill.Plan`。

**实际发生的错误：** root agent 在路由判定阶段读了 `STORY-020-BE/state.json`（Phase 3 / human-review-4-final / 已完成），被其 Story 状态机信息污染，把一个全新微任务当成"对 STORY-020 的后续修补"处理，导致路由判定过重、把微任务路径走成了重流程。

**根因链路：**

1. 目标文件属 STORY-020 → 系统里唯一的 state artifact 是 `STORY-020-BE/state.json`（Story 作用域）
2. 没有 `Plan-im-domainmessage-quality-opt/state.json` 这种小/微任务状态文件存在（schema 不支持）
3. root agent 读 STORY-020 的 state.json **不是临场失误，是状态模型缺口的必然后果**——系统只给了这一个状态文件可读
4. 读完被 Phase 3/完成态信息污染路由判定

**这不是"agent 没守规矩"，是 SKILL 没给规矩。** 路由阶段"读哪个 state、读哪个 txnName 的 state"在 SKILL.md 里没有明确定义，默认套用了重任务"按 STORY-ID 读 state"的习惯。

## 真正的设计裂缝（修正前序误判）

> 注：本节修正 root agent 在诊断初期列出的 5 条"裂缝"。其中 G-00 资产门卫、14 门禁统一适用、非 git 仓库降级等经用户指正后**撤回**——那些是门禁措辞问题或合理设计。唯一站得住的是状态模型缺口，即本提案主题。

**裂缝：路由模型有 3+1 类任务，状态模型只有 1 类作用域。**

| 任务类型（路由层原语） | 事务命名 | state.json 作用域（当前） | 状态可追踪（当前） |
|---|---|---|---|
| 大任务（入口节点 DR） | `{STORY-ID}` | `.auto-engineering/{STORY-ID}/` | ✅ |
| 中任务（入口节点 Story） | `{STORY-ID}` | `.auto-engineering/{STORY-ID}/` | ✅ |
| 小任务（入口节点 Task） | `Task-{服务}-{简述}` | ❌ 无 schema | 🔴 无状态孤儿 |
| 微任务（入口节点 Plan） | `Plan-{服务}-{简述}` | ❌ 无 schema | 🔴 无状态孤儿 |

路由层从 v3.0 起承认小/微任务是合法任务，状态层从 v1.0 起只认 Story。**两层脱节 6 个版本未收口。**

## 核心设计：节点相对状态模型

### 设计立场

任务类型不是规模枚举（`micro|small|story`），而是**这个任务从流水线的哪个节点进入**。流水线 = `需求分析 → DR → Story → Task → Plan`，任务身份 = 入口节点。规模只是"挑入口节点"的人话别名。

> 用户原话定调："任务类型可能是按定位到的节点来定的，节点分为 PRD 需求分析阶段-DR-Story-Task-Plan"。

### 节点即原语映射

| 规模标签（派生别名，人话） | 真正的原语：入口节点 | 生命周期内激活的节点 |
|---|---|---|
| 微任务 | **Plan**（coding-skill） | `[Plan]` |
| 小任务 | **Task**（task-generate） | `[Task, Plan]` |
| 中任务 | **Story**（story-generate） | `[Story, Task, Plan, CodeReview]` |
| 大任务 | **DR**（dr-generate） | `[DR, Story, Task, Plan, CodeReview]` |
| 从 PRD | **需求分析**（requirement-analysis） | `[RA, DR, Story, Task, Plan, CodeReview]` |

### state.json 新 schema（任务作用域 + 节点相对 + 事件日志）

**路径：** `.auto-engineering/{txnName}/state.json`（txnName 不限于 STORY-ID，含 `Task-*` / `Plan-*`）

```json
{
  "txnName": "Plan-im-domainmessage-quality-opt",
  "entryNode": "Plan",                    // ← 任务类型原语 = 入口节点
  "originStory": "STORY-020-BE",          // ← 仅溯源，不归属（目标文件来自哪个 Story）
  "activeNodes": ["Plan"],                // ← entryNode 起往后才激活（Plan 任务只激活 Plan）
  "nodeStates": {
    "Plan": { "subState": "coding-done", "round": 1 }
  },
  "events": [                             // ← append-only 事件流（用户诉求：什么时候重入了什么状态）
    { "ts": "2026-06-25T10:00", "event": "entered-node", "node": "Plan" },
    { "ts": "2026-06-25T10:20", "event": "plan-generated" },
    { "ts": "2026-06-25T10:40", "event": "coding-done" },
    { "ts": "2026-06-25T10:45", "event": "completed" },
    { "ts": "2026-06-28T09:00", "event": "reopened", "reason": "follow-up tweak" },
    { "ts": "2026-06-28T09:30", "event": "completed" }   // ← 用户诉求：重新进入完成态
  ],
  "currentState": "completed",
  "lastUpdated": "2026-06-28T09:30"
}
```

### 与 Story 级 schema 的兼容（向后兼容）

现有 Story schema 的 `currentPhase / currentStep / completedSteps / codingRound` **不是另一套东西**，是 `entryNode ∈ {Story, DR, 需求分析}` 时的特化视图：

- Phase 1 = `{DR, Story, Testcase}` 节点集合
- Phase 2 = `{Task, Plan, Coding}` 节点集合
- Phase 3 = `{CodeReview}` 节点集合
- `currentStep` = `currentNode` + `nodeStates[currentNode].subState` 的扁平投影

Story 任务迁移后保留 Phase/step 视图作为兼容层，`entryNode=Story` 时自动投影；小/微任务（`entryNode ∈ {Task, Plan}`）不启用 Phase 视图，只有节点级 `nodeStates`。

### 路由阶段"读哪个 state"规则（直接堵住根因）

| 用户输入 | 读哪个 state | 禁止 |
|---|---|---|
| "从 STORY-X 继续" / "重入 Y" | 读 `.auto-engineering/{STORY-ID}/state.json` | — |
| 全新任务（"优化代码"/"加个缓存"/"改个枚举"） | 路由判定出 txnName 后，读 `.auto-engineering/{txnName}/state.json`（不存在则视为新任务） | 🔴 **禁止读 originStory 的 state.json**——originStory 仅作溯源字段，不构成状态归属 |

> 这条规则直接堵住 root agent 在本次案例中读 `STORY-020-BE/state.json` 的错误。微任务的 `originStory` 是"我这个任务碰了 STORY-020 的文件"的溯源标记，不是"我归属 STORY-020 状态机"的归属声明。

## 触发原因

- **实测案例暴露根因：** life 项目 STORY-020 微任务路由判定被 Story state.json 污染（详见 §根因诊断）
- **路由-状态脱节 6 版本未收口：** v3.0 引入 4 类需求路由（承认小/微任务合法），状态模型从 v1.0 起只有 Story 作用域，至今未补
- **v3.3.0 只解决"往上叠"：** PRD 级状态机覆盖 PRD>Story，但 Plan/Task 入口节点的状态归属仍空缺
- **用户诉求明确：** "如果有小任务、微任务，state.json 也要记日志的呀，说什么时候什么时候重入了什么状态，什么时间执行完成，什么时间重新进入完成态"——要求 append-only 事件流 + 重入/完成/重新完成可追溯
- **用户定调原语：** "任务类型可能是按定位到的节点来定的，节点分为 PRD 需求分析阶段-DR-Story-Task-Plan"——明确 entryNode 为任务类型原语，而非规模枚举

## 影响范围

- **运行时逻辑变更：** 是（state.json schema 扩展 + 路由阶段 state 读取规则）
- **CLI 变更：** 是（`state read/write` 新增 `--txn` 参数，旧 `--story` 降为语法糖）
- **门禁数变化：** 否（不新增 G-XX 门禁；可选未来加 G-STATE：路由阶段禁止跨任务读 state）
- **文档存放路径变更：** 是（新增 `.auto-engineering/{txnName}/state.json`，与现有 `{STORY-ID}/` 及 v3.3.0 `{PRD-ID}/` 三层共存）
- **版本号推进：** v3.3.0 → v3.4.0（minor 递增，状态模型重大扩展）
- **破坏性变更：** 否（Story 任务 schema 向后兼容，Phase/step 作为兼容视图；旧 `{STORY-ID}/state.json` 自动按 `entryNode=Story` 识别）
- **与 v3.3.0 关系：** 互补不冲突。v3.3.0 = PRD 级（往上叠）；v3.4.0 = 节点相对（往下覆盖小/微任务）。三层状态：PRD（聚合）→ Story/Task/Plan（任务）→ events（事件日志）
