# 2026-07-10 | ae-sdd v3.9.21 - 门禁按会话 engage 按需启用

## Summary

用户反馈"没用 ae-sdd 的 Agent 也被 hook 锁了"。定位根因：`gate_intercept.check_intercept` 只要项目存在 `.ae-sdd/` 目录就调 `resolve_default_state` 按 phase 锁工具，而该函数的单候选兜底层（`work_item_context.py:318-321`）**无条件**命中——只要项目里有 1 个 active work-item，就锁死所有会话，不管该会话是否调过 `/ae-sdd`。用户确认期望语义是"没调 /ae-sdd 前 hook 完全不工作，调了之后才启用校验"。本次引入"会话 engage 标记"机制实现该语义：`prompt_inject` 检测到 `/ae-sdd` 触发词时写入会话级 engage 标记（`.ae-sdd/.session-engaged/<session-key-hash>.json`），`gate_intercept` 在 `resolve_default_state` 之前检查该标记——有则正常按 phase 锁，无则直接放行。engage 标记按 session_key 维度，子 Agent 继承父会话 session_id 时随主会话 engage；用户说"退出 ae-sdd"/"不锁了"等退出词时清除标记，恢复放行。

## 触发原因

- 用户反馈"没用 ae-sdd 的 Agent 也被 hook 锁了"，Claude 客户端实测确认全局 hook（`~/.claude/settings.json` PreToolUse）按工具名匹配不按会话意图匹配。
- 源码核查确认 `check_intercept:964-985` 的判断链"找到 .ae-sdd/ → resolve_default_state → 按 phase 锁"缺少"本会话是否 engage"判定；`resolve_default_state` 单候选兜底对未 engage 会话也生效。
- 已有 session 绑定机制（`prompt_inject` 每轮 `bind_session=True`）只用于 work-item 路由，不作为门禁开关，且单候选兜底不写绑定——无法直接复用。

## 影响范围

- 涉及运行时门禁逻辑（PreToolUse hook 的 engage 判定），**改变核心语义**：从"项目有 .ae-sdd/ 就锁所有会话"变为"调了 /ae-sdd 才锁该会话"。
- 破坏性变更：未 engage 的会话不再被门禁拦截（这是本次目的，但下游依赖"无脑锁"行为的场景需注意）。对已 engage 的会话，门禁行为与改动前完全一致。
- 版本号推进：`3.9.20` → `3.9.21`（需 `distribute.py` 同步到全局安装的 skill 副本才会在 D:\Item\life 等下游项目生效）。
- 既有测试债（23 个基线失败，用老式 `.ae-sdd/state.json` 镜像格式）不受本次改动影响——全量对比零新增回归。

## 验证方式

- `python -m pytest tools/tests/test_gate_intercept.py -q` 全部通过（131 passed，含新增 8 engage 用例）。
- 全量 `python -m pytest tools/tests/ -q` 对比基线：零新增回归（改动前 23 failed / 改动后 23 failed，失败集合完全相同，均为既有测试债）。
- 人工核对 engage 生命周期：`is_session_engaged` False → `mark_session_engaged` → True → `disengage_session` → False。
- 端到端验证（life 项目）：未 engage 会话发 Bash 放行（修复核心目标）；已 engage 会话按 phase 锁；非 ae-sdd 项目放行。
