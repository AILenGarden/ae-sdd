# Story Generate — 从 DR 生成 Story Skill

> **核心定位：** 与 `story-review-skill.md` 同等地位 — Story Generate 是**设计阶段**的执行（从 DR → Story），Story Review 是设计阶段的**评审**（校验 Story）。两者结构对齐。
>
> **与现有 SKILL 的分工：**
> - `ae-sdd-skill.md` = 流程编排（Phase 1 ① 在哪）
> - **`story-generate-skill.md`（本文件）** = Story 生成的环节内具体规则（怎么生成）
> - `story-review-skill.md` = Story Review 的环节内具体规则（怎么审）
> - `story-update-skill.md` = Story 修改的环节内具体规则（怎么改）
> - [`templates/design/story-template.md`](../../templates/design/story-template.md) = Story 空白模板
>
> **🔴 核心立场（2026-06-06 新建）：** 之前 Phase 1 ① 节点只有 AE-skill 角色 1（`story-writer`）的 5 行描述，**没有独立 SKILL**。本次新建补齐。

## 📦 文档存放前置调用（🔴 横切依赖）

> **🔴 强制：** 本 SKILL 生成的 Story 文档在写入磁盘前**必须先调用 [`document-storage-skill.md`](../cross-cutting/document-storage-skill.md)** 的 API，**不再手写路径**：
> 1. **路径**（§0.6.1 `resolve_path()`）：通过 `intent=STORY` 自动定位到 `ae-sdd-doc/iterations/{YYYY-MM-DD}/Story/`
> 2. **命名 + 版本号**（§0.6.7 `save_doc()`）：**设计类文档带 v{major}.{minor}**（重入时 v 递增，旧版本保留）
> 3. **重入判定**（§0.6.11 `get_latest_version()`）：Story 重入时**新增版本**（v 递增），不修改历史
> 4. **关联性分析**（§0.6.8 `choose_iteration()`）：业务=0 ∧ 逻辑=0 → 强制问用户
> 5. **ChangeLog**（§5 ChangeLog 机制）：`save_doc()` 自动追加
> 6. **.gitignore**（§0.6.13 `check_and_update_gitignore()`）：首次写入时自动维护

**本 SKILL 输出文档与 document-storage-skill API 调用对应：**

| 输出文档 | API 调用 | 命名规则 | 重入时动作 |
|---------|---------|---------|----------|
| Story 主文档 | `save_doc(intent="STORY", storyId, version={major:1,minor:0})` | v{major}.{minor} | 新增版本（v 递增）|
| Story Supplement | `save_doc(intent="STORY_SUPPLEMENT", storyId)` | 不带版本号 | 原地累加 |
| Story-WriterReport | `save_doc(intent="STORY_WRITER_REPORT", storyId)` | 带 r{N} | 新增（r 递增）|
| 跨轮 Review 对比表 | `save_doc(intent="REVIEW_COMPARE", storyId, version="v1-to-v2")` | 带 v1-to-v2 | 新增（每对比）|

> **调用示例：** 详见 `document-storage-skill.md §15.5.3` 完整调用流程。

## 🧠 阶段记忆强制调用（🔴 横切依赖）

> **🔴 强制：** Story 生成必须读取 RA / design 记忆，避免重复遗漏用户已确认的规则、缺口和边界。Story 输出后必须写入 design 记忆。

```bash
ae-sdd memory enter --phase design --story <STORY-ID>
# 生成 Story
ae-sdd memory write --phase design --story <STORY-ID> --kind decision --summary "<Story关键设计决策/冲突/未决项>"
ae-sdd memory exit --phase design --story <STORY-ID>
```

`memory exit` 未通过 = Story 节点未完成，禁止进入 Story Review 或 TestCase。

## 目标

从 DR 文档生成**完整、可执行、可评审**的 Story 文档，目标：

- 业务背景与核心价值清晰（让读者 5 秒内理解）
- 主流程 / 异常流程 / AC / 接口契约 / 数据模型 / 任务映射 6 大必填章节齐全
- ①bis 前端接口契约 6 维度完整（契约完整性 / 调用流程 / 状态展示 / 错误码 / 边界场景 / 联调支持）
- 与 DR 100% 一致（业务规则/边界场景/验收标准/数据模型/接口契约）
- 生成后可立即进入 Story Review SKILL 评审
- 7 阶段挖掘 + 实现方案决策基线 + 8 道闸全过

## Story Generate 总则（🔴 贯穿全 SKILL，违反 = 结论无效）

### 标尺 1：完整性（🔴 "覆盖所有"必须先有穷举清单）

| 维度 | 穷举清单来源 |
|------|-------------|
| 业务背景 | DR 业务背景 + 目标用户 + 核心价值 |
| 主流程步骤 | DR 业务步骤 + PRD 用户旅程 |
| 异常流程 | DR 异常场景 + PRD 边界场景 + 隐性边界（如幂等/并发/超时）|
| AC 验收标准 | DR 验收标准 + 业务规则 + 边界场景 + `strategies/be-testcase-strategy.md` 的类型策略与通用覆盖维度（每个 AC 都可独立测试，且覆盖核心验收维度）|
| 接口契约 | DR 接口契约 + SPI 服务名（项目资产 §7）|
| 数据模型 | DR 数据模型 + 项目资产 §6.5 数据库规范 |
| 任务映射 | Story 内 Task 列表（按 DDD 分层排序）|
| 前端契约（①bis）| PRD + 产品原型 6 维度 |

### 标尺 2：DR 一致性（🔴 Story 不得偏离 DR）

- 业务规则、验收标准、边界场景、接口契约、字段定义 **必须** 与 DR 100% 一致
- 偏离必须明确标注"偏离声明"，**禁止**默认一致
- 不一致 → 走异常路径 A1（修正 Story 或触发 DR Update）

### 标尺 3：可执行性（🔴 "可评审"必须先有可执行细节）

- 每个 AC 都有 Given-When-Then（可写测试）
- 每个接口都有完整 Request/Response 字段 + 错误码
- 每个数据模型字段都有类型/约束/注释
- 每个 Task 都有"做什么 + 涉及工程层"

### 标尺 4：语言精确性（🔴 禁用纯主观词）

| ❌ 禁用 | ✅ 替换为 |
|--------|----------|
| "用户会喜欢" / "系统应该" | 引用 DR/PRD 的具体条款 |
| "合理的" / "自然的" | 给出"满足 X 业务规则"或"符合 X 约束" |
| "等等" / "其他" | 穷举所有场景，禁止省略 |
| "大概" / "可能" | 引用 DR 原文 + 行号 |

### 标尺 5：实现方案决策基线（🔴 复用优先 + 成熟方案参考 + 五维质量）

Story 中所有实现方案都必须先完成决策基线，不只第三方能力需要复用检查。

**适用范围：** 接口设计、状态机、领域服务、应用编排、Repository/Mapper、定时任务、消息/通知、缓存、幂等、并发控制、外部集成、前端接口适配、测试支撑等所有实现点。

**强制顺序：**
1. 先做现有能力复用扫描：项目资产、真实代码、依赖 Story、历史 Story/Task、公共组件、平台能力、团队约定。
2. 再列业内成熟实现方案：通用架构模式、成熟框架/库、框架官方推荐做法、团队已有成功实现。
3. 再做候选方案取舍：复用 / 扩展现有能力 / 新建能力。
4. 最后用五维代码质量标准评估：**可用性、高效性、可维护性、健壮性、可读性**。

**不复用的强制说明：** 每个“不复用/新建”结论必须说明对五维质量的影响，尤其是可维护性影响；禁止用“更方便”“先这样”“后面再统一”作为理由。

**红线：** 未完成实现方案决策基线，禁止生成接口契约、实现伪代码和实现任务映射。

```

    ↓

    ↓

    ├─ 阶段 A：业务背景与核心价值

    ├─ 阶段 D：接口契约（REST + SPI）
    ├─ 阶段 E：数据模型
    ├─ 阶段 F：实现任务映射（Task 列表）
    └─ 阶段 G：①bis 前端接口契约（6 维度）
    ↓
Story 结论：{STORY-ID}
    ↓
第三步：合理性自检（与 DR 一致性 / 可执行性 / 完整性）
    ↓

    ↓

    ↓

    ↓

    ↓

```

## Plan-first 生成原则（🔴 写 Story 前硬前置）

> **🔴 强制：** Story 生成前**必须**先有 StoryGeneratePlan，按 Plan 执行。
> **Plan-first 与 Review-first 的差异：** Review SKILL 是"问题-修复计划"双向链（review→plan→update）；Generate SKILL 是"DR-章节-初稿"单向链（DR→plan→draft）。

**Plan 内容：**
- DR 章节清单（哪些章节要展开成 Story 章节）
- 7 阶段挖掘 SOP（每阶段要查什么）
- 实现方案决策基线：所有实现点的复用扫描、成熟方案参考、五维质量评估和能力归属
- 模板填写顺序（先填必填章节，再填可选章节）
- 与 Story Review 的衔接点（生成完立即进 Review）

## 第一步 bis：实现方案决策基线（🔴 生成实现设计前硬门禁）

> **目的：** 在写接口契约、实现伪代码、第三方服务和 Task 拆分之前，先证明“为什么这么实现”。所有实现方案都必须复用优先，并参考业内成熟方案；没有证据的方案选择视为不可评审。

### 1bis.1 实现点清单（先穷举）

从 DR / PRD / Story 主流程中穷举所有需要实现的能力点。至少覆盖：
- 对外接口 / 跨服务接口 / 事件接口
- 领域规则 / 状态机 / 业务不变量 / 计算规则
- 应用编排 / 事务边界 / 补偿重试
- Repository / Mapper / 数据转换 / 索引和查询
- 通知 / 消息 / 定时任务 / 回调 / 外部系统集成
- 缓存 / 幂等 / 并发控制 / 降级熔断
- 前端接口适配 / Mock / 测试支撑

| # | 实现点 | 来源（DR/PRD/主流程） | 业务能力归属 | 是否高风险 | 备注 |
|---|---|---|---|---|---|
| 1 |  |  |  | 是 / 否 |  |

### 1bis.2 现有能力复用扫描（所有实现点必填）

| 实现点 | 搜索范围 | 搜索关键词 / 类名 / 接口名 | 已发现的现有能力 | 结论（复用/扩展/新建） | 不复用理由 | 证据 |
|---|---|---|---|---|---|---|
|  | 项目资产 / 真实代码 / 依赖 Story / 历史 Task / 公共组件 |  |  |  |  | 文件路径:行号 / Story 章节 |

**扫描要求：**
- 真实代码可访问时，必须用代码搜索验证；不能只看项目资产。
- 历史 Story/Task 已实现过同类能力时，必须优先复用其契约或实现点。
- 若选择新建，必须说明现有能力为什么不能满足，不得只写“未找到”。

### 1bis.3 业内成熟方案参考（所有非平凡实现点必填）

| 实现点 | 业内成熟方案 / 常见模式 | 适用条件 | 本 Story 是否采用 | 取舍理由 | 参考证据 |
|---|---|---|---|---|---|
| 状态机 | 事件驱动状态机 / Spring StateMachine / 枚举转移表 / 领域对象 transition | 多状态、多触发事件、多非法流转 | 是 / 否 |  | 官方文档 / 团队既有实现 / 项目代码 |

**要求：**
- 不要求盲目引入框架，但必须知道成熟方案是什么。
- 状态机、幂等、重试补偿、分布式锁、消息消费、外部集成这类高风险能力，必须列至少 1 个成熟方案或团队既有成熟实现。

## 第二步：Story 章节生成（7 阶段并行挖掘）

### 阶段 A：业务背景与核心价值章节

**目的：** 让读者 5 秒内理解 Story 在做什么。

**输入：** DR 业务背景 + PRD 业务背景

**输出：** Story §"业务背景与核心价值" 章节

**必填字段：**
- **业务背景**（3-5 段）：业务问题 / 现状痛点 / 解决方案
- **目标用户**（1 段）：使用角色 + 典型场景
- **核心业务价值**（1-2 句）：对用户 / 业务的价值

**示例：**
> **业务背景：** 当前 Boss 后台管理用户列表依赖 DBA 手动执行 SQL，无法支持业务侧的实时查询需求。典型场景是客服人员需要在用户来电时快速定位用户状态。
> **目标用户：** Boss 后台管理员 + 客服人员
> **核心业务价值：** 提供实时分页查询接口 + 角色/状态过滤，提升客服响应效率 5 倍。

**🔴 必禁：** "系统应..." / "用户会..."（无业务事实依据）。

### 阶段 B：主流程 + 异常流程章节

**目的：** 描述业务步骤 + 异常处理路径。

**输入：** DR 主流程 + DR 异常场景 + PRD 用户旅程 + 产品原型交互流程

**输出：** Story §"主流程" + §"异常流程" 章节

**主流程必填：**
- 按用户操作步骤列（1/2/3/...）
- 每步骤：用户操作 → 触发接口 → 后端处理 → 数据变更 → 异常处理
- 用 Mermaid 或 ASCII 画流程图

**异常流程必填：**
- 按异常类型分组（业务异常 / 系统异常 / 数据异常 / 并发异常）
- 每异常：触发条件 → 检测点 → 处理动作 → 用户提示

**示例（主流程）：**
> 1. 管理员点击"用户列表"按钮 → 前端调用 `GET /boss-user-bff/api/v1/users?page=1&size=20`
> 2. BFF 接收请求 → 调 `BossUserManagementService.list(request)`（SPI）
> 3. Service 接收 → 调 `BossUserAppService.list(query)`（本地）
> 4. AppService 调 `BossUserRepository.findByQuery(query)`（仓储接口）
> 5. Repository 拼 MyBatis 动态 SQL → 查 DB → 返回 `PagedModels<BossUserDO>`
> 6. AppService 转 `PagedModels<BossUserDTO>` → 返回 BFF
> 7. BFF 转 `PagedModels<BossUserVO>` → 返回前端

**🔴 AC 格式（Given-When-Then）：**
- AC_ID: AC-001
- 描述：{一句话}

- **业务规则验收**：每条业务规则至少有一个 AC 或明确的不适用说明。

**示例：**
> | AC_ID | Given | When | Then |
