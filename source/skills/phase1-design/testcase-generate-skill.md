# TestCase Generate — 测试用例生成 SKILL

## 📦 文档存放前置调用（🔴 横切依赖）

> **🔴 强制：** 本 SKILL 生成的测试用例在写入磁盘前**必须先调用 [`document-storage-skill.md`](../cross-cutting/document-storage-skill.md)** 的 API，**不再手写路径**：
> 1. **路径**（§0.6.1 `resolve_path()`）：通过 `intent=TESTCASE` 自动定位到 `ae-sdd-doc/iterations/{YYYY-MM-DD}/Test/{STORY-ID}/`
> 2. **命名 + 版本号**（§0.6.7 `save_doc()`）：**设计类文档带 v{major}.{minor}**（重入时 v 递增，旧版本保留）
> 3. **重入判定**（§0.6.11 `get_latest_version()`）：TestCase 重入时**新增版本**（v 递增）
> 4. **ChangeLog**（§5）：`save_doc()` 自动追加
> 5. **.gitignore**（§0.6.13 `check_and_update_gitignore()`）：首次写入时自动维护

| 输出文档 | API 调用 | 命名规则 | 重入时动作 |
|---------|---------|---------|----------|
| 测试用例 | `save_doc(intent="TESTCASE", storyId, version={major,minor})` | v{major}.{minor} | 新增版本（v 递增）|
| TestCase-WriterReport | `save_doc(intent="TESTCASE_WRITER_REPORT", storyId, version={r:N})` | 带 r{N} | 新增（r 递增）|
| 测试报告 | `save_doc(intent="TEST_REPORT", storyId, version={v:N,r:M})` | 带 `v{N}-r{M}` | **新增**（r 递增）|
| 合规性校验报告 | `save_doc(intent="TESTCASE_COMPLIANCE_REPORT", storyId, version={r:N})` | 带 r{N} | 新增（r 递增）|

> **调用示例：** 详见 `document-storage-skill.md §15.5.2` 调用矩阵。

```
  - 刚好未到达

步骤 4：覆盖并发场景
  - 多实例同时触发（分布式锁）

步骤 5：覆盖异常场景
  - 处理中某条数据失败，不影响其他数据
```

#### 集成策略用例生成规则

```
步骤 1：覆盖全链路成功场景
  - 所有服务调用成功 → 完整流程完成

步骤 2：覆盖逐环节失败场景
  - 第 1 步失败 → 前序回滚
  - 第 2 步失败 → 前序回滚
  - ...
  - 第 N 步失败 → 前序回滚

步骤 3：覆盖事务回滚场景
  - 失败时前序操作是否正确回滚

步骤 4：覆盖超时场景
  - 某个服务调用超时

步骤 5：覆盖降级场景
  - 非核心服务失败时是否降级处理
```

### 3.2 第二层用例生成（通用维度）

#### 维度一：输入字段边界

| 字段名 | 字段类型 | 有效等价类 | 无效等价类 | 边界值 | 用例 ID |

| {field2} | Long | 正数 | null、0、负数 | 1、Long.MAX | TC-xxx |

**规则：**
- 每个字段至少 1 条有效值用例 + 1 条无效值用例

### 3.3 第三层：分配测试层级

对每个用例标注测试层级：

| 场景 | 测试层级 | 判定依据 |
|------|---------|---------|

| HTTP 参数校验注解 | L2 | 需要 Spring MVC 框架 |
| HTTP 状态码映射 | L2 | 需要异常处理器 |
| 唯一索引幂等 | L3 | 需要真实数据库 |
| 事务回滚 | L3 | 需要真实事务管理器 |
| 完整业务流程 | L4 | 需要多组件协作 |

### 3.4 用例去重

第一层和第二层可能有重叠（如回调策略的"字段校验"与通用维度的"输入字段边界"），去重后取并集。

**去重规则：**
- 相同场景描述的用例保留一条
- 包含关系：具体用例覆盖通用用例时，删除通用用例（保留更具体的那条。例如："email字段有效值"比"String字段有效值"更具体，保留前者）

## 第五步：输出测试用例文档

### 5.1 文件路径

通过 `documentStorage.resolve_path(intent="TESTCASE", storyId, docType="Testcase")` 自动定位（详见 `document-storage-skill.md §0.6.1`）：

```
ae-sdd-doc/iterations/{YYYY-MM-DD}/Test/{STORY-ID}/
└── {STORY-ID}-testcase-v{major}.{minor}.md
```

### 5.2 文档格式

**必须按 `templates/testcase/be-testcase-template.md` 模板格式输出，包含以下章节：**

1. **元信息** - 用例 ID、来源 Story、覆盖 AC、状态
2. **覆盖目标** - 测试目标和重点验证内容
3. **覆盖矩阵** - AC ID、用例 ID、场景、测试层级、自动化方式
4. **测试数据** - 数据构造方式、约束、清理方式
5. **用例列表** - 每个用例的完整定义（前置、Mock、步骤、断言）
6. **用例数量自检** - 第一层 + 第二层公式计算
7. **覆盖完整性自检清单** - 逐项打勾确认
8. **回归范围** - 必跑测试、可跳过项
9. **风险与未覆盖项** - 不可测试项的原因和替代方案
10. **测试真实性预埋** - 数据来源、真实链路、Mock 边界、执行证据要求

### 5.3 用例定义格式

每个用例必须包含：

```markdown
### TC-XXX {场景描述}

- 覆盖 AC：AC-XXX
- 测试层级：L1/L2/L3/L4
- 测试数据来源：Story §X / Task §Y / 接口契约示例
- 真实链路要求：真实 HTTP / 真实 DB / 单元测试 / 外部依赖 Mock
- 前置条件：
- Mock 配置：
  - `when(...).thenReturn(具体业务值)`（禁止 `thenReturn(any())` / 全 Mock 核心路径）
- 操作步骤：
  1. 
- 期望结果：
- 断言：
  - 
- 负向/失败注入：无 / 参数非法 / 状态非法 / DB 约束 / 外部依赖失败 / 事务回滚
- 自动化入口：`src/test/java/{package}/{TestClass}#{method}`
- 清理动作：无 / @Rollback
```
