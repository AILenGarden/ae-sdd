# Review Core — 严格验证式代码评审

> Review 以验证为主：先确定适用规范和覆盖范围，再用代码、需求、运行和测试证据判断实现是否满足规范。适用规范不能被主观取舍或“本次未触发”跳过。

## 1. 评审前置

按入口的必读范围加载上下文，确认项目身份、本次 diff、目标行为、需求/契约/AC、级联范围及可执行的验证环境。收齐适用 global、language、architecture、project SKILL 的条目、命名模板、阈值、证据要求和例外条件。

适用规范的每一条都进入检查清单并得到“满足 / 不满足 / 证据不足”结论。规范冲突记录来源、适用范围和裁决；未裁决前不输出整体通过。

## 2. 严格评审结论

每条意见必须包含：

```text
位置：文件:行号、类/方法或契约字段
触发：输入、状态、并发、权限或依赖条件
规范：规范 ID、条目、来源文件
影响：破坏的行为、不变量、质量目标或兼容语义
证据：代码、需求、运行记录、测试输出或适配 SKILL
结论：不满足 / 证据不足 / 满足
处理：修正方向或补充验证
```

整体结论只能是：

| 结论 | 必要条件 |
|---|---|
| 通过 | 前置事实已确认，§3 各检查面及所有适用规范、需求条目均已按 §4 检查；没有不满足或关键证据不足项；规范冲突已裁决；剩余风险已被规范允许或明确接受 |
| 不通过 | 存在确定缺陷、适用规范不满足、需求不满足或项目要求的关键证据缺失 |
| 无法判定 | 关键事实、环境、规范或证据缺失，尚不能证明满足；列出阻断范围 |

“未发现问题”只表示列出的检查范围内未发现确定缺陷，不能替代整体通过。没有证据的“已实现”“已验证”“符合规范”均无效。

严重度按影响、发生条件和恢复成本确定：

| 等级 | 适用判断 |
|---|---|
| 阻断 | 核心行为、权限、数据不变量或兼容性失效，或规范明确规定为阻断级 |
| 严重 | 高影响并发、性能、资源、依赖失败或安全缺陷 |
| 一般 | 局部规范、命名、维护性或重复问题，不改变核心行为 |
| 建议 | 不影响当前契约的表达和惯用法改进 |

严重度描述影响大小；是否通过按上表判定。一般级规范不满足也不能通过，证据不足单列验证限制。

## 3. 强制覆盖面

以下检查面是 Review 的固定基线；每项都要列出适用条目、检查结果和证据。适配 SKILL 可增加更严格条目。

### A. 需求与行为

- 逐项对照需求 AC、接口/事件契约、前置/后置条件、异常和边界场景。
- 核对主流程、状态转移、错误语义、权限、幂等、可见性和兼容行为。
- 反向检查代码新增行为是否有需求或契约依据。

### B. 现状与级联

- 核对直接差异、调用方、消费者、数据映射、索引、缓存、配置、观察点和恢复资产。
- 识别复用对象的语义、生命周期、失败和约束差异。
- 级联影响逐项标记受影响、无影响或证据不足。
- 对账方案、代码、测试、文档和产出物，确认相同契约及级联调整一致。

### C. 结构与规范

- 逐项执行适用的语言、架构、项目和全局规范，包括层级、职责、命名、包路径、依赖方向和禁用项。
- 规范只在有来源时作为判定依据；Core 通用原则不能替代适配规范的具体条款。

### D. 数据、状态与副作用

- 核对数据所有权、字段映射、唯一性、不变量、迁移兼容和保留要求。
- 核对事务范围、提交后动作、跨边界部分成功、补偿、对账和订正路径。
- 查询、索引、分页、批量、缓存和写放大按项目/语言规范与实际量级证据判断。

### E. 失败、并发、性能与资源

- 逐项覆盖 Coding Core 的 R01–R08：原子性、并发、幂等、同步异步、一致性、外部容错、性能和资源隔离。
- 每个等待、重试、队列、锁、连接和副作用有边界、失败结果和验证证据。
- 核心路径与低优负载同时存在时，检查预算、拒绝、优先级、积压和容量证据。

### F. 安全、运维与验证

- 逐项覆盖 R09–R11：输入、认证授权、敏感数据、密钥、审计、日志、指标、告警、开关、回退和订正。
- 测试断言来自需求、契约、规范或固定真实数据；覆盖与风险相称。
- 真实 DB、消息、HTTP 或外部协议要求真实证据时，Mock 结果不能替代。

## 4. 证据规则

| 检查结果 | 证据要求 |
|---|---|
| 满足 | 规范条目 + 检查动作 + 代码/文件/行号或可复核测试输出 |
| 不满足 | 规范条目 + 触发条件 + 实际差异 + 影响 |
| 证据不足 | 缺少的事实/环境/报告 + 无法证明的范围 + 补证动作 |

测试报告必须能回指命令、退出码、报告文件或运行记录。测试独立性、AC 覆盖、真实依赖覆盖和断言有效性分别说明。不能把自我声明、全量 Mock、永真断言或实际结果回填期望值当作证明。

结论记录必须覆盖：需求条目、适用规范条目、受影响代码范围、识别的异常/边界场景、验证项和剩余限制。报告形式随任务规模调整；可合并相同证据，但每条适用要求的结论必须可追踪。结论范围小于变更范围时明确说明。

## 5. 根因与整改

发现偏差后沿以下顺序定位最早失真的层级：

```text
事实/环境 → 需求/契约 → 规范/设计 → 实现 → 验证
```

规范、需求或设计不满足时，意见指向对应上游并列出代码和测试级联；实现修复后重新检查受影响条目及证据，按 §2 更新整体结论。修正一处不能自动证明其他引用、调用方、数据和验证已同步。
