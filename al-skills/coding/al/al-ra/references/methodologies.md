## 1. Impact Mapping（影响地图）

**创始人**：Gojko Adzic  
**核心理念**：目标驱动，避免"伪需求"，确保每个功能都能追溯到业务目标。

### 核心结构

```
Why（目标）→ Who（角色）→ How（影响）→ What（交付物）
```

### 四层提问

| 层级 | 问题 | 示例 |
|------|------|------|
| **Why** | 我们为什么做这个？业务目标是什么？ | 提升用户留存率 10% |
| **Who** | 谁会受到影响？关键角色是谁？ | 新用户、老用户、运营人员 |
| **How** | 角色的行为如何影响目标？ | 新用户：简化注册流程 → 提升转化<br>老用户：提供快捷登录 → 提升活跃 |
| **What** | 我们需要交付什么功能来产生影响？ | F001: 手机号快捷登录<br>F002: Token 自动续期 |

### 应用示例

```
Why: 提升销售额 20%
├─ Who: 新客户
│   ├─ How: 降低首单门槛
│   │   └─ What: 新用户首单 8 折优惠
│   └─ How: 增强信任感
│       └─ What: 显示用户评价和销量
├─ Who: 老客户
│   └─ How: 提升复购率
│       └─ What: 会员积分体系
└─ Who: 运营人员
    └─ How: 精准营销
        └─ What: 用户画像分析工具
```

### 价值

- ✅ **防止伪需求**：无法追溯到 Why 的功能 = 伪需求
- ✅ **优先级决策**：直接影响目标的功能优先级更高
- ✅ **范围控制**：通过 Who 和 How 过滤无关需求

## 2. JTBD（Job to Be Done）

**创始人**：Clayton Christensen（《创新者的窘境》作者）  
**核心理念**：用户"雇佣"产品来完成任务，关注任务而非产品特性。

### 核心框架

**用户雇佣产品完成三类任务**：

| 任务类型 | 定义 | 示例 |
|----------|------|------|
| **功能性任务**<br>Functional Job | 完成具体操作 | 用户雇佣外卖App"在30分钟内吃上午饭" |
| **情感性任务**<br>Emotional Job | 获得某种感受 | 用户雇佣星巴克"感受中产生活方式" |
| **社交性任务**<br>Social Job | 他人如何看待 | 用户雇佣iPhone"展示科技品味" |

### JTBD 问题模板

```
用户雇佣[产品/功能]来完成什么任务？

深挖三问：
1. 当前用什么方案解决这个任务？（现状）
2. 当前方案有什么不足？（痛点）
3. 期望的进步（Progress）是什么？（目标）
```

### 应用示例

**错误视角（产品特性）**：
> "用户需要一个视频播放功能"

**正确视角（JTBD）**：
> "用户雇佣我们的App来'在通勤路上打发无聊时间'（功能性任务）  
> 当前方案：刷抖音，但流量消耗大（痛点）  
> 期望进步：离线缓存 + 智能推荐 + 省流量模式（解决方案）"

### 价值

- ✅ **聚焦本质**：不被产品特性束缚，关注用户真正的任务
- ✅ **发现竞品**：真正的竞品是"完成同一任务的替代方案"（星巴克的竞品不是瑞幸，而是"工位边喝速溶咖啡"）
- ✅ **创新方向**：理解任务后，可以用全新方式满足（如Netflix从DVD租赁 → 流媒体）

## 3. Kano Model（卡诺模型）

**创始人**：狩野纪昭（Noriaki Kano，东京理科大学教授）  
**核心理念**：需求对用户满意度的影响不同，指导优先级决策。

### 五类需求

| 需求类型 | 英文 | 定义 | 满意度曲线 | 优先级 |
|----------|------|------|------------|--------|
| **基本型需求**<br>Must-be | Basic | 必须有，否则用户拒绝使用 | 有：不满意 → 中性<br>无：极度不满 | 🔴 P0 |
| **期望型需求**<br>Performance | Expected | 做得越好，满意度越高 | 线性关系 | 🟠 P1 |
| **兴奋型需求**<br>Attractive | Delighters | 超预期惊喜，有则大喜 | 有：高满意<br>无：无所谓 | 🟡 P2 |
| **无差异需求**<br>Indifferent | Neutral | 有无皆可，用户不在意 | 平线 | ⚪ P3 |
| **反向需求**<br>Reverse | Dissatisfier | 做了反而降低满意度 | 负相关 | 🚫 删除 |

### Kano 问卷法

对每个功能提问：

**正向问题**："如果有这个功能，你会怎么想？"
- A. 我很喜欢
- B. 理应如此
- C. 无所谓
- D. 勉强接受
- E. 我不喜欢

**反向问题**："如果没有这个功能，你会怎么想？"
- A. 我很喜欢
- B. 理应如此
- C. 无所谓
- D. 勉强接受
- E. 我不喜欢

**判定矩阵**：

|  | 反向：喜欢 | 反向：理应 | 反向：无所谓 | 反向：勉强 | 反向：不喜欢 |
|--|-----------|-----------|------------|----------|-----------|
| **正向：喜欢** | 可疑 | 兴奋型 | 兴奋型 | 兴奋型 | 期望型 |
| **正向：理应** | 反向型 | 无差异 | 无差异 | 无差异 | 基本型 |
| **正向：无所谓** | 反向型 | 无差异 | 无差异 | 无差异 | 基本型 |
| **正向：勉强** | 反向型 | 无差异 | 无差异 | 无差异 | 基本型 |
| **正向：不喜欢** | 反向型 | 反向型 | 反向型 | 反向型 | 可疑 |

### 应用示例（电商App）

| 功能 | Kano分类 | 理由 | 优先级 |
|------|----------|------|--------|
| 商品搜索 | 基本型 | 没有搜索，用户无法使用 | 🔴 P0 |
| 商品详情页 | 基本型 | 必须有详情才能决策 | 🔴 P0 |
| 快速配送（次日达） | 期望型 | 越快越好，但不是必需 | 🟠 P1 |
| 界面美观 | 期望型 | 越美观越好 | 🟠 P1 |
| AR试穿功能 | 兴奋型 | 超预期惊喜 | 🟡 P2 |
| 商品3D展示 | 兴奋型 | 有则惊喜，无则无感 | 🟡 P2 |
| 过度复杂的筛选条件 | 反向型 | 用户觉得麻烦 | 🚫 删除 |

### 价值

- ✅ **优先级决策**：P0（基本型）→ P1（期望型）→ P2（兴奋型）
- ✅ **资源分配**：资源有限时，砍掉兴奋型，保留基本型
- ✅ **竞争策略**：基本型 = 入场券，兴奋型 = 差异化

### 注意事项

- ⚠️ **动态变化**：兴奋型会变成期望型（如iPhone的触摸屏，现在是基本型）
- ⚠️ **用户分层**：不同用户群体的Kano分类可能不同

## 4. Event Storming（事件风暴）

**创始人**：Alberto Brandolini  
**核心理念**：协作式需求探索，通过识别领域事件快速建立共识。

### 核心概念

| 元素 | 颜色 | 定义 | 示例 |
|------|------|------|------|
| **领域事件**<br>Domain Event | 🟠 橙色 | 领域中发生的事实（过去式） | 订单已创建、支付已完成 |
| **命令**<br>Command | 🔵 蓝色 | 触发事件的动作（祈使句） | 提交订单、发起支付 |
| **聚合**<br>Aggregate | 🟡 黄色 | 保证一致性的边界 | 订单、用户、支付 |
| **策略**<br>Policy | 🟣 紫色 | 业务规则（当...时...） | 当订单超时未支付时，自动取消 |
| **外部系统**<br>External System | 🟥 粉色 | 第三方依赖 | 支付网关、短信服务 |
| **用户/角色**<br>Actor | 👤 黄色便签 | 触发命令的人 | 买家、卖家、管理员 |

### Event Storming 流程

**阶段1：风暴（Storming）**
1. 团队围在白板/墙前
2. 每人写橙色便签（领域事件），贴在墙上
3. 不讨论，快速写，头脑风暴
4. 按时间顺序排列事件

**阶段2：时间线（Timeline）**
1. 识别命令（蓝色）：什么动作触发了事件？
2. 识别策略（紫色）：什么规则触发了自动事件？
3. 识别聚合（黄色）：谁来处理命令并产生事件？
4. 识别外部系统（粉色）：哪些事件涉及外部依赖？

**阶段3：限界上下文（Bounded Contexts）**
1. 将相关事件聚类
2. 画出限界上下文边界
3. 定义上下文间的关系

### 应用示例（电商订单）

```
👤买家 → 🔵提交订单 → 🟡订单聚合 → 🟠订单已创建
       → 🟠库存已锁定（策略：订单创建时自动锁库存）
       → 🔵发起支付 → 🟥支付网关 → 🟠支付已完成
       → 🟠库存已扣减（策略：支付完成时扣减库存）
       → 🟠订单已完成

🟣策略：当订单创建30分钟未支付时 → 🟠订单已取消 + 🟠库存已释放
```

### 价值

- ✅ **团队共识**：所有人（产品/开发/测试/业务）参与，快速对齐
- ✅ **发现盲点**：可视化业务流程，发现遗漏的场景
- ✅ **识别边界**：自然形成限界上下文，指导微服务拆分

## 5. 5W2H 分析法

**起源**：管理学经典方法  
**核心理念**：系统化提问，确保需求完整性。

### 七问模板

| 维度 | 英文 | 问题 | 目的 |
|------|------|------|------|
| **What** | 什么 | 做什么？核心功能是什么？ | 明确范围 |
| **Why** | 为什么 | 为什么做？业务目标？解决什么痛点？ | 追溯价值 |
| **Who** | 谁 | 谁使用？谁负责？谁受益？ | 识别角色 |
| **When** | 何时 | 何时触发？执行频率？有无时效？ | 时间维度 |
| **Where** | 何地 | 在哪使用（Web/App/API）？跨系统？ | 环境上下文 |
| **How** | 如何 | 如何实现？技术方案？集成方式？ | 实现路径 |
| **How much** | 多少 | 数据量级？并发量？成本？SLA要求？ | 量化指标 |

### 应用示例（用户登录功能）

```
What   → 用户使用手机号+验证码登录系统
Why    → 降低注册门槛，提升新用户转化率 15%
Who    → 目标用户：新用户（无密码）、老用户（忘记密码）
When   → 触发时机：用户打开App → 点击登录 → 输入手机号获取验证码
       → 时效要求：验证码5分钟内有效
Where  → 使用场景：移动端App（iOS/Android）、Web端（PC/H5）
How    → 技术方案：后端生成6位随机验证码 → 存储Redis（TTL 5分钟）
       → 调用阿里云短信网关发送 → JWT Token认证
How much → 数据量级：日均登录10万次
       → 并发量：高峰期QPS 1000
       → 成本：短信0.05元/条，日成本约5000元
       → SLA：接口响应时间P95 < 200ms
```

### 价值

- ✅ **结构化思维**：不遗漏关键维度
- ✅ **澄清模糊需求**：用户说"我要一个报表"，5W2H追问后才知道真实需求
- ✅ **跨角色沟通**：产品/开发/测试用统一框架讨论

## 6. STRIDE 威胁建模

**创始人**：Microsoft Security Team  
**核心理念**：系统化识别安全威胁，指导安全需求设计。

### STRIDE 模型

| 威胁类型 | 英文 | 定义 | 示例 | 防护措施 |
|----------|------|------|------|----------|
| **S**poofing | 身份伪造 | 攻击者伪造合法身份 | 伪造Token登录 | 强认证（JWT签名）、MFA |
| **T**ampering | 篡改 | 恶意修改数据/代码 | 中间人篡改请求参数 | HTTPS、数据签名 |
| **R**epudiation | 抵赖 | 否认操作行为 | 用户否认删除了数据 | 审计日志（不可篡改） |
| **I**nformation Disclosure | 信息泄露 | 敏感数据暴露 | 日志打印密码 | 加密、脱敏、权限控制 |
| **D**enial of Service | 拒绝服务 | 恶意请求打垮系统 | DDoS攻击 | 限流、熔断、WAF |
| **E**levation of Privilege | 权限提升 | 普通用户获得管理员权限 | 越权访问他人订单 | RBAC、接口权限校验 |

### STRIDE 应用流程

**Step 1：绘制数据流图（DFD - Data Flow Diagram）**
```
[用户] --登录请求--> [Web服务器] --验证--> [认证服务] --查询--> [数据库]
```

**Step 2：对每个元素应用STRIDE**

| 元素 | 威胁类型 | 具体威胁 | 缓解措施 |
|------|----------|----------|----------|
| 用户 → Web服务器 | T（篡改） | 中间人篡改请求 | HTTPS强制 |
| Web服务器 | D（拒绝服务） | DDoS攻击 | CDN + 限流 |
| 认证服务 | S（伪造） | 伪造Token | JWT签名验证 + 黑名单 |
| 数据库 | I（泄露） | 密码明文存储 | BCrypt加密 |
| 日志 | R（抵赖） | 篡改审计日志 | 日志只读权限 + 区块链存证 |
| 接口 | E（提权） | 越权访问 | RBAC + 数据权限过滤 |

### 应用示例（登录接口）

```
接口：POST /api/v1/auth/login

STRIDE分析：
✅ S（Spoofing）：
   威胁：攻击者伪造Token
   缓解：JWT HS256签名 + Token黑名单

✅ T（Tampering）：
   威胁：请求参数被中间人篡改
   缓解：HTTPS（TLS 1.3） + 请求签名

✅ R（Repudiation）：
   威胁：用户否认登录行为
   缓解：记录登录日志（userId/IP/时间/设备）

✅ I（Information Disclosure）：
   威胁：日志打印密码、Token泄露
   缓解：日志脱敏（只记录Token前8位）

✅ D（Denial of Service）：
   威胁：暴力破解、接口刷量
   缓解：限流（同一IP每秒10次）+ 验证码（错误5次触发）

✅ E（Elevation of Privilege）：
   威胁：普通用户尝试以管理员身份登录
   缓解：后端校验用户角色，禁止前端传role参数
```

### 价值

- ✅ **系统化**：不遗漏安全维度（STRIDE六个维度）
- ✅ **前置安全**：需求阶段就考虑安全，而非上线后打补丁
- ✅ **可追溯**：每个威胁有对应缓解措施

## 方法论组合使用

实际项目中，多种方法论配合使用效果最佳：

| 阶段 | 使用方法论 | 目的 |
|------|-----------|------|
| **需求引导** | 5W2H + JTBD | 澄清模糊需求，理解用户任务 |
| **目标分解** | Impact Mapping | 确保需求追溯到业务目标 |
| **优先级排序** | Kano Model | 分类需求，决定优先级 |
| **业务建模** | Event Storming | 识别领域事件，划分限界上下文 |
| **安全需求** | STRIDE | 识别安全威胁，设计防护措施 |

---

## 总结

- **Impact Mapping**：目标驱动，防止伪需求
- **JTBD**：关注用户任务，而非产品特性
- **Kano Model**：需求分类，指导优先级
- **Event Storming**：协作建模，快速共识
- **5W2H**：结构化提问，确保完整性
- **STRIDE**：安全威胁建模，前置安全

这些方法论不是教条，而是工具箱，根据项目复杂度灵活选用。
