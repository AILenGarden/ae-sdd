# IEEE 830 需求质量验证清单

## IEEE 830 标准概述

IEEE 830-1998 是软件需求规格说明（SRS - Software Requirements Specification）的推荐实践标准，定义了8个核心质量属性。

---

## 质量属性详解

### 1. 完整性（Completeness）

**定义**：SRS包含所有必要的需求信息，无遗漏。

**验证检查清单**：

#### 功能完整性
- [ ] **PRD覆盖**：所有PRD提及的功能点已转化为需求（逐条对比）
- [ ] **原型覆盖**：所有原型图的交互/页面已转化为需求
- [ ] **口述覆盖**：所有口述需求已结构化记录
- [ ] **CRUD完整**：涉及数据的功能，增删改查都考虑到
- [ ] **角色完整**：所有用户角色的诉求都覆盖
- [ ] **流程完整**：业务流程从开始到结束无断点

#### 场景完整性
- [ ] **正常场景**：主流程（Happy Path）已描述
- [ ] **异常场景**：错误处理覆盖 ≥ 80%（参数错误/权限不足/依赖失败）
- [ ] **边界场景**：边界值（0/空/极大值）已测试
- [ ] **组合场景**：多条件交叉情况已考虑

#### 非功能需求完整性
- [ ] **性能需求**：响应时间/吞吐量/并发量已定义
- [ ] **安全需求**：认证/授权/加密/审计已定义
- [ ] **可用性需求**：SLA/容灾/降级已定义
- [ ] **可维护性需求**：日志/监控/扩展性已定义
- [ ] **兼容性需求**：浏览器/设备/API版本已定义
- [ ] **合规性需求**：隐私/等保/行业规范已定义

#### 接口完整性
- [ ] **输入定义**：所有输入参数（类型/长度/约束/示例）已定义
- [ ] **输出定义**：所有输出字段（类型/格式/错误码）已定义
- [ ] **依赖定义**：所有外部依赖（服务/接口/SLA）已识别

#### 数据完整性
- [ ] **实体识别**：所有核心实体已建模
- [ ] **关系定义**：实体间关系已明确
- [ ] **字段定义**：所有字段（类型/约束/默认值）已定义
- [ ] **索引定义**：查询场景对应的索引已设计

**完整性测试方法**：
1. **正向检查**：从PRD到需求，逐条核对
2. **反向检查**：从需求到PRD，确认每条需求有来源
3. **场景推演**：模拟用户操作，检查是否有遗漏路径
4. **评审会议**：多角色参与，群体智慧发现遗漏

---

### 2. 正确性（Correctness）

**定义**：每条需求准确反映用户意图和业务目标。

**验证检查清单**：

#### 业务正确性
- [ ] **业务目标一致**：每条需求可追溯到业务目标（Impact Mapping）
- [ ] **业务规则准确**：业务规则与实际业务流程一致
- [ ] **术语准确**：业务术语与业务方定义一致（统一语言）
- [ ] **计算逻辑正确**：金额计算/积分计算等逻辑正确

#### 技术正确性
- [ ] **技术方案可行**：无技术上不可实现的需求
- [ ] **数据模型合理**：实体关系符合范式要求
- [ ] **接口定义正确**：RESTful规范/参数类型正确
- [ ] **性能指标合理**：性能要求在技术能力范围内

#### 用户意图一致性
- [ ] **用户访谈确认**：关键需求已与用户确认
- [ ] **产品确认**：所有需求已与产品经理确认
- [ ] **优先级准确**：优先级反映真实的业务紧迫性

**正确性验证方法**：
1. **用户故事回顾**：与产品/用户一起过一遍故事
2. **原型演示**：用原型模拟，确认理解一致
3. **用例演练**：角色扮演，模拟操作流程
4. **专家评审**：领域专家审查业务规则

---

### 3. 无歧义性（Unambiguous）

**定义**：每条需求只有唯一解释，不同读者理解一致。

**验证检查清单**：

#### 避免模糊词汇
- [ ] **禁用词汇**：无"尽快"/"合理"/"适当"/"某些"/"通常"/"可能"
- [ ] **量化指标**：用"<200ms"代替"快速"，用"≥99.9%"代替"高可用"
- [ ] **明确主体**：用"系统"/"用户"/"管理员"，不用"它"/"这个"
- [ ] **明确动作**：用"创建"/"删除"/"修改"，不用"处理"/"操作"

#### 清晰的条件表达
- [ ] **逻辑清晰**：用"当X且Y时"代替"在某些情况下"
- [ ] **枚举完整**：状态枚举完整（待支付/已支付/已取消/已退款），无"等"字
- [ ] **边界明确**：用"0 < X ≤ 100"代替"X在合理范围内"

#### 一致的术语
- [ ] **术语统一**：同一概念全文统一命名（如"用户ID"不混用"用户编号"/"UserID"）
- [ ] **缩写定义**：首次使用缩写时给出全称（如"QPS（每秒查询率）"）
- [ ] **术语表**：建立统一语言词汇表

#### 明确的格式
- [ ] **时间格式**：统一使用ISO 8601（2026-09-09T10:30:00Z）
- [ ] **金额格式**：明确币种和精度（如"CNY 99.99，保留2位小数"）
- [ ] **数据类型**：明确类型（如"bigint"而非"数字"）

**歧义检测方法**：
1. **多人理解测试**：让3个人独立理解同一条需求，对比结果
2. **反向陈述测试**：让读者用自己的话复述需求
3. **极端情况测试**：问"如果X是极端值，应该怎样？"
4. **代码预演**：开发人员尝试写伪代码，看是否有疑问

**模糊词汇对照表**：

| 模糊表达 | 明确表达 |
|----------|----------|
| 快速响应 | P95 < 200ms |
| 高并发 | 支持1000 QPS |
| 尽快处理 | 5秒内处理完成 |
| 合理的重试次数 | 最多重试3次 |
| 某些情况下 | 当用户状态=禁用时 |
| 适当的超时时间 | HTTP超时时间3秒 |
| 通常情况下 | 正常流程中（定义"正常"） |

---

### 4. 一致性（Consistency）

**定义**：需求之间无矛盾，逻辑自洽。

**验证检查清单**：

#### 命名一致性
- [ ] **术语一致**：同一概念全文统一（如"订单"不混用"工单"）
- [ ] **字段命名一致**：数据库字段/接口参数/UI标签命名一致
- [ ] **错误码一致**：同一类错误使用相同错误码

#### 逻辑一致性
- [ ] **无循环依赖**：需求A依赖B，B不能依赖A
- [ ] **状态机一致**：状态转换规则无冲突（如"已完成"不能转为"待支付"）
- [ ] **优先级一致**：P0需求不能依赖P2需求

#### 数据一致性
- [ ] **数据流一致**：上游输出=下游输入（字段类型/格式一致）
- [ ] **计算一致**：同一计算逻辑在不同场景结果一致
- [ ] **单位一致**：时间统一用秒/毫秒，金额统一用元/分

#### 规则一致性
- [ ] **业务规则不矛盾**：如"验证码5分钟过期"和"验证码10分钟过期"矛盾
- [ ] **权限规则一致**：同一角色在不同模块的权限逻辑一致

**一致性检测方法**：
1. **交叉引用检查**：用工具搜索同一术语，检查定义是否一致
2. **状态机图绘制**：画出状态转换图，检查有无死锁/冲突
3. **依赖关系图**：画出需求依赖图，检查有无循环依赖
4. **规则矩阵**：列出所有业务规则，检查有无矛盾

**常见不一致示例**：

| 不一致类型 | 示例 |
|------------|------|
| 命名不一致 | 需求1叫"用户ID"，需求2叫"用户编号" |
| 数据类型不一致 | 需求1说userId是String，需求2说是Long |
| 规则矛盾 | 需求1说"最多重试3次"，需求2说"最多重试5次" |
| 优先级矛盾 | P0需求依赖P2需求完成 |
| 状态矛盾 | "已取消"订单可以"发货" |

---

### 5. 可验证性（Verifiable）

**定义**：每条需求可通过测试、检查、分析等方法验证是否满足。

**验证检查清单**：

#### 验收标准明确
- [ ] **每个功能需求有AC**：验收条件（Acceptance Criteria）明确
- [ ] **AC可测试**：可编写测试用例验证
- [ ] **AC可观察**：结果可观察（UI变化/日志记录/数据变化）

#### 非功能需求可量化
- [ ] **性能可度量**：有具体数值（如"P95 < 200ms"）
- [ ] **可用性可度量**：有SLA指标（如"99.9%"）
- [ ] **安全可验证**：可通过安全扫描/渗透测试验证

#### 主观需求客观化
- [ ] **"易用性"量化**：用"用户3次点击完成操作"代替"易于使用"
- [ ] **"美观"量化**：用"符合设计规范XYZ"代替"界面美观"
- [ ] **"稳定性"量化**：用"24小时无崩溃"代替"系统稳定"

**可验证性测试方法**：
1. **测试用例预演**：尝试为需求编写测试用例，卡住则说明不可验证
2. **验收模拟**：模拟验收场景，问"如何判断此需求已完成？"
3. **指标可采集**：确认监控系统能采集到验证指标

**不可验证需求示例**：

| 不可验证需求 | 可验证需求 |
|--------------|------------|
| 系统应该快速响应 | 接口响应时间P95 < 200ms |
| 界面应该美观 | 界面符合Material Design 3规范 |
| 系统应该易用 | 新用户无需培训可完成注册流程 |
| 系统应该稳定 | 7×24小时运行，可用性≥99.9% |

---

### 6. 可追溯性（Traceable）

**定义**：每条需求可以追溯到业务目标，并可追踪到设计/代码/测试。

**验证检查清单**：

#### 向后追溯（Backward Traceability）
- [ ] **追溯到业务目标**：每条需求关联到Why（Impact Mapping）
- [ ] **追溯到来源**：标注来源（PRD章节号/原型图页码/访谈记录）
- [ ] **追溯到利益相关者**：明确此需求是哪个角色提出的

#### 向前追踪（Forward Traceability）
- [ ] **关联到设计**：需求ID关联到设计文档章节
- [ ] **关联到代码**：需求ID关联到代码模块/类/方法
- [ ] **关联到测试**：需求ID关联到测试用例编号

#### 追溯矩阵
- [ ] **需求追溯矩阵100%覆盖**：每条需求都在矩阵中
- [ ] **矩阵无孤儿需求**：无法追溯到业务目标的需求（可能是伪需求）
- [ ] **矩阵无孤儿目标**：每个业务目标至少对应1条需求

**追溯矩阵示例**：

| 需求ID | 来源 | 业务目标 | 用户故事 | 用例 | 设计 | 代码 | 测试 |
|--------|------|----------|----------|------|------|------|------|
| F001 | PRD-3.1 | 提升留存10% | US001 | UC001 | DD-001 | UserService.login() | TC001-TC010 |

**追溯性价值**：
1. **变更影响分析**：业务目标变更，快速定位受影响需求
2. **需求覆盖分析**：检查每个业务目标是否都有需求支撑
3. **测试覆盖分析**：检查每个需求是否都有测试用例
4. **代码清理**：无需求关联的代码可能是冗余代码

---

### 7. 可修改性（Modifiable）

**定义**：SRS结构清晰，易于修改且修改不会引入不一致。

**验证检查清单**：

#### 结构化组织
- [ ] **模块化**：需求按功能模块组织，非平铺直叙
- [ ] **单一职责**：每章节只讲一个主题
- [ ] **交叉引用**：相关需求通过引用关联，非重复书写
- [ ] **目录清晰**：有完整目录，支持快速定位

#### 避免冗余
- [ ] **无重复定义**：同一概念只在一处定义，其他地方引用
- [ ] **无复制粘贴**：通用规则（如数据字典）集中定义，需求引用
- [ ] **模板化**：相似需求使用模板，降低维护成本

#### 版本控制
- [ ] **版本号**：SRS有版本号（如v1.0, v1.1）
- [ ] **变更历史**：有变更日志记录（日期/变更人/变更内容）
- [ ] **变更影响分析**：修改需求时，分析影响范围

#### 可扩展性
- [ ] **预留扩展点**：如接口版本控制（/api/v1/, /api/v2/）
- [ ] **可插拔设计**：如支付方式可扩展（支付宝/微信/银联）

**可修改性测试方法**：
1. **修改演练**：模拟一个需求变更，看是否容易修改
2. **一致性检查**：修改后，自动检查有无不一致
3. **影响分析**：使用追溯矩阵快速定位受影响模块

---

### 8. 优先级明确（Ranked for Importance）

**定义**：需求有明确优先级，指导开发顺序和资源分配。

**验证检查清单**：

#### 优先级分类
- [ ] **Kano模型分类**：基本型/期望型/兴奋型/无差异型/反向型
- [ ] **MoSCoW标注**：Must/Should/Could/Won't
- [ ] **P0/P1/P2标注**：紧急程度

#### 优先级合理性
- [ ] **MVP明确**：P0需求构成最小可行产品（MVP）
- [ ] **依赖优先**：被依赖的需求优先级更高
- [ ] **价值优先**：高价值需求优先级更高
- [ ] **风险优先**：高风险需求尽早验证

#### 优先级一致性
- [ ] **无矛盾**：P0需求不依赖P2需求
- [ ] **有取舍**：资源不足时，明确哪些需求可延后/删除（Won't）

**优先级矩阵（价值vs成本）**：

```
高价值 | P1: 快速迭代  | P0: 立即做
     | (低成本高价值) | (高成本高价值)
     |________________|________________
     | P3: 延后或不做 | P2: 分阶段做
低价值 | (低成本低价值) | (高成本低价值)
       低成本           高成本
```

## IEEE 830 质量评分卡

| 质量属性 | 权重 | 评分(1-5) | 加权分 | 备注 |
|----------|------|-----------|--------|------|
| 完整性 | 20% | | | 功能/场景/非功能需求完整 |
| 正确性 | 20% | | | 准确反映业务意图 |
| 无歧义性 | 15% | | | 无模糊词汇，可量化 |
| 一致性 | 10% | | | 术语/逻辑/数据一致 |
| 可验证性 | 15% | | | 有验收标准，可测试 |
| 可追溯性 | 10% | | | 追溯矩阵100%覆盖 |
| 可修改性 | 5% | | | 结构清晰，易维护 |
| 优先级明确 | 5% | | | 有Kano/MoSCoW标注 |
| **总分** | 100% | | | |

**评分标准**：
- 5分：完全满足，无缺陷
- 4分：基本满足，有少量改进空间
- 3分：部分满足，有明显问题
- 2分：较少满足，问题较多
- 1分：几乎不满足，需要重写

**通过标准**：
- 总分 ≥ 4.0：优秀，可进入下一阶段
- 总分 3.0-3.9：合格，需小幅改进
- 总分 < 3.0：不合格，需要重大返工

## 快速检查清单（Checklist）

打印此清单，逐项检查需求文档：

### 完整性
- [ ] PRD所有功能点已覆盖
- [ ] 正常+异常+边界场景 ≥90%
- [ ] 非功能需求6维度齐全

### 正确性
- [ ] 每条需求可追溯到业务目标
- [ ] 关键需求已与产品/用户确认
- [ ] 业务规则准确无误

### 无歧义性
- [ ] 无"尽快/合理/适当"等模糊词
- [ ] 非功能需求已量化（具体数值）
- [ ] 术语统一，有术语表

### 一致性
- [ ] 同一概念命名统一
- [ ] 无循环依赖
- [ ] 优先级无矛盾

### 可验证性
- [ ] 每个功能需求有验收标准（AC）
- [ ] 非功能需求可度量

### 可追溯性

### 可修改性
- [ ] 文档结构清晰，有目录
- [ ] 无重复定义
- [ ] 有版本号和变更历史

## 总结

IEEE 830 八维质量模型是需求工程的基石：

1. **完整性**：不遗漏
2. **正确性**：不出错
3. **无歧义**：不模糊
4. **一致性**：不矛盾
5. **可验证**：可测试
6. **可追溯**：可溯源
7. **可修改**：易维护
8. **有优先级**：分轻重

**记住**：需求质量直接决定项目成败，投入在需求阶段的时间，会在后续阶段10倍节省回来。
