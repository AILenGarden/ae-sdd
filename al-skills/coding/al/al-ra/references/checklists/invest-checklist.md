# INVEST 用户故事质量检查清单

## INVEST 原则详解

### I - Independent（独立）

**定义**：用户故事应该相互独立，可以以任意顺序开发和交付。

**检查项**：
- [ ] 此故事不依赖其他未完成的故事
- [ ] 此故事的价值可以独立体现
- [ ] 如果有技术依赖，已通过架构解耦（如接口定义先行）
- [ ] 可以单独演示和验收

**违反示例**：
- ❌ 故事A："实现用户登录UI"，故事B："实现用户登录后端接口"（强依赖）
- ✅ 故事A："实现用户登录功能（前后端）"（独立完整）

**例外情况**：
- 技术故事（如数据库迁移）可能是其他故事的前置依赖，应尽早完成

---

### N - Negotiable（可协商）

**定义**：用户故事的实现细节可以与团队协商，不是固定的合同。

**检查项**：
- [ ] 故事描述聚焦"做什么"（What），而非"怎么做"（How）
- [ ] 实现方式有多种选择（技术方案可讨论）
- [ ] UI细节/交互方式可以优化调整
- [ ] 与产品/用户保持沟通，可根据反馈调整

**违反示例**：
- ❌ "使用Redis缓存用户信息，TTL设置为30分钟"（实现细节固化）
- ✅ "提升用户信息查询性能，响应时间<100ms"（留协商空间）

**协商范围**：
- 技术实现方式（缓存/数据库优化/算法选择）
- 交互细节（按钮位置/提示文案）
- 非核心功能（可选特性）

**不可协商**：
- 核心业务价值
- 合规要求
- 已承诺的SLA

---

### V - Valuable（有价值）

**定义**：用户故事必须对用户或业务有明确价值。

**检查项**：
- [ ] 能回答"为什么做这个"（So that子句清晰）
- [ ] 价值可以量化或明确描述（提升X指标/解决Y痛点）
- [ ] 用户愿意为此功能付费/使用
- [ ] 可追溯到业务目标（Impact Mapping）

**价值类型**：
- **直接价值**：用户可感知的功能改进
- **间接价值**：降低成本/提升效率/减少风险
- **战略价值**：长期竞争力/市场卡位

**验证方法**：
- 问产品："如果不做这个，会怎样？"
- 问用户："这个功能对你有什么帮助？"
- 量化价值："预计提升X%转化率"

**违反示例**：
- ❌ "重构UserService代码"（技术债务，用户无感知）
- ✅ "重构UserService，降低接口RT从500ms到200ms"（性能提升，用户有感）

---

### E - Estimable（可估算）

**定义**：团队能够估算此故事的工作量。

**检查项**：
- [ ] 需求足够清晰，团队理解要做什么
- [ ] 技术方案可行，无重大未知风险
- [ ] 有类似经验可参考
- [ ] 可以给出Story Points或工作日估算

**不可估算的原因**：
1. **需求不清晰**：边界模糊/验收标准不明
2. **技术不确定**：新技术栈/复杂算法/性能未知
3. **依赖不明确**：第三方服务能力未确认
4. **故事太大**：需要拆分

**解决方法**：
- 需求不清 → 补充细节/与产品澄清
- 技术不确定 → Spike（技术预研故事，time-boxed）
- 依赖不明 → 提前调研/联系第三方
- 故事太大 → 拆分为多个小故事

**估算技巧**：
- Planning Poker（团队共识）
- 参考历史故事（相似度对比）
- T-shirt sizing（S/M/L/XL）

---

### S - Small（小）

**定义**：用户故事应该足够小，能在1-2个Sprint内完成（通常3-5天）。

**检查项**：
- [ ] 估算 ≤ 13 Story Points（斐波那契数列）
- [ ] 可以在1个Sprint（2周）内完成
- [ ] 开发人员能在短时间内完成并演示
- [ ] 不需要跨多个Sprint才能看到价值

**过大的信号**：
- 估算 > 13 SP
- 涉及多个模块/子系统
- 需要多个角色协同（前端+后端+DBA+运维）
- 无法在2周内完成并测试

**拆分策略**：
| 拆分维度 | 示例 |
|----------|------|
| **按工作流步骤** | "用户注册" → "填写信息" + "验证手机号" + "创建账号" |
| **按业务规则** | "订单计算" → "基础价格计算" + "优惠券折扣" + "积分抵扣" |
| **按用户角色** | "权限管理" → "管理员权限" + "普通用户权限" |
| **按CRUD操作** | "用户管理" → "创建用户" + "查询用户" + "修改用户" |
| **按数据规模** | "导入用户" → "导入<1000条" + "导入大批量" |
| **按优先级** | "搜索功能" → "基础关键词搜索" + "高级筛选" |

**注意**：拆分后的故事仍需满足INVEST其他原则（尤其是I和V）

---

### T - Testable（可测试）

**定义**：用户故事有明确的验收标准，可以编写测试用例验证。

**检查项**：
- [ ] 有明确的验收条件（Acceptance Criteria）
- [ ] 验收条件可观察/可度量（非主观判断）
- [ ] 可以编写自动化测试（单元测试/集成测试）
- [ ] 测试通过即认为故事完成

**验收标准格式（Given-When-Then）**：
```gherkin
Scenario: [场景名称]
  Given [前置条件]
  When [触发动作]
  Then [预期结果]
  And [额外验证]
```

**可测试的特征**：
- 输入输出明确
- 状态变化可验证
- 错误处理可模拟
- 性能指标可度量

**违反示例**：
- ❌ "优化用户体验"（主观，无法测试）
- ✅ "用户登录页面加载时间<1.5s"（可测试）

**测试类型**：
- **功能测试**：正常流程 + 异常流程 + 边界场景
- **性能测试**：响应时间/吞吐量
- **安全测试**：权限校验/注入攻击
- **兼容性测试**：浏览器/设备

## INVEST 检查表（快速检查）

对于用户故事：
```
As a [角色]
I want to [行动]
So that [价值]
```

### 快速检查清单

| 原则 | 检查问题 | ✓/✗ |
|------|----------|-----|
| **I**ndependent | 此故事能否独立开发和交付？ | |
| **N**egotiable | 实现细节是否留有协商空间？ | |
| **V**aluable | 能否清晰说明业务价值？ | |
| **E**stimable | 团队能否估算工作量？ | |
| **S**mall | 能否在1-2个Sprint内完成？ | |
| **T**estable | 是否有明确验收标准？ | |

**通过标准**：6项全部✓

**不通过处理**：
- I/S不满足 → 重新拆分故事
- N不满足 → 去掉实现细节，聚焦"做什么"
- V不满足 → 与产品澄清业务价值，或删除此故事
- E不满足 → 补充需求细节，或创建Spike预研
- T不满足 → 补充验收条件（AC）

---

## 完整示例

### ❌ 不符合INVEST的故事

```
故事：实现用户管理模块

问题：
- I: ✗ 太大，依赖很多子功能
- N: ✗ "实现"一词过于宽泛，无协商空间说明
- V: ✗ 价值不明确
- E: ✗ 范围太大，无法估算
- S: ✗ 太大，需要1个月
- T: ✗ 无验收标准
```

### ✅ 符合INVEST的故事

```
故事：US001 - 手机号快捷登录

As a 新用户
I want to 使用手机号+验证码登录
So that 无需记忆密码，快速进入系统

验收条件：
- Given 用户已获取验证码
  When 输入正确的手机号和验证码
  Then 登录成功，跳转到首页

- Given 用户输入错误验证码
  When 点击登录
  Then 提示"验证码错误"，剩余重试次数2次

INVEST检查：
- I: ✓ 独立功能，可单独交付
- N: ✓ 实现方式可选（Redis/数据库存验证码）
- V: ✓ 价值明确（提升新用户转化率）
- E: ✓ 估算5 Story Points
- S: ✓ 3天可完成
- T: ✓ 有明确验收条件
```

## 常见反模式

### 反模式1：技术故事伪装成用户故事

❌ **错误示例**：
```
As a 开发人员
I want to 升级Spring Boot到3.x
So that 使用最新特性
```

**问题**：用户无感知，无业务价值

✅ **正确做法**：
1. 如果有性能/安全收益：
```
As a 用户
I want to 系统响应速度提升20%
So that 操作更流畅

技术实现：升级Spring Boot 3.x（利用虚拟线程）
```

2. 如果纯技术债务：创建技术任务（Tech Task），不写成用户故事

---

### 反模式2：史诗级故事（Epic）

❌ **错误示例**：
```
As a 用户
I want to 使用完整的订单管理功能
So that 管理我的订单
```

**问题**：太大，无法在1个Sprint完成

✅ **正确做法**：拆分为多个故事
```
- US001: 查看订单列表
- US002: 查看订单详情
- US003: 取消订单
- US004: 申请退款
```

---

### 反模式3：包含实现细节

❌ **错误示例**：
```
As a 用户
I want to 系统使用Redis缓存用户数据
So that 提升性能
```

**问题**：实现细节固化，无协商空间

✅ **正确做法**：
```
As a 用户
I want to 个人中心页面秒开（<500ms）
So that 快速查看我的信息

技术方案：考虑使用Redis缓存（在设计阶段讨论）
```

---

## 总结

**INVEST是质量标准，而非创作模板**

- 先写用户故事（As a... I want... So that...）
- 再用INVEST检查质量
- 不合格则调整/拆分/补充

**记住**：
- 好的用户故事是**对话的起点**，而非详细的规格说明
- INVEST帮助团队**快速迭代**，持续交付价值
- 当故事不满足INVEST时，**优先考虑拆分（Small）**
