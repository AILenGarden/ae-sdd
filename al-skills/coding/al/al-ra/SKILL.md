# al-ra — 需求分析

## 1. 定位

RA 只负责把需求本身分析清楚，产出一份**事实明确、边界清楚、行为闭合、数据可追溯、问题显式化**的需求分析结果。

RA 不负责：

- 设计架构或技术方案；
- 编写其他类型的规格、设计文档或实现计划；
- 规定其他阶段的流程、模板或交接方式；
- 编造代码结构、接口路径、类名、枚举、错误码或数据库结构。

分析可以包含对实现有帮助的业务约束和现状证据，但必须停留在需求事实、业务语义和可验证行为层面。

## 2. 核心原则

1. **先事实，后分析**：区分原始输入、现状证据、推断、假设、建议、风险和开放问题。
2. **先边界，后细节**：明确目标、范围、非目标、角色、触发器和完成条件。
3. **行为必须闭合**：每个重要行为都要有触发、前置条件、主流程、结果、异常和状态变化。
4. **数据必须可追溯**：说明数据由谁产生、从哪里进入、如何校验/转换、由谁拥有、流向哪里以及是否产生副作用。
5. **不确定性显式化**：来源冲突、信息缺失和设计改变性问题不得被静默填补。
6. **按风险裁剪**：分析深度由行为风险决定，不为追求文档长度而套用无关方法论。
7. **可验证优先**：用可观察结果、明确值域、状态、条件和证据替代“快速”“合理”“友好”等模糊表述。

## 3. 输入与证据

根据当前需求读取最小必要资料：

- 用户口述、PRD、Issue、原型、验收要求；
- 现有业务规则、流程、状态说明和术语；
- 现有系统的代码、接口定义、数据库结构、配置、枚举、测试和日志；
- 性能、安全、兼容性、合规、发布和迁移约束。

项目已有 `.al-knowledge/` 时，通过 ae-sdd 的内置知识能力定位术语和现状证据；读取 ae-sdd 入口旁的 `capabilities/al-knowledge/references/consumption-contract.md`。用户无需单独调用知识 Skill；缺少 ae-sdd 或知识库时直接回源，不要求先建库。知识缺口不补成业务事实，查询只读，维护限于当前授权范围。

重要结论使用以下标签：

| 类型 | 含义 |
|---|---|
| `Fact` | 能由输入材料或现有系统证据直接验证的事实 |
| `Decision` | 责任人已经明确确认的业务选择 |
| `Assumption` | 为继续分析暂时采用的假设，必须可追踪、可撤销 |
| `Proposal` | 分析中提出的候选方向，不是已确认事实 |
| `Risk` | 可能影响正确性、范围、兼容性、运维或验证的风险 |
| `Open Question` | 当前无法确定且需要责任人确认的问题 |

来源冲突时记录各来源和差异，不得自行选择“看起来更合理”的版本。

## 4. 分析流程

### 4.1 建立需求上下文

先明确：

- 背景和待解决问题；
- 业务目标和成功标准；
- 参与角色及其目标；
- 触发时机和使用场景；
- 范围与非目标；
- 已知约束、术语和关键假设。

### 4.2 识别业务行为

把需求拆成可独立描述的行为单元。每个行为至少包含：

```text
行为 ID
行为名称和一句话描述
触发者 / 触发事件
前置条件
主成功流程
替代流程
异常流程
后置条件和可观察结果
业务规则
状态变化
外部副作用
```

只有在角色、触发器、责任边界、发布范围或失败规则不同时才拆分行为；不要按模板机械拆分。

### 4.3 分析状态与规则

对涉及生命周期或状态的对象建立状态模型：

```text
当前状态 → 触发事件 → 目标状态
```

同时说明：

- 状态进入条件；
- 状态退出条件；
- 允许的转换；
- 禁止的转换；
- 转换产生的副作用；
- 重复、并发、过期和回退行为；
- 状态值的来源和证据。

业务规则必须写成“条件 + 规则 + 结果”，并保持唯一归属，避免同一规则在多个章节出现不一致版本。

### 4.4 分析数据来源与流转

对影响行为的每个重要字段闭合以下链路：

```text
产生者
→ 进入点
→ 可信边界
→ 校验
→ 转换
→ 业务语义
→ 权威来源/所有者
→ 保存或外部去向
→ 输出/副作用
```

至少回答：

1. 谁产生数据？
2. 数据从请求、上下文、配置、数据库、远程服务、事件还是计算结果进入？
3. 客户端是否允许提供或修改？
4. 哪个来源是权威来源？
5. 类型、值域、必填性和校验规则是什么？
6. 是否发生格式、类型、枚举或单位转换？
7. 数据由谁拥有，生命周期和时效性是什么？
8. 最终保存到哪里、传给谁或展示在哪里？
9. 是否产生审计、通知、事件或其他副作用？
10. 来源缺失、过期、冲突或不可用时如何处理？

不要把“客户端提交的值”自动当作事实；身份、租户、权限、状态、金额和归属等敏感字段必须分析可信来源。

### 4.5 分析异常、边界和组合

按实际适用范围检查：

- 输入缺失、格式错误、非法值；
- 不存在、无权限、已禁用、状态不允许；
- 重复请求、重复消息、并发修改；
- 超时、依赖失败、部分成功；
- 过期、未开始、边界值、空数据、大批量；
- 重试、补偿、恢复和人工介入；
- 多条件组合和时序敏感行为。

不适用的场景可以省略，但省略时应说明原因；不能为了达到固定覆盖率而虚构场景。

### 4.6 分析现状与变更

如果是存量系统变更，必须区分：

```text
当前行为：现有系统实际表现
目标行为：需求要求达到的表现
行为差异：新增、删除、修改和不变部分
影响范围：受影响的角色、数据、状态、接口和副作用
```

现有代码事实必须带文件路径、符号或其他可定位证据；无法验证的内容标为未知或假设。

### 4.7 形成分析结论

最后归纳：

- 已确认事实；
- 关键业务规则；
- 行为和状态结论；
- 数据来源和权威性结论；
- 异常与边界结论；
- 影响范围；
- 风险；
- 待确认问题；
- 当前是否可以结束分析。

## 5. 标准输出结构

默认使用最小充分结构；只有用户明确要求正式完整文档时，才加载旧 RAD 模板。

```markdown
# Requirements Analysis

## 0. Metadata
- ra_id / status / source / scope / updated

## 1. Requirement Context
- 背景与问题
- 目标与成功标准
- 角色与场景
- 范围与非目标
- 约束、术语、假设

## 2. Evidence Ledger
| ID | 内容 | 类型 | 来源 | 状态 |

## 3. Behavior Model
| ID | 行为 | Trigger | Preconditions | Observable Result | Owner |

### 主流程、替代流程与异常流程

## 4. Business Rules
| ID | Condition | Rule | Result | Evidence |

## 5. State Model
| Object | Current | Event | Target | Guard | Side Effect | Forbidden Cases |

## 6. Data Lineage
| Field ID | Field | Producer | Entry Point | Client Writable | Authoritative Source | Owner |
|---|---|---|---|---|---|---|

| Field ID | Type/Value Domain | Requiredness | Validation | Transformation | Destination | Freshness/Consistency |
|---|---|---|---|---|---|---|

## 7. Failure, Boundary and Recovery
| ID | Scenario | Condition | Expected Behavior | Observable Evidence |

## 8. Current-to-Target Delta
- 仅在变更分析时输出

## 9. Impact and Constraints
- 角色、数据、状态、依赖、兼容性和副作用影响

## 10. Risks and Open Questions
| ID | Type | Description | Impact | Owner | Blocking |

## 11. Analysis Conclusion
- 已确认
- 暂定
- 待确认
- 分析结论
```

按需求类型裁剪章节，不要求每次输出所有章节。

## 6. 分析模式

根据用户目标和信息状态选择模式，不把模式理解为其他阶段的交接协议：

| 模式 | 适用场景 | 最小输出 |
|---|---|---|
| `clarify` | 信息不足或表述模糊 | 已知事实、未知信息、最小问题集 |
| `behavior` | 需要梳理业务行为 | 上下文、行为、规则、状态、异常 |
| `data` | 数据含义或来源不清 | 数据来源、权威性、约束、冲突 |
| `impact` | 分析已有系统变更 | 当前/目标行为、差异和影响范围 |
| `review` | 评审需求质量 | 缺口、冲突、歧义、不可验证项 |
| `full` | 用户明确要求完整分析报告 | 按旧 RAD 模板输出，但仍遵守本 Skill 的事实和边界规则 |

如果用户没有指定模式，按输入内容选择最小充分模式；不确定时优先 `clarify`。

## 7. 质量门禁

分析完成前检查：

- 目标、范围、非目标和角色明确；
- 重要行为的触发、前置条件、结果和异常已说明；
- 状态转换和禁止行为没有遗漏；
- 业务规则写成条件、规则和结果；
- 关键字段有来源、可信边界、校验、转换和去向；
- 权威来源和数据所有者明确，或已列为开放问题；
- 现状、目标和推断没有混淆；
- 输入冲突已经显式记录；
- 重要结论有证据或被标为未知；
- 输出中的结果可以被观察或验证；
- 没有编造技术实现、代码符号或不存在的系统事实。

以下情况阻断分析完成：

- 核心目标、行为、状态或数据语义仍然无法确定；
- 关键来源冲突会改变需求范围或行为；
- 关键字段的权威来源不明且会影响正确性或安全；
- 关键异常或状态转换没有可描述的结果；
- 结论依赖未标记的假设。
