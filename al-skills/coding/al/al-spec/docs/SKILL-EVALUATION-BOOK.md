# ALSpec 三类 Skill 测评书

## 1. 目的

本测评书用于评估 `dr`、`story`、`testcase` 三个全局 Skill 是否能够让 Agent 产出可理解、可实现、可验证、可复用的规格文档。

测评关注实际决策和输出质量，不以关键词命中或章节数量作为唯一依据。每次测评都使用一个真实任务、最小必要上下文和指定模板；除非样本明确提供，不得假设 PRD、DR、Story、代码或测试存在。

## 2. 被测对象

| Skill | 文件 | 主要输出 |
|---|---|---|
| DR | `skills/dr/SKILL.md` | 技术设计、边界、决策、数据、契约、故障与运维设计 |
| Story | `skills/story/SKILL.md` | 独立行为、流程、接口/字段、规则和可观察 AC |
| TestCase | `skills/testcase/SKILL.md` | 可执行测试场景、夹具、步骤、断言、Oracle 和证据 |

项目测评使用对应的项目模板；没有匹配项目模板时使用全局模板。不得同时加载全局模板和项目模板。

## 3. 测评方式

### 3.1 测评输入

每个样本包含：

- 用户任务；
- 已确认的 `project_id` 或明确的未知项目；
- 必需的最小上下文文件；
- 允许读取的仓库/项目资产范围；
- 期望输出类型和模板。

测评输入不得提供评分结论、预期答案或待修复问题，以避免引导 Agent。

### 3.2 测评流程

1. 让独立 Agent 只加载目标 Skill、适用模板和样本列出的证据。
2. 要求 Agent 生成或审查一份完整规格。
3. 记录 Agent 实际读取的文件、选择的模板、提出的问题和最终文档。
4. 由自动检查和人工评审分别评分。
5. 对失败样本进行复盘，只修正被证据支持的问题，不为单个样本无限增加规则。

### 3.3 测评模式

- **生成测评：** 从需求、缺陷、原型、DR、Story、契约或代码证据生成规格。
- **审查测评：** 给出一份含缺陷的规格，要求识别遗漏、冲突、编造事实和不可验证内容。
- **项目匹配测评：** 分别使用未知项目和 `icec-cloud-life`，验证模板选择。
- **最小上下文测评：** 删除非必要文档，确认 Agent 不会把缺失资料当成事实。
- **冲突证据测评：** 提供互相矛盾的来源，确认 Agent 记录冲突并提出责任人与解决条件。

## 4. 统一评分模型

总分 100 分。每项按 0、半分或满分评分；评审应记录证据，不以文档篇幅加分。

| 维度 | 分值 | 评分重点 |
|---|---:|---|
| 上下文与模板选择 | 15 | 读取最小必要证据；正确选择项目/全局模板；记录选择依据 |
| 事实与未知管理 | 15 | 区分 Fact、Decision、Assumption、Risk、Open Question；不编造路径、类名、命令和字段 |
| 范围与职责 | 15 | 行为/设计/测试边界清楚；职责归属正确；没有无关扩张 |
| 语义密度 | 15 | 信息集中；术语和规则只定义一次；没有重复、历史和装饰性内容 |
| 可执行性 | 15 | 实现者或测试者无需猜测关键输入、输出、状态、数据和证据 |
| 异常与风险覆盖 | 10 | 覆盖适用的非法、权限、并发、超时、依赖失败、部分成功和恢复场景 |
| 可验证性 | 10 | 结果可观察；AC、断言或设计验收有明确证据目标 |
| 独立性与追踪 | 5 | 相关规格可选引用；不建立隐含上下游前置依赖；ID 和引用稳定 |

### 评分等级

- **90–100：** 可作为投产候选输出。
- **80–89：** 可内部使用，需要小范围修订。
- **70–79：** 有明显质量缺陷，不应直接交付。
- **0–69：** 测评失败，需要修正 Skill 或上下文加载行为。

以下任一项直接判失败，即使总分达到 80 分：

- 加载了错误模板，或同时加载全局模板与项目模板；
- 把未提供的项目事实、路径、接口、命令或类名写成确定事实；
- 把 PRD、DR、Story 或 TestCase 当作强制前置依赖；
- 关键结果不可观察或无法复现；
- 忽略样本中明确给出的冲突、安全风险或数据一致性问题；
- 输出包含流程编排、自动 handoff、文档存储协议或其他非目标流程产物。

## 5. DR 专项测评

### 5.1 必测样本

| ID | 场景 | 最小输入 | 重点观察 |
|---|---|---|---|
| DR-GEN-01 | 新增跨服务能力 | 用户目标、两个服务的现有接口、数据表 | 组件职责、接口方向、数据归属、事务/一致性边界 |
| DR-GEN-02 | 外部依赖不稳定 | 外部 API 契约、超时和错误样例 | 超时、重试、幂等、补偿、降级和恢复 |
| DR-GEN-03 | 状态机改造 | 当前状态枚举、变更需求、已有代码片段 | 允许/禁止迁移、触发条件、并发和拒绝结果 |
| DR-REV-01 | 设计文档缺陷审查 | 含重复规则、无替代方案、虚构路径的 DR | 决策证据、替代方案、成本、边界泄漏和未知项 |
| DR-PROJ-01 | `icec-cloud-life` 模块设计 | project_id、life 资产和模块结构 | life 模板、BFF/Service/SPI/Web 边界和项目事实核验 |

### 5.2 DR 专项评分

| 检查项 | 通过标准 |
|---|---|
| 设计问题 | 用问题/目标/成功信号定义设计，不直接跳到方案 |
| 决策 | 每个非平凡决策有选项、拒绝理由、接受代价、负责人和证据 |
| 架构边界 | 每个组件写清职责和非职责，协议、编排、领域和基础设施不混淆 |
| 数据设计 | 写清 owner、key/唯一性、生命周期、事务、一致性、迁移和回滚 |
| 契约 | 请求/响应、错误、认证、兼容、超时、重试、幂等和可观测性可实现 |
| 故障设计 | 依赖失败、重复、部分成功、补偿、恢复和人工介入有结果描述 |
| 验收 | 每条 `AC-*` 有 Given/When/Then、一个结果和证据目标 |

DR 专项硬失败：没有任何替代方案的关键设计决策；没有数据 owner；没有关键状态迁移规则；把 Story 细节或逐文件 CodingPlan 当成 DR 主体。

## 6. Story 专项测评

### 6.1 必测样本

| ID | 场景 | 最小输入 | 重点观察 |
|---|---|---|---|
| STORY-GEN-01 | 正常行为 | 用户需求、原型或入口描述 | 角色、触发、价值、主流程、范围和可观察结果 |
| STORY-GEN-02 | 异常行为 | 业务规则、错误码和依赖行为 | 非法、未授权、缺失、重复、超时和恢复路径 |
| STORY-GEN-03 | 字段闭环 | 请求字段、领域字段、表字段、响应字段 | source → input → domain → persistence → output 链路 |
| STORY-REV-01 | Story 质量审查 | 含模糊 AC、重复规则、越界架构的 Story | 语义密度、边界、可观察 AC 和事实证据 |
| STORY-PROJ-01 | `icec-cloud-life` 行为 | project_id、life 模板和仓库事实 | life 模板选择、接口分层和项目字段规范 |

### 6.2 Story 专项评分

| 检查项 | 通过标准 |
|---|---|
| 行为内核 | 一句话明确触发、角色/系统、可观察行为和价值 |
| 范围 | In Scope/Out of Scope、前置、后置和状态变化清晰 |
| 流程 | 每一步有输入、动作、状态变化、输出和责任边界 |
| 契约 | 实际方法/路径/事件、请求、响应、校验、错误和兼容性明确 |
| 字段 | 关键字段的来源、转换、必填性、校验、去向和原因闭合 |
| AC | 每条 AC 只有一个可观察结果，并有证据目标 |
| 边界 | 只覆盖当前行为需要的异常，不扩展成系统架构或 CodingPlan |

Story 专项硬失败：主行为无法由单一读者理解；AC 只有“正常工作/处理成功”等模糊结论；关键字段没有来源或输出；把模板示例写成项目事实。

## 7. TestCase 专项测评

### 7.1 必测样本

| ID | 场景 | 最小输入 | 重点观察 |
|---|---|---|---|
| TC-GEN-01 | 业务规则单元测试 | 规则、输入边界和预期状态 | L1 选择、确定性 fixture、业务断言和 oracle |
| TC-GEN-02 | HTTP 契约测试 | API 契约、认证、错误和数据状态 | L2 真实边界、请求/响应、错误和副作用 |
| TC-GEN-03 | 数据一致性测试 | 表结构、事务边界、失败注入 | L3 真实依赖、回滚、锁、幂等和恢复 |
| TC-REV-01 | 测试设计审查 | 含弱断言、不可重放 fixture、过度 Mock 的 TestCase | 测试层级、fixture、oracle、Mock 理由和证据 |
| TC-PROJ-01 | `icec-cloud-life` 测试设计 | project_id、模块、测试约束和模板 | 实际 runner、HTTP/DB 选择、项目技术栈和路径核验 |

### 7.2 TestCase 专项评分

| 检查项 | 通过标准 |
|---|---|
| 测试目标 | 明确被测行为/风险、动作、层级和业务结果 |
| 层级选择 | L1–L4 与风险匹配，省略项有理由或补偿证据 |
| Fixture | 初始数据、身份、权限、配置、时间、依赖状态和清理可复现 |
| 步骤 | 使用已证实的请求/命令/事件/操作，顺序明确 |
| Oracle | 能区分通过、失败和不确定，检查业务字段和副作用 |
| 失败恢复 | 失败注入、结果状态、重试/补偿/降级、恢复证据明确 |
| Mock | 只 Mock 直接外部依赖，返回值和理由明确 |

TestCase 专项硬失败：只有 HTTP 200 断言；fixture 使用生产数据；命令/路径为猜测；没有清理；无法区分失败和不确定；用 Mock 代替被测的数据库、事务或协议语义。

## 8. 自动检查

自动检查用于发现结构性错误，不替代人工评分：

- Skill frontmatter 和目录有效；
- registry 中三类全局 Skill、模板路径和项目映射有效；
- 当前项目模板与全局模板不同时加载的规则存在；
- 模板不包含 Skill 加载说明或维护流程说明；
- 运行时 Skill 不包含 changelog、流程交接、存储协议和自动 handoff；
- 发布包不包含 `life-dr`、`life-story`、`life-testcase` Skill；
- 所有 `AC-*`、`TC-*`、`DEC-*` ID 格式有效；
- 发布包中的 registry 引用路径全部存在。

建议命令：

```text
python scripts/validate_registry.py .
python -X utf8 C:/Users/EDY/.codex/skills/.system/skill-creator/scripts/quick_validate.py skills/dr
python -X utf8 C:/Users/EDY/.codex/skills/.system/skill-creator/scripts/quick_validate.py skills/story
python -X utf8 C:/Users/EDY/.codex/skills/.system/skill-creator/scripts/quick_validate.py skills/testcase
python -m unittest discover -s tests -p "test_*.py"
```

这些是维护验证命令，不是 `al-spec` 产品 CLI。

## 10. 投产门槛

三个 Skill 各至少通过：

- 2 个生成样本；
- 1 个审查样本；
- 1 个项目模板匹配样本；
- 1 个最小上下文样本；
- 1 个冲突证据样本。

每个 Skill 要求：

- 平均分 ≥ 85；
- 没有硬失败；
- 所有项目模板匹配正确；
- 所有关键结果可观察或可复现；
- 人工评审认为没有系统性重复、编造事实或流程依赖。

三类 Skill 的整体投产门槛：

- 总体平均分 ≥ 88；
- 任一 Skill 平均分不得低于 85；
- 发布包验证通过；
- 最近一次评测结果和证据已归档；
- Skill、模板、registry 和发布包版本一致。
