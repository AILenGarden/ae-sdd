# ALSpec 总入口

这是 ALSpec 的任务分流入口。先判断用户要处理的规格类型，再加载且只加载对应的类型 SKILL 和规范模板；不要把三个类型的规则混合到同一份文档中。

## 能力清单

- **DR（Design Requirements）**：描述系统级设计、边界、架构决策、接口契约、数据与运行后果。
- **Story**：描述一个可验证的业务行为或用户能力，包括触发、规则、状态变化和验收条件。
- **TestCase**：描述可执行、可重放、可判定并能留证的测试场景。
- **审查**：对已有 DR、Story 或 TestCase 检查完整性、证据和可实现性，仍按原类型加载对应 SKILL。

当前不负责 PRD 或 CodingPlan；如果请求主要是需求澄清或代码实现，应转交相应的需求分析或编码能力，除非用户明确要求产出上述三类规格之一。

## 类型判定

按用户的目标而不是关键词选择：

| 用户目标 | 选择 |
| --- | --- |
| 设计整体方案、模块边界、架构、契约、技术决策或运行影响 | `al-spec:dr` |
| 定义一个业务行为、用户故事、状态流转或验收规则 | `al-spec:story` |
| 定义测试步骤、fixture、oracle、证据或回归场景 | `al-spec:testcase` |
| 审查已有文档 | 识别文档原类型，再选择对应 SKILL |

若一个请求同时包含多种产物，先按交付物拆分，分别调用对应类型；不要用 DR 代替 Story，也不要用 Story 代替 TestCase。若类型确实无法判断，先依据主要交付目标作最小假设，并在文档中记录该假设。

## 加载顺序

1. 阅读 `framework/registry.yaml`，确认类型注册和项目模板映射。
2. 加载一个且仅一个目标类型的 `skills/<type>/SKILL.md`。
3. 若已确认项目 ID，使用该类型映射的项目模板；否则使用全局模板。
4. 先按公共加载契约检查现有项目代码和项目资产，再按类型 SKILL 的要求读取必要证据，然后创建或审查文档。
5. 在结果中记录实际加载的 SKILL、模板、项目 ID（如有）、代码/资产路径及选择理由。

`framework/loading-contract.md` 是加载协议；`framework/registry.yaml` 是唯一发现表。`standards/` 下文件是维护参考资料，不是运行时额外的规范来源。项目模板只改变模板与词汇，不会自动产生新的项目 SKILL。

## 硬约束

- DR、Story、TestCase 相互独立；一个类型不能强制要求另一个类型存在。
- 只能使用注册表中启用的类型和模板。
- 不要凭项目名称推断项目 SKILL；只有显式注册的项目 SKILL 才能加载。
- 先分流和加载上下文，再写作或审查；不要直接套用记忆或自定义结构替代 canonical template。
