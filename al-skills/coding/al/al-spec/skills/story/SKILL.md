# Story

## 写前必须加载的上下文

1. 确认仓库和 `project_id`，选择一个模板：有项目模板就用项目模板，
   否则用 `templates/global/story.md`。`icec-cloud-life` 使用
   `templates/project/life-story.md`。
2. 主动查找并读取当前需求对应的 RA、DR、PRD 和原型；存在就必须读取，
   不得因用户描述看似完整而跳过。工具输出被截断时继续读取。
3. 加载适用的项目约束、规范和资产。
4. 检查相关代码、接口、Schema、配置和测试，确认：
   - 已实现哪些相关功能；
   - 哪些能力、接口或数据结构可以复用；
   - 本次需要新增、修改或保持什么。
5. 记录上下文路径、模板选择理由和关键证据。文档不存在无需补造；无法
   访问或来源冲突时明确标记，并说明对 Story 的影响。

区分已确认事实、拟定行为、假设、风险和未决问题；不得把模板示例、推测
的类名、路径、错误码或命令写成事实。

## 写作约束

- 严格遵守已加载的项目约束和本模板。
- 信息密度高、可读性高：术语和规则只定义一次，删除重复和无关说明。
- 内容完整：不得因压缩遗漏需求、价值、范围、规则、字段、状态、异常、
  契约或验收标准。
- 排版正确：标题层级、列表、表格、链接、代码块和空行符合 Markdown。
- 按模板组织产出；不适用的必填项说明原因，可选项按实际内容填写。
- 删除最终文档中的占位符和示例数据。
- 不写 changelog、修订日志、评审记录或执行日志。

## Story 写作方法

先写一句行为概括：

```text
当 <触发条件> 时，<角色/系统> 可以 <可观察行为>，从而 <获得的价值>。
```

用业务动作表达行为，不用“新增类、修改表、调用方法”等实现动作代替。
随后明确前置条件、后置条件、状态变化、责任方、范围内和范围外内容。

主流程从触发写到结果；只保留会影响业务规则、状态、契约、可观察结果或
运行后果的技术步骤。异常流程从实际判断点和失败点推导，按需覆盖非法输入、
权限、数据缺失、重复/重试、并发、超时、依赖失败、部分成功和恢复，并写明
条件、响应或可见结果、最终状态、副作用及是否允许重试。

重复使用的业务规则用 `BR-*` 标识，定义条件、判断、结果和责任方。关键字段
说明来源、类型/转换、必填性、校验、去向和语义原因，尽量闭合：

```text
来源 → 入口/请求/事件 → 应用/领域 → 持久化/外部系统 → 输出/副作用
```

相关 REST、SPI、事件或 UI 契约只写当前行为所需的入口、方向、调用方、输入输出、
校验、业务错误，以及会改变行为的认证、幂等、顺序、超时、重试、限流、兼容性
和界面状态。

从行为概括、规则、状态、主流程和适用异常推导 `AC-*`。每条 AC 使用
Given/When/Then，验证一个具体可观察结果，并指出观察位置。不要编造验收要求，
也不要把 AC 写成测试步骤、fixture 或 Mock 配置。

## 交付前检查

确认已读取应读上下文、核实项目现状和复用能力、正确选择模板；行为、范围、
流程、异常、字段、契约和 AC 没有遗漏或矛盾；事实与假设已区分；Markdown 可
正确渲染；没有 changelog、流程产物或未经证实的实现细节。
