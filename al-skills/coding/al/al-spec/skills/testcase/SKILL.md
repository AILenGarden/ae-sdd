# TestCase

## 写前必须加载的上下文

1. 确认仓库和 `project_id`，读取本插件的 `../../framework/registry.yaml`，
   选择一个模板：精确项目映射优先，否则使用全局模板。`icec-cloud-life`
   使用 [life 模板](../../templates/project/life-testcase.md)，其他项目使用
   [全局模板](../../templates/global/testcase.md)，不同时加载两个模板。
2. 主动查找并读取对应的 RA、PRD、DR、Story、原型、接口契约和测试约束；
   存在就必须读取。工具输出被截断时继续读取。文档不存在无需补造；无法访问
   或来源冲突时记录并说明对验证的影响。
3. 检查相关代码、现有测试、测试工具、构建命令、Schema、配置、夹具和环境，
   确认已覆盖什么、可复用什么、本次需要验证什么。
4. 记录上下文路径、模板选择理由和证据；区分事实、假设、风险和未决问题，
   不得猜测路径、类名、命令、请求、响应或测试数据。

## 写作约束

- 遵守已加载约束和模板；信息密度高、可读性高、内容完整、Markdown 正确。
- 按模板产出；不适用的必填项说明原因，删除占位符和示例数据。
- 不写 changelog、修订日志、评审记录、执行日志或流程产物。
- TestCase 描述验证设计；实现方案、架构决策和业务行为仍由相应规格或代码负责。

## 测试设计方法

先明确：

```text
给定 <系统状态/风险>，执行 <测试动作>，以证明 <可观察业务结果>。
```

按风险、影响和失败代价选择最小充分的测试层级：L1 单元、L2 接口/契约、L3
集成、L4 端到端。低层测试覆盖规则和转换，高层测试只保留关键用户旅程；不要
用大量 E2E 代替可更快、更稳定的单元和集成测试。省略层级或场景时说明理由和
补偿证据。

根据被测规则选择设计技术：

- 输入有范围、长度、格式或枚举时，用等价类覆盖有效/无效分区，并测试边界及
  边界相邻值；
- 多个条件组合决定不同结果时，用决策表覆盖关键组合；
- 存在状态或事件时，用状态迁移表覆盖允许、禁止和终态迁移；
- 多参数组合影响结果时，使用有依据的组合覆盖，说明为何不穷举；
- 接口、事件或消息契约变化时，验证请求/响应结构、兼容性、错误和消费者可用性。

## 用例、Oracle 与证据

每个 `TC-*` 写清前置条件、确定性夹具、顺序步骤、预期业务结果、副作用、Oracle、
清理和证据位置。步骤使用已核实的请求、命令、事件、数据库操作或 UI 操作。

断言业务字段、持久化数据、事件、状态和副作用，不只断言 HTTP 状态或“不抛异常”。
Oracle 必须能区分通过、失败和不确定，并说明观察位置、判定条件和证据形式。关键
失败要写注入条件、结果状态、重试/补偿/降级、恢复动作和恢复证据。测试数据必须
隔离、可复现且不含生产数据。

只 Mock 直接外部依赖，并记录返回值、注入失败和理由；数据库、事务、锁、队列、
缓存、回调、协议和幂等语义在可行时使用真实依赖。命令、测试入口、路径和证据位置
必须有来源，不得为填充模板自行编造。

## 交付前检查

确认上下文、项目现状、复用能力和模板已核实；风险、层级、覆盖技术、夹具、步骤、
Oracle、清理和证据完整；业务结果和副作用已断言；适用失败/恢复已覆盖；事实、
假设和风险已区分；无占位符、编造内容或流程产物。
