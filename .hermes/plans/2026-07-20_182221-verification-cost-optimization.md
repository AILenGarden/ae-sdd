# ae-sdd Verification Cost Optimization Implementation Plan

> **For Hermes:** Execute this plan task-by-task only after ae-sdd has completed the required large-route design documents and the user has approved `state.executionPlan`. Do not delegate or create commits unless the user explicitly authorizes those actions.

**Goal:** Replace ae-sdd's mock-heavy, shallow, mostly serial verification package with a user-oriented black-box scenario strategy that proves real behavior through repeatable HTTP and persistence flows, while also using risk tiers and fingerprints to avoid unrelated tests, repeated scans, and repeated review work.

**Architecture:** Make test validity the first gate and cost optimization the second gate. Every executable HTTP contract gets a scenario manifest describing actors, state transitions, requests, response assertions, persisted-state assertions, cleanup, and a repeatable command. The approved `state.executionPlan` remains the human-authorized contract; `state.verificationPlan` derives the scenario obligations plus V0-V3 lanes and fingerprint-bound evidence. Unit tests remain only for pure logic or explicitly isolated fault injection; acceptance evidence must use a real running boundary and real persistence where the Story requires it. Existing schema-v1 plans remain strict and are never silently downgraded.

**Tech Stack:** Python 3 standard library, existing ae-sdd CLI/operations/state/evidence modules, pytest/unittest test suite, Markdown SKILL/standards sources, compiled runtime generated by `scripts/build_dist.py`.

---

## 1. Current context and confirmed causes

- `tools/lib/verification_plan.py` already schedules focused/module tests and defers full Story regression for production-code changes, but the Test Generate contract still describes L1-L4 as the normal execution package.
- `source/skill-fallbacks/skills/phase3-review/test-review-skill.full.md` performs TV-1~TV-10 plus an independent sample rerun, while phase transition gates re-evaluate G-09 and G-CODE-1.
- HTTP AC currently requires local real HTTP and test-environment HTTP with the same build ID for every admitted HTTP contract.
- Evidence already supports immutable snapshots and safe reuse, but gate execution does not consistently convert a reusable evidence hit into a no-subprocess fast path.
- Missing or invalid work-item scope falls back to a full-repository scan.
- Existing runtime telemetry measures CLI commands and scanner spans, but not test-authoring, test-execution, review, retry, or cache-hit wall time as distinct verification categories.
- The current TestCase template permits `INSERT / Builder / Mock` data setup and records HTTP level/stage, but does not require a user-oriented state-transition scenario, complete field round-trip assertions, persisted-state assertions, or a repeatable command.
- The HTTP authenticity scanner blocks MockMvc/internal mocks when it sees them, but there is no equivalent blocker for "HTTP AC exists but has no executable HTTP scenario" or "scenario only asserts status code".
- A test can therefore be technically non-mocked and still be shallow: it may call a method, assert `200`, and never prove that data was persisted, returned, updated, isolated, or recoverable through the public interface.

## 2. Mandatory ae-sdd route before implementation

This is a cross-cutting change to workflow semantics, state, gates, evidence, SKILL instructions, and generated runtime. Treat implementation as a **large** ae-sdd self-update:

1. Produce or update RA covering verification cost, quality risk, backward compatibility, and rollout.
2. Produce or update DR defining policy authority, tier derivation, evidence reuse, and gate semantics.
3. Produce a Story containing contracts, fields, flows, data model, AC, and a verification matrix.
4. Resolve project constraints and the complete CodingModel.
5. Persist the compact `state.executionPlan` and obtain explicit user approval.
6. Only then modify code, tests, standards, or generated runtime.

The `.hermes/plans/` document is an implementation aid and does not replace the required RA/DR/Story or the approved `state.executionPlan`.

## 3. Target contracts

### 3.0 Test validity is a prerequisite to cost optimization

Risk tiering only answers **how much** to verify. It does not answer whether the chosen test can expose a real defect. The implementation must enforce the following order:

1. **Validity:** the test crosses the boundary that users cross and can fail on a real defect.
2. **Depth:** the test validates the complete state transition, not only an HTTP status or a mocked return value.
3. **Repeatability:** another agent or CI can rerun the same scenario from a clean/isolated state.
4. **Evidence:** request, response, persisted state, expected values, command, build ID, and artifacts are recorded.
5. **Cost:** only after 1-4 are satisfied do V0-V3 and fast/final/release lanes select the minimum required amount of work.

#### Mock policy

- HTTP/API acceptance tests must not mock the system under test, Controller, Service, Repository, Mapper, ORM, transaction boundary, or internal event path.
- `MockMvc`, direct Controller invocation, `MockBean`, `SpyBean`, service/repository mocks, and an in-memory fake replacing the persistence path cannot satisfy an HTTP AC.
- Test doubles remain allowed only for external systems outside the Story boundary, explicit fault injection, and pure deterministic unit tests. Every such double must state the external boundary, injected failure, and why a real dependency cannot be used.
- A unit test may support confidence but never replace the minimum required black-box scenario for an HTTP, DB, transaction, authorization, or persistence AC.

#### Required black-box scenario contract

For every HTTP AC, create a scenario record with at least:

```json
{
  "scenarioId": "SC-USER-UPDATE-ALL-FIELDS",
  "acIds": ["AC-002"],
  "actor": "authenticated-user",
  "preconditions": ["service-ready", "isolated-tenant"],
  "setup": {"strategy": "real-http-or-fixture-seed", "dataSet": "user-full-v1"},
  "steps": [
    {"method": "POST", "path": "/users", "bodyRef": "user-full-v1"},
    {"method": "GET", "pathRef": "created-id"},
    {"method": "PATCH", "pathRef": "created-id", "bodyRef": "user-full-v2"},
    {"method": "GET", "pathRef": "created-id"}
  ],
  "assertions": {
    "http": ["status", "schema", "all-response-fields"],
    "state": ["all-writable-fields", "server-managed-fields", "persistence"],
    "invariants": ["identity-stable", "tenant-isolated"]
  },
  "cleanup": {"strategy": "delete-or-namespace", "required": true},
  "repeatability": {
    "command": "<project-native-http-test-command> --scenario SC-USER-UPDATE-ALL-FIELDS",
    "baseUrlParameter": "HTTP_BASE_URL",
    "seedParameter": "TEST_SEED"
  }
}
```

#### Minimum scenario families for write APIs

The Story/contract matrix must expand every write endpoint into the following user-facing families when applicable:

1. **Create round trip:** create a record, query detail, and compare every response field and every persisted writable field against the submitted intent. Verify server-managed fields separately.
2. **Full update round trip:** create a complete record, modify every writable field, query detail, and compare the complete post-update state. Verify immutable identity/version fields remain correct.
3. **Partial update semantics:** omit fields, send `null`, send empty values, and send unchanged values; verify the API's documented distinction between omitted/null/empty.
4. **Read/list consistency:** detail, list, filtering, sorting, pagination, and count results agree for the same record and tenant.
5. **Negative and abuse paths:** duplicate/replay, malformed type, missing required field, invalid enum, boundary length, Unicode/encoding, unauthorized actor, cross-tenant ID, stale version, and unsupported method.
6. **Lifecycle cleanup:** delete/disable/archive then query, list, and repeat the operation; verify the documented 404/410/idempotent outcome and no orphaned state.
7. **Failure atomicity:** force a downstream or validation failure and verify no partial write, event, audit record, or cache state remains unless explicitly expected.

The examples supplied by the user (create -> detail and create -> update every field -> detail) are mandatory baseline scenarios, not optional illustrative tests.

#### Field and state coverage

For each request/response field, record whether it is writable, readable, server-managed, nullable, defaulted, normalized, immutable, or security-sensitive. The scenario manifest must identify the expected value after each state transition. A test that asserts only `2xx`, non-empty JSON, or object existence is shallow and cannot satisfy an HTTP AC.

#### Effectiveness proof

The harness must include a small, repeatable effectiveness check for representative endpoint families. Seeded defects should include at least one persistence-field mapping error, one update-path omission, one response-field omission, and one authorization/tenant-isolation failure. The scenario suite must fail when each defect is introduced. This is a pilot/CI quality check rather than a requirement to run a full mutation campaign on every commit.

#### Repeatability rules

- The scenario can run by ID from a clean checkout with a supplied `baseUrl`, build ID, and seed/namespace.
- Test data is isolated by namespace/tenant or deterministic cleanup; execution order is not a hidden prerequisite.
- The scenario records the exact command and supports rerunning only that scenario after a failure.
- Evidence contains normalized request/response payloads, expected-vs-actual field diff, persistence observation, logs, and artifact hashes.

### 3.0.1 HTTP coverage gate

Add a lightweight blocker gate, proposed as `G-HTTP-1`, for HTTP contracts:

- every HTTP AC maps to at least one executable scenario;
- every write endpoint has the required round-trip scenario families or a documented, user-approved exception;
- the scenario has a repeatable command, base URL parameter, isolation/cleanup strategy, and complete field/state assertions;
- the scenario is not satisfied by MockMvc, direct Controller calls, internal mocks, or status-only assertions;
- the recorded command is runnable and produces a request/response plus state evidence.

`G-HTTP-1` validates presence and shape. G-09 validates authenticity and evidence integrity. Neither gate should rerun the full HTTP suite when a valid scenario evidence fingerprint already exists.

- `requiresTestEnv=true` forces V3 release-lane HTTP evidence.

### 3.2 Derived executable contract

Upgrade `state.verificationPlan` to schema version 2 while preserving schema-v1 reads:

```json
{
  "schemaVersion": 2,
  "storyId": "STORY-001",
  "workItem": "WI-001",
  "policy": {
    "tier": "V1",
    "riskSignals": [],
    "affectedACs": ["AC-002"],
    "reviewMode": "mechanical"
  },
  "lanes": {
    "fast": ["compile", "focused-test", "G-09-scoped", "G-CODE-1-delta"],
    "final": ["module-test"],
    "release": []
  },
  "required": ["compile", "focused-test", "module-test", "G-09-scoped", "G-CODE-1-delta"],
  "deferredUntilFinal": [],
  "deferredUntilRelease": ["full-story-regression"],
  "notRequired": ["http-test-env"],
  "sourceExecutionPlanFingerprint": "sha256:...",
  "planFingerprint": "sha256:...",
  "evidenceInputFingerprint": "sha256:...",
  "changedPaths": ["src/A.java"]
}
```

Rules:

- `sourceExecutionPlanFingerprint`, changed paths, risk policy, command selection, and toolchain inputs all participate in the fingerprint.
- A change to production code, test code, execution plan, Story AC boundary, toolchain, or scanner ruleset invalidates only dependent evidence.
- A valid fingerprint match allows a gate to validate the attestation without launching the scanner subprocess again.

### 3.3 Tier matrix

| Tier | Minimum triggers | Fast lane | Final lane | Release lane | Review |
| --- | --- | --- | --- | --- | --- |
| V0 | Documentation/format-only; no executable contract change | schema/lint | none | none | findings-only mechanical check |
| V1 | Pure logic or bounded internal production code | compile, focused tests, scoped authenticity | affected-module tests | full Story regression deferred | mechanical evidence review |
| V2 | DB/transaction/local HTTP/build behavior | V1 plus affected integration boundary | real DB or local real HTTP | environment regression deferred unless declared | logical multi-perspective review |
| V3 | Public API, auth/security, money, data loss, concurrency, irreversible action, cross-Story, release-critical | V2 | full affected integration | test-environment/cross-Story evidence | independent verifier plus full depth review |

Legacy schema-v1 plans and missing policies must retain the current strict HTTP and reviewer behavior.

## 7. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Tier heuristic underestimates risk | Story/user/boundary rules have higher precedence; ambiguity escalates; protected risks force V3 |
| A test is realistic but still shallow | G-HTTP-1 requires state transitions, field-level assertions, persistence observations, cleanup, and a standalone rerun command |
| HTTP test exists only on paper | G-HTTP-1 requires a runnable command and execution evidence; missing command is a blocker |
| Generic scenario helper hides defects | Require explicit field matrix and seeded-defect effectiveness checks for representative endpoint families |
| Eliminating mocks removes useful fault-injection coverage | Keep doubles for external boundaries and explicit fault injection, but never count them as primary HTTP/DB acceptance evidence |
| Cache hides new defects | Bind reuse to content, scope, execution plan, toolchain, command, scanner version, and ruleset fingerprints |
| Deferred tests are mistaken for PASS | Represent deferred lanes explicitly; completion gates require them only at their declared target lane |
| Existing projects unexpectedly become less strict | Schema-v1 and missing-policy paths retain legacy strict semantics |
| G-09B/review-depth weakening becomes a loophole | Policy-aware applicability with downgrade checks; blockers and tampering always block |
| Source and compiled runtime diverge | Modify authoritative source/fallbacks, rebuild, runtime verify, update-check; never hand-edit generated runtime |
| Performance tests become flaky | Assert scanner invocation counts and cache semantics deterministically; treat wall-time comparisons as pilot telemetry, not hard unit-test thresholds |
| Plan schema duplicates executionPlan | `executionPlan.verificationProfile` is approved intent; `verificationPlan` is a deterministic derived artifact with a source fingerprint |

## 8. Rollout strategy

1. Land the scenario manifest, G-HTTP-1, and repeatable HTTP runner contract first; do not enable cost-tier defaults while HTTP coverage can still be absent or shallow.
2. Run the seeded-defect effectiveness pilot against representative create/update/list/delete/authorization endpoint families.
3. Land schema-v2 support behind compatibility behavior: legacy remains strict.
4. Enable generated V0/V1 policies for documentation and bounded pure-code changes only after their supplemental unit tests are proven not to replace required black-box scenarios.
5. Enable V2 for DB/local-HTTP work after real persistence and local HTTP evidence is stable.
6. Keep V3 as the default for public HTTP AC, security, money, concurrency, irreversible, and cross-Story work.
7. Compare at least representative V0-V3 samples using scenario defect-kill results, verification wall time, scanner invocation count, rerun count, failed-review rate, and defect-escape signals.
8. Change defaults only after the evidence shows lower cost without reduced scenario effectiveness or V3 assurance.

## 9. Open decisions for the approving Story/DR

1. Whether build/config changes default to V1 or V2; recommended: V2 when runtime behavior or packaging changes, V1 for non-runtime developer tooling.
2. Whether V2 review uses one logical multi-perspective reviewer or an independent session; recommended: logical review by default, independent when a protected risk signal exists.
3. Default budgets by tier; recommended starting values are descriptive telemetry targets, not blockers, until pilot data exists.
4. Whether release-lane execution occurs inside the same work-item state machine or is consumed by CI/release automation; recommended: record the obligation in the work item and allow CI to satisfy it with fingerprint-bound evidence.
5. Whether missing scope should immediately block or first attempt deterministic git-diff recovery including untracked files; recommended: attempt safe recovery once, then block with remediation rather than silently scan the full repository.
6. Whether persistence assertions observe through a second public read API, a read-only test query, or both; recommended: use a second public read whenever available, and use a read-only DB observation only when the Story explicitly requires storage-level proof.
7. Whether scenario data is authored as JSON/YAML fixtures or language-native builders; recommended: keep the scenario contract data-driven and let the project-native runner bind it to its language without duplicating the scenario definition.
8. Whether seeded-defect checks run on every change or scheduled representative endpoint families; recommended: representative families in CI/nightly and whenever the scenario harness or contract changes, not every local edit.
