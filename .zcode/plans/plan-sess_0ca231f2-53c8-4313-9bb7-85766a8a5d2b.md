# 修复计划：ae-sdd hook 死锁 + Pbl.md 缺陷 1/2/4

## 背景

Pbl.md（基于 v3.9.22 会话复盘）列了 4 条缺陷。经 v3.10.3 源码核实：
- **缺陷3（memory 摩擦）已被 v3.10.3 重构彻底解决**（L1-L4 五层 + enter/exit 三段式全废弃，改为业务实体树 + compact.md），**无需修复**。
- 实际要修：hook 死锁（基础设施，前置依赖）+ 缺陷 1/2/4。
- 核实还揪出 Pbl.md 没提到的连带问题：`flow_monitor` 与 `gate_intercept.PHASE_ENTRY_GATES` 双源不一致（G-05 残留触发）。

## 修复 0：hook 死锁——ae-sdd 自身仓库豁免（P0 基础设施）

**根因**：`D:\Item\ae-sdd` 是 ae-sdd 工具本体源码仓，永远不会有 `.ae-sdd/`（它不是落地项目）。但用户在此仓内发 `/ae-sdd` 触发词时，`prompt_inject` 会写 `.ae-sdd-pending-init` 标记，`gate_intercept._check_pending_init_intercept` 随后无差别拦截所有 Write/Edit/Bash——连"修 hook 自己"都拦，形成死锁。源码中**没有任何自身仓库豁免逻辑**，v3.10.2 只补了 disengage 暗号当逃生口。

**修法**：在 `_check_pending_init_intercept`（`gate_intercept.py:891`）入口加一道前置豁免——若 cwd 落在 ae-sdd 工具自身仓库内，直接放行，不进 pending-init 拦截分支。

**自身仓库判定**：从 cwd 上溯最多 5 层，若某层目录同时含 `tools/bin/ae-sdd` 文件 + `tools/lib/gate_intercept.py` 文件，判定为 ae-sdd 工具自身仓库。双文件标志避免误判普通项目。

**改动文件**：
- `tools/lib/gate_intercept.py`：新增 `_is_ae_sdd_self_repo(cwd)` 辅助函数（~10 行），在 `check_intercept` 的 pending-init 分支（`:988-990`）之前插入豁免检查。豁免只跳过 pending-init 拦截，不影响已初始化项目的正常门禁。
- `tools/tests/test_pending_init_deadlock_fix.py`：新增用例 `test_self_repo_exempt_from_pending_init`——在模拟的 ae-sdd 工具仓库结构（含 tools/bin/ae-sdd + tools/lib/gate_intercept.py）下，触发词写标记后，Write/Edit 不应被拦截。

**风险**：低。豁免条件严格（双特定文件名），误判概率极低。且只豁免 pending-init 分支，已 init 项目的门禁不受影响。

## 修复 1：G-05 glob 与 TASK 文件名不匹配 + flow_monitor 双源不一致（P0）

**根因**（核实确认）：
1. `gates.py:359` 的 G-05 用 `list_docs(project_dir, current_story, "-task-*.md")`，期望文件名 `STORY-004-BE-task-*.md`。
2. `document_storage.py:50` 的 TASK 模板产出 `{docId}.md`（doc_id 缺省 = story_id），即 `STORY-004-BE.md`。两者永远不匹配。
3. v3.10 主链 `PHASE_ENTRY_GATES`（gate_intercept.py:768-804）已摘 G-05，但 `flow_monitor.get_phase_gate_map()`（flow_monitor.py:89）残留 `code-reviewed -> ["G-05"]`，经 UserPromptSubmit hook 每轮调用 `detect_drift` 仍会触发 G-05 误报漂移。

**修法**（双保险）：
1. **flow_monitor 对齐主链**：`flow_monitor.py:89` 的 `"code-reviewed": ["G-05"]` 改为与 `PHASE_ENTRY_GATES` 的 code-reviewed 项一致（`["G-00", "G-09", "G-CODE-1", "G-10", "G-11", "G-REVIEW-DEPTH"]`），消除双源不一致。同时清理 `task-generated`/`task-reviewed` 等 v3.10 已砍的 legacy phase 映射。
2. **修 G-05 glob**（防未来回归）：`gates.py:359` 的 `-task-*.md` 改为 `.md`（匹配 `{docId}.md` 实际产出），使 G-05 被调用时结果正确。保留 `check_g05` 函数不删（避免破坏现有 TestG05 测试），但更新测试用例的文件名期望。
3. **补一致性单测**：新增 `test_intent_gate_glob_consistency`——遍历 _PATH_TEMPLATES 的 TASK 类 intent，用模板生成路径落文件，再跑 G-05 检查，确保写读对齐。

**改动文件**：
- `tools/lib/flow_monitor.py:80-91`：对齐 PHASE_ENTRY_GATES，清理 legacy 映射。
- `tools/lib/gates.py:359`：glob `-task-*.md` → `.md`。
- `tools/tests/test_gates.py`（TestG05 类）：更新文件名期望（`STORY-001-task-001.md` → `STORY-001.md`）。
- `tools/tests/test_gates.py`：新增 intent-gate 一致性用例。

## 修复 2：doc save 写读分桶不一致——story_id 非空时优先用 story_id 作目录名（P0）

**根因**（核实确认，比 Pbl.md 描述更深）：
- 写入侧：`document_storage.py:296` `effective_work_item = work_item_id or story_id or doc_id or task_name`，"按 Story 归档"intent 目录名用 `{workItem}`。当传 `--work-item Story-004 --story-id STORY-004-BE` 时，目录 = `Story-004`。
- 读取侧：`paths.list_docs`（paths.py:660）硬编码 `Task/{story_id}` 目录，用 **story_id 分桶**。
- **写读分桶键不一致**——这才是 Pbl.md "路径脱节"的真正根因。v3.7.4 "升级为 WorkItem 分桶"只改了写入侧，没改读取侧，埋下不对称。

**修法**：统一写读到 story_id 分桶（当 story_id 非空时）。
- `document_storage.py:296`：对"按 Story 归档"intent（CODING_PLAN/CODING_REPORT/CODING_ISSUE_LOG/CODE_REVIEW/TESTCASE/TESTCASE_COMPLIANCE_REPORT/TESTCASE_REVIEW/TEST_REPORT/TRACE_MATRIX/STORY_REVIEW/REVIEW_UPDATEPLAN/REVIEW_COMPARE/PROPOSAL/PROPOSAL_ARCHIVE/STORY_SUPPLEMENT/STORY_GENERATE_PLAN/STORY_WRITER_REPORT/TASK/TASK_SUPPLEMENT/TASK_WRITER_REPORT/TASK_REVIEW/TASK_IMPL_PLAN），当 `story_id` 非空时，目录名优先用 `story_id` 而非 `work_item_id`。story_id 为空时（BUG/OPT 无 story）回退到 `work_item_id`，保持 WorkItem 分桶兼容。
- 用 `_STORY_SCOPED_INTENTS` 集合显式声明这组 intent，避免散落判断。

**兼容性**：
- BUG/OPT 场景（无 story_id）：行为不变，仍走 work_item_id 分桶。现有测试 `test_work_item_id_buckets_task_without_story_id` 不受影响。
- Story 场景（有 story_id）：目录名从 work_item_id 变为 story_id，与读取侧 list_docs 对齐，与既有文档树（`Coding/STORY-004-BE/`）一致。
- `task_name` 回退分支：CLI 无 `--task-name` 参数（核实确认），此分支从不触发，保留不删（库 API 可能用）。

**改动文件**：
- `tools/lib/document_storage.py`：新增 `_STORY_SCOPED_INTENTS` 集合 + 修改 `effective_work_item` 计算逻辑（~8 行）。
- `tools/tests/test_document_storage.py`：新增用例 `test_story_scoped_intent_uses_story_id_as_dir`（同时传 story_id + work_item_id，断言目录 = story_id）+ `test_bug_task_keeps_work_item_bucketing`（无 story_id，断言目录 = work_item_id）。
- `source/skill-fallbacks/skills/cross-cutting/document-storage-skill.full.md`：更新分桶说明，注明"story_id 非空时优先 story_id 分桶"（消除文档与代码漂移，遵循 AGENTS.md 红线11）。

## 修复 4：只读 state 命令 work-item 歧义时按 mtime 自动推断（P2）

**根因**（核实确认）：
- `resolve_default_state`（work_item_context.py:410-411）在 `len(active_candidates) > 1` 时直接 `raise AmbiguousWorkItemError`，无 mtime 兜底。
- 旧 mtime 推断逻辑（ae-sdd:217-234）已退化为死代码（`_active_state_from_mirror` 在 :182 return None 短路）。
- `state read`/`state next-step` 遇歧义直接 `_emit_work_item_ambiguity` + return 1（虽列候选，但不自动推断）。

**修法**：给 `resolve_default_state` 加 `prefer_recent: bool = False` 参数。
- `prefer_recent=True` 时（只读命令用）：歧义场景按 `candidate.path.stat().st_mtime` 降序取最近活跃的 work-item，返回它并标注 `source="recent-by-mtime"`，不抛错。
- `prefer_recent=False` 时（写门禁用）：保持原硬拒绝行为，不放松。
- `state read`/`state next-step` 的 CLI 调用链（`_main_state_path_for_args`）传入 `prefer_recent=True`。
- `gate_intercept.check_intercept` 的写门禁调用链不传（默认 False），保持硬拒绝。
- 歧义时输出改为：候选列表 + "已按最近活动时间自动选中 {key}（如非预期请显式传 --work-item）"。

**改动文件**：
- `tools/lib/work_item_context.py:383-413`：`resolve_default_state` 加 `prefer_recent` 参数 + mtime 排序分支。
- `tools/bin/ae-sdd`：`_main_state_path_for_args` 加 `prefer_recent` 透传；`cmd_state_read`/`cmd_state_next_step` 传 `prefer_recent=True`。
- `tools/tests/test_cli_state_work_item.py`：新增用例 `test_state_read_auto_picks_recent_by_mtime_on_ambiguity`（两个活跃 work-item，断言 read 自动选 mtime 更新的那个）+ 确认 write 仍硬拒绝。

**风险**：中。mtime 推断可能选错（如用户其实在改旧 work-item）。但只读命令选错只是"看了错 state"，无破坏性，且输出明确提示"如非预期请显式传 --work-item"。写命令不放松，保证安全。
