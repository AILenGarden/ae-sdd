## 业务流程全景 `必填`

> 在进入主流程细节之前，先用一段话和一张表说清楚这个 Story 干了什么。
> 让任何人不看代码、不看主流程，就能理解：收到什么 → 做了什么 → 改变了什么 → 返回什么。

### 一句话描述

> {角色} 通过 {触发方式}，{业务动作}，最终 {业务结果}。

### 输入 → 处理 → 输出

| 维度 | 内容 |
|------|------|
| **输入** | 谁发起（角色/系统）、传入什么数据（关键入参字段及其业务含义） |
| **前置状态** | 系统/数据在处理之前必须处于什么状态（存在性/状态枚举/权限等） |
| **核心处理** | 系统执行了哪些关键业务动作（校验了什么、计算了什么、改变了什么，用业务语言描述，不写类名方法名） |
| **最终效果** | 哪些数据从什么值变成了什么值（字段级，例如：`ticket.status: WAITING → IN_PROGRESS`） |
| **输出** | 返回给调用方什么（关键出参字段及其含义） |
| **副作用** | 是否触发了其他动作（发了什么事件/通知/MQ，改了哪些关联数据） |

> 示例（坐席接单）：
>
> **一句话描述：** 坐席通过接单接口领取一个待接单工单，工单状态变为处理中，坐席与工单绑定。
>
> | 维度 | 内容 |
> |------|------|
> | **输入** | 坐席（agentId 来自登录上下文）、工单 ID（ticketId，路径参数） |
> | **前置状态** | 工单存在且状态为 `WAITING`；坐席在线且未达最大并发数 |

## 主流程 `必填`

> **视角**：系统处理视角，描述系统处理了什么，不描述代码怎么写。
> **颗粒度**：每一步对应一个可独立失败、可独立验收或可独立观测的业务处理动作。
> **步骤类型**：`校验` / `查询` / `判断` / `执行` / `持久化` / `调用` / `通知` / `返回`
> **边界**：主流程只写处理顺序和业务结果；分层职责、类名、方法名、DTO/DO/PO 转换写入"实现伪代码"；字段级来源、字段赋值、DB 列变化写入"数据操作（CRUD）逻辑"和"字段链路映射"。
> **允许**：允许写业务级数据变化，例如"将工单状态从待接单变为处理中"。
> **禁止**：禁止写具体类名、方法名、Mapper、Repository、Controller、ServiceImpl、事务注解、字段逐项赋值。
> **拆分规则**：每步原则上只标一个主类型。若查询与存在性校验的失败处理完全一致，可合并为一个查询步骤；若查询失败、记录不存在、状态非法对应不同错误码或不同处理策略，必须拆成独立步骤。

### 步骤类型说明

| 类型 | 使用场景 | 颗粒度要求 |
|---|---|---|
| 校验 | 入参格式、权限、状态、业务前置条件、幂等条件校验 | 同一类失败处理可以合并；不同错误码或不同处理策略必须拆开 |
| 查询 | 查询本地实体、关联实体、配置、外部依赖数据 | 每次关键查询单独成步；查询不到时必须说明失败去向 |
| 判断 | 根据查询结果或当前状态走不同业务分支 | 必须写清分支条件和对应异常流程/后续步骤 |
| 执行 | 执行业务决策、状态流转、计算、生成业务变更 | 只写业务级变化，不写字段级赋值 |
| 持久化 | 插入、更新、删除、批量写入 | 只写持久化意图；字段明细写入 CRUD 逻辑 |
| 调用 | 调用外部系统或上游/下游服务获取结果 | 必须说明失败时是否阻断、降级、重试或补偿 |
| 通知 | 发送事件、MQ、站内信、Push、WebSocket 等 | 必须说明失败是否影响主流程 |
| 返回 | 返回成功结果、幂等结果或错误结果 | 返回内容写业务含义，不写 VO 字段赋值 |

### 字段设计原则 🔴

> 数据模型中的**每一个字段**都必须能回答以下四个问题，无法回答的字段视为设计不清晰，禁止进入实现阶段。

| 问题 | 对应维度 | 说明 |
|------|---------|------|
| 这个字段为什么有必要存在？ | **必要性** | 如果删掉这个字段，哪个业务场景会出问题？不能用"方便扩展""以后可能用"作为答案 |
| 什么场景会用到这个字段？ | **使用场景** | 哪个接口读它、哪个业务逻辑写它、哪个调用方依赖它——至少有一个具体场景 |
| 这个字段的数据来源是否有效？ | **来源有效性** | 数据从哪里产生（用户输入 / 系统计算 / 外部服务 / 常量）？该来源是否可信、可追溯、不会为空？ |
| 这个字段是否能够正确处理？ | **可处理性** | 类型是否合适（Long/BigDecimal/String/Boolean）？空值如何处理？枚举值是否完整？边界值能否正确存取和转换？ |

> **判定规则：** 四个问题任意一个无法回答 → 🔴 阻断型：字段设计缺陷，必须在进入 Coding 前补全。

### 测试分层

| 层级 | 测试对象 | 测试策略 | 外部依赖处理 |
|------|---------|---------|-------------|
| L1 接口 | Controller / Facade | 🔴 能用真实 HTTP 请求测的，必须走真实 HTTP（SpringBootTest RANDOM_PORT + TestRestTemplate），不退化成方法调用或 MockMvc | Mock 签名验证、Mock 第三方服务 |
| L2 应用 | AppService | 直接方法调用，Mock 仓储/领域服务 | Mock Repository、Mock 外部 Client |
| L3 领域 | DomainService / 聚合根 | 纯单元测试 | Mock 一切外部依赖 |
| L4 基础设施 | Repository / Filter | 集成测试或 Mock | Mock DB Connection |

### 测试原则

1. **能走真实链路就不用模拟**：能走真实 HTTP 的接口走真实 HTTP，核心落库走真实 DB，不用 MockMvc/全 Mock 替代
2. **由外而内**：先验证接口层行为，再验证业务逻辑
3. **分层 Mock**：每层只 Mock 直接依赖，不跨层 Mock
4. **外部依赖隔离**：签名校验、外部 API 调用等使用 Stub 或 Mock
5. **异常优先**：先测试异常路径，再测试正常路径

### 常见问题处理

| 问题 | 解决方案 |
|------|---------|
| 真实 HTTP 测试序列化失败 | 🔴 修复序列化配置（Jackson 配置/字段注解），不得退回方法调用或 MockMvc 绕过——序列化失败正是真实 HTTP 要暴露的问题 |
| 签名验证复杂 | Filter 层可独立单元测试，但接口主流程仍需走真实 HTTP 端到端验证一次 |
| 第三方 API 调用 | 使用 WireMock 或 Mock Server |
| 数据库依赖 | 使用 H2 内存数据库或 Mock MyBatis-Plus Mapper |

### 测试层级选择决策

| 场景 | 推荐测试层级 | 说明 |
|------|------------|------|
| 纯算法/领域逻辑（如签名校验、状态机） | 单元测试 | 直接实例化测试，无外部依赖 |
| 应用层编排（如 AppService 调用 Repository） | 单元测试 + Mock | Mock 直接依赖，保留业务逻辑验证 |
| Controller 接口（参数校验、返回值封装） | 接口测试 | 🔴 真实 HTTP（SpringBootTest RANDOM_PORT + TestRestTemplate），MockMvc 仅框架过老时降级 |
| 涉及真实外部系统（融云、极光） | 联调测试/集成测试 | 单元测试阶段标记为 ⏸️ Skip |
| 涉及真实数据库事务 | 集成测试 | 单元测试阶段标记为 ⏸️ Skip |

### 不可单元测试的识别

以下情况不适合单元测试，应标记为联调/集成测试：
- 需要真实外部系统（融云 Webhook、极光推送等）
- 需要真实数据库事务和回滚
- 需要完整 HTTP 链路验证
- 需要网络通信时序（如超时、重试）

## 实现伪代码 `必填`

> 用**分层调用骨架**表达实现大方向：哪层调哪层、调用顺序、关键分支 / 事务边界 / 状态判定落在哪。目的是把握大方向，不是写完整实现。
> - 🔴 只写骨架，不写具体语法 / 完整实现（那是 Task 核心代码的事，本节不替代 Task）。
> - 🔴 **分层职责必须正确**（依据分层职责红线）：领域逻辑（状态流转/不变量/计算）写在 Domain；业务编排（调用顺序/事务边界/协调多依赖）写在 Application；Repository 只出现存取调用（find/save/update）。伪代码里若把业务判断写进 Repository，即暴露设计错误。
> - 标注每层职责注释，让读者一眼看清调用链是否分层合理。

```
// Interfaces 层：协议适配 + 参数校验
XxxController.method(req):
    @Valid 校验入参格式
    return xxxAppService.method(req 转 command)

// Application 层：业务编排 + 事务边界（不写领域规则）
@Transactional
XxxAppService.method(cmd):
    entity = xxxRepository.findById(cmd.id)        // 取
    if entity == null: throw XxxNotFoundException  // 异常路径
    entity.doDomainLogic(cmd.xxx)                  // 领域逻辑下沉到 Domain
    xxxRepository.save(entity)                     // 存
    publish(XxxEvent)（事务提交后触发）            // 事务外通知
    return XxxConverter.toDTO(entity)

// Domain 层：领域逻辑（状态流转规则、业务不变量、计算）
XxxEntity.doDomainLogic(xxx):
    if 不满足业务前置条件: throw XxxException
    if !canHandle(当前状态, 业务事件): throw IllegalTransitionException
    变更字段（充血模型自身完成）

// Infrastructure 层：Repository 只做存取（无任何业务判断）
XxxRepositoryImpl.save(entity):
    po = XxxConverter.toPO(entity)
    xxxMapper.updateById(po)   // 乐观锁 version
```

> 示例（业务事件驱动的状态机）：
>
> ```
> // Interfaces：参数校验 + 转发
> TicketController.claim(ticketId, request):
>     @Valid 校验请求格式
>     return ticketAppService.claim(ticketId, 当前操作人, request.remark)
>
> // Application：编排 + 事务边界
> @Transactional
> TicketAppService.claim(ticketId, operator, remark):
>     ticket = ticketRepository.findById(ticketId)          // 系统读取当前状态
>     if ticket == null: throw TicketNotFoundException       // → AC-002
>     ticket.handle(TicketEvent.CLAIM, operator, remark)     // 领域事件驱动状态机
>     ticketRepository.save(ticket)                          // 存
>     publish(TicketClaimedEvent)（提交后触发）               // 事务外
>     return TicketConverter.toDTO(ticket)
>
> // Domain：状态流转规则 + 不变量
> Ticket.handle(event, operator, remark):
>     if !canHandle(this.status, event): throw IllegalTransitionException  // → AC-003
>     根据业务事件计算下一状态并记录处理人/处理时间/原因
>
> // Infrastructure：Repository 只存取
> TicketRepositoryImpl.save(ticket):
>     ticketMapper.updateById(TicketConverter.toPO(ticket))  // 乐观锁 version
> ```

> **状态机红线：** 生命周期状态机不得把 `targetStatus` 作为主入口参数，不得公开 `updateStatus` / `changeStatus(targetStatus)` 驱动流转。调用方提交业务命令/事件，系统内部读取当前状态并决定下一状态。

## 验收记录 `选填（Story 完成时填写）`

> 支持拆分验收：可按实现任务分批验收，不必等待全部完成。不可测试的 AC 需标注原因。

### 拆分边界

**可拆分的验收单元：**
- 按实现任务拆分（如：DDL/PO/Mapper → 接口实现 → 业务逻辑 → 集成测试）
- 按依赖拆分（如：纯内部逻辑 → 依赖外部系统 → 端到端）
- 按测试层级拆分（如：单元测试 → 接口测试 → 集成测试）

**不可拆分的最小单元：**
- 单个 AC 不可拆分，必须作为一个整体验收
- 同一批次的 AC 应同时验收或同时 Skip

### 拆分原则

| 原则 | 说明 |
|------|------|
| 依赖驱动 | 前置批次通过后，才能启动后续批次 |
| 独立可验 | 每批次应能独立验证，不依赖未实现的代码 |
| 风险隔离 | 高风险项（外部依赖、集成点）放后期批次，尽早暴露问题 |
| 增量价值 | 每批次完成应产生可用的功能增量 |
